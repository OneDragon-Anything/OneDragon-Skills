# 运行时迭代深度细则(阶段 8,生命周期视角)

> 本文件是 SKILL.md 阶段 8 的按需读深度细则(**生命周期视角**)。**op 级运行时技术(信息密度 / 调试纪律 / 预料外画面调研 / 运行时不确定性预留日志 / 重复建op)single source 在 `od-dev-write-operation/references/runtime-craft.md`** —— 本文件只给生命周期层的迭代节奏 + 事件 loop 模式,op 级细节去那里读。

## 探索式迭代(为什么阶段 8 是循环,不是善后)

自动化脚本**需求不可完备**:阶段 1 玩法建档只能摸**大概**(主流程 + 主要决策点),玩法的分支 / 子状态 / 边缘情况(随机事件、条件子界面、过渡叠层、各类结算、失败路径…)建档时摸不清,要实机跑到才暴露。故初始方案只是骨架,工作方式是**建档-led 增量**:

**实现(阶段 5)→ 测试(阶段 6)→ 发现未预期状态 / 分支 → 补建档 + 补分支(回阶段 3 画面建档 / 阶段 4 设计 / 阶段 5 实现)→ 再测,循环到稳定。**

**这与肉鸽无必然关系** —— 大部分玩法都有分支(肉鸽只是密)。这是自动化开发的**根本工作方式**,贯穿阶段 5-8,不是某玩法类型的善后阶段。op 级怎么写才适应它(激进拆小 op 单跑定位 / 决策点多 log 多截图 / 预料外画面调研建档 / 调试先读日志 / 重复手动建op)见 `od-dev-write-operation`(探索式主线 + `runtime-craft.md`)。

## §事件长尾 —— 边玩边重构(loop 层)

多分支玩法**事件类型巨多**,没法一次写全。生命周期层(loop)方法论:
- **loop 跑,卡在哪个事件,就读屏 + 加一个 handler op,再跑。**(handler op 怎么写 / 调试见 `od-dev-write-operation`)
- 兜底:任何匹配不到的状态走 fallback(点空白 / ESC),避免死循环。
- 每跑深一点冒新事件是常态,别指望一次覆盖。
