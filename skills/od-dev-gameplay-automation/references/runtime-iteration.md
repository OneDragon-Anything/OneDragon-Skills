# 运行时迭代深度细则(阶段 8,生命周期视角)

> 本文件是 SKILL.md 阶段 8 的按需读深度细则(**生命周期视角**)。**op 级运行时技术(信息密度 / 调试纪律 / 预料外画面调研 / 运行时不确定性预留日志 / 重复建op / **随机态钩子(采集/停机)** / **过渡帧与瞬态假象**)single source 在 `od-dev-write-operation/references/runtime-craft.md`** —— 本文件只给生命周期层的迭代节奏 + 事件 loop 模式,op 级细节去那里读。
> **随机态钩子分流判据**:**bot 能继续推进但 reader 不可靠 → 采集钩子**(存样本 bot 继续跑,离线设计 reader;细作法见 `od-dev-screen-onboarding` 随机/条件态节);**bot 卡住无法推进(未建档画面/无分支匹配)→ 停机钩子**(停 bot 保画面当场建档;细作法见 `od-dev-write-operation` runtime-craft「钩子触发停 bot 留画面」节;钩子生命周期判据[临时捕获 vs 常驻兜底 / flag 三要素 / 停机→留证降级治理]与停机现场处理协议见 `od-dev-stop-hooks`)。**埋任何一类钩子前必加前置门**:reader 只在**目标画面态锚点命中**时才算数 —— 锚点不命中(面板收起 / 未展开 / 过渡帧)时 reader 的「空读 / 全 miss」是伪信号(画面态非法,非目标态出现),直接跳过(不停机 / 不写 sentinel / 不存样本);**钩子触发 = 画面态合法 且 reader 检出,缺一不可**(实现步见 runtime-craft 同节)。**过渡帧/瞬态视觉假象**(动画残影假阳、阈值灰区假 MISS)见 `od-dev-write-operation/references/framework-pitfalls.md` 坑 8/9;**场景切换半开帧(主体先渲染、overlay 后弹 → 识别对但状态没定型)**的分发前稳定门 / op 入口出口定型门见 `od-dev-write-operation/references/runtime-craft.md`「settle-then-dispatch」节;截图时机(操作后等动画再截)见 `od-dev-screen-onboarding`。

## 探索式迭代(为什么阶段 8 是循环,不是善后)

自动化脚本**需求不可完备**:阶段 1 玩法建档只能摸**大概**(主流程 + 主要决策点),玩法的分支 / 子状态 / 边缘情况(随机事件、条件子界面、过渡叠层、各类结算、失败路径…)建档时摸不清,要实机跑到才暴露。故初始方案只是骨架,工作方式是**建档-led 增量**:

**实现(阶段 5)→ 测试(阶段 6)→ 发现未预期状态 / 分支 → 补建档 + 补分支(回阶段 3 画面建档 / 阶段 4 设计 / 阶段 5 实现)→ 再测,循环到稳定。**

**这与肉鸽无必然关系** —— 大部分玩法都有分支(肉鸽只是密)。这是自动化开发的**根本工作方式**,贯穿阶段 5-8,不是某玩法类型的善后阶段。op 级怎么写才适应它(激进拆小 op 单跑定位 / 决策点多 log 多截图 / 预料外画面调研建档 / 调试先读日志 / 重复手动建op)见 `od-dev-write-operation`(探索式主线 + `runtime-craft.md`)。

## §事件长尾 —— 边玩边重构(loop 层)

多分支玩法**事件类型巨多**,没法一次写全。生命周期层(loop)方法论:
- **loop 跑,卡在哪个事件,就读屏 + 加一个 handler op,再跑。**(handler op 怎么写 / 调试见 `od-dev-write-operation`)
- 兜底:任何匹配不到的状态走 fallback(点空白 / ESC),避免死循环。
- 每跑深一点冒新事件是常态,别指望一次覆盖。

## §跨玩法偏离的运行时恢复(loop 调度层)

> §事件长尾的兜底是「任何匹配不到的状态走 fallback(点空白 / ESC)」。但有一类未匹配状态**不能**走这个兜底 —— bot 偏离到了**非目标玩法**:命中画面属于另一个玩法(认知完整,只是非当前在跑的目标)。对它点空白 / ESC 只会让 bot 卡在错玩法里反复转,导航不回目标。须**先分类再分派**。

**loop 的未匹配状态分派,先分类**(每轮读屏未命中目标玩法任何已知画面时):
- 命中画面属于**目标玩法**的未建档事件 / 分支 → 走 §事件长尾(读屏 + 加 handler op + 兜底 fallback)。
- 命中画面属于**非目标玩法**(认得它是玩法 B,但 B 不是当前在跑的玩法 A)→ **不走通用 fallback**,走下方「导航回目标」恢复。

**导航回目标(跨玩法偏离恢复,禁停)**:
1. **退非目标玩法 B**:用 B 画面档案的状态流转出口回到通用枢纽画面(大世界 / 主菜单类)。
2. **进目标玩法 A**:从枢纽走 A 的入口导航路径(查 A 的 screen doc / application 入口节点链)回到 A 的工作画面。
3. **续被打断的工作**:回 A 后接续,不从头重启、不 stall。
- **判据复用 `od-dev-screen-onboarding` 的「跨玩法偏离协议」**(认知完整但非目标 → 导航回,非探索 / 非停);本节补的是 **loop 调度层**怎么把这个恢复落进未匹配状态分派,screen-onboarding 补的是 dev 遇偏离怎么手动导航回 + 把恢复路径建进 screen_info / doc。

**禁止**:stall / 盲重试同一偏离画面 / 走通用 fallback(点空白 ESC 会卡在错玩法)/ 停下等用户指示 —— 偏离是可恢复的运行时状态,导航回目标是 bot 职责,不是中断理由。

**依赖 + 降级**:导航回目标需 B 的出口 + A 的入口路径都已在画面档案建模。**未建档 → 不能自动恢复 → 记日志 + 上报**(别盲循环烧回合);同时触发 `od-dev-screen-onboarding` 补建档(把偏离路径 + 恢复导航建进 screen_info / doc),补全后 loop 后续遇同偏离自动恢复。

**三个「防偏离」别混(不同维度)**:
- **任务进度防偏离**(`progress-tracking.md` §2 防偏离门):**dev 的焦点纪律** —— 别让自主 loop / agent 漂离主线工作(如没打地基就调策略)。
- **dev 跨玩法偏离**(`od-dev-screen-onboarding` ADR-0016):**dev / 建档遇偏离**怎么手动导航回 + 建档防再偏。
- **运行时跨玩法偏离恢复**(本节):**bot loop 自主运行**遇偏离怎么调度恢复。

## §验证信号分层(取最小可归因信号 + 长跑并行)

> 验证一个改动该取什么信号、长任务跑的时候人在干嘛 —— 两条纪律一起守。**适用于一切验证**(op / reader / 策略 / 流程),不只策略调优;策略侧引用见 `strategy-craft.md` T1。

**归因判据(先问再验)**:这个信号**能归因到本次改动吗**?
- **可归因信号**:单次操作的客观前后差异(识别结果变化 / 动作落地证据)、一轮日志、一次识别输出 —— 信号与改动之间没有别的变量。
- **不可归因信号**:整局胜负 / 通关时长 / 多局统计 —— 被 策略+随机性+词缀+商店 多因素污染,赢了不知归谁,输了不知怪谁。这类信号只配给**已经是多变量改动包**的最终评估用,不配验证单点修复。

**偶发类问题的样本判据**:修复对象是偶发现象(间歇失败 / 低概率误判)时,单次成功不算修复 —— 连续 N 次命中无复发才算确认(N 按原发生频率定,别拍脑袋);确认前的每次长跑都是又一次采样机会(配合下方并行协议,成本近零)。**取最小可归因信号即止**:判定改动生效 / 失效后**立刻转下一件未阻塞任务**,别干等全量结局“再确认一下” —— 结局等来也只是噪声。反例:① 干盯长跑等结局(空转,期间什么都该做);② 用整局胜负验证单点修复(误诊,噪声当归因)。

**长跑并行协议**:启动分钟级长跑(对局 / 采集 / 验证)本身是合法推进;启动后**靠被动渠道回收**(钩子 / 哨兵文件 / 日志 / 完成通知),期间推进其他未阻塞任务(离线代码 / 接线 / 文档 / 数据)。判据:**启动长跑后没事干只能盯它 = 该去找下一件未阻塞的活,不是等**。与 build-craft「实现-测试流水线」划界:那节管 op **实现期**的写→测→写下个 流水线;本节管**验证信号选择** + 任意长任务的并行纪律 —— 互补不复制。

**bot 跑 / 等加载 / 等刷新期间同理**(原「等待时别闲着」):同时做别的事(自检类似坑 / 预写日志 / 补画面建档 / 沉淀经验),别纯 sleep。
