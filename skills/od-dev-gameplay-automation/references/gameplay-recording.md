# 玩法建档深度细则(阶段 1)

> 本文件是 SKILL.md 阶段 1「玩法建档」的**按需读深度细则**(到了阶段 1、想把玩法理解固化成文档时读;与 `screen-identification.md` 是阶段 3 的深度细则对称)。
> **只覆盖阶段 1 的「玩法记录」部分**(理解玩法本身、把客观事实记成文档)。阶段 1 的另一个产出**画面清单**见 SKILL.md 阶段 1 正文(它直接衔接到阶段 3 画面建档)。
> 与「画面建档」(阶段 3)不同层次:本文件记**玩法本身**(玩家视角的事实,游戏怎么玩);画面建档记**画面怎么识别**(screen_info / area)。
> **定位**:SKILL.md 阶段 1 判据(能口述机制 + 一局流程 + 决策点)是**达标线**(脑子懂了);本文件是**把懂的固化成可复用文档**的深度做法 —— 简单玩法口述够用,复杂玩法(子系统多 / 跨局状态多 / 后续要反复查)值得落成文档。这是深度细则,**不抬达标线**(和 `screen-identification.md` 一样:阶段判据不变,深度细则按需读)。

## 核心原则:玩法是客观事实,不是代码的附属

游戏玩法(定位 / 机制 / 流程 / 数据 / 状态 / 边界等)是**游戏本身提供的客观事实** —— 无论自动化代码怎么写、改不改、过不过时,玩法都不变。

- **源是游戏本身,不是代码;数据源按权威三级排序:游戏内图鉴 > 官方资料站 > wiki / 攻略**。代码只是"当下怎么自动化的",会过时、会错、会改;玩法事实由游戏决定。三级判据:同一事实多源冲突,以高级别为准;wiki / 攻略只采信"玩法技巧"类主观总结,**数值 / 机制不采信 wiki**(编辑质量不可控);图鉴条目(游戏自带数据库)对数值 / 效果文本是 canonical,官方资料站次之。
- **玩家视角记**(游戏怎么玩),不是代码视角(怎么自动化)。
- **客观事实 vs 推断分区**:查来 / 实机验证的 = 事实(标来源);自己推理 / 攻略推测的 = 推断(标【待验证】,优先从游戏验证,别写成既成事实)。
- **玩法文档的漂移来源是游戏版本更新**(机制 / 数值改了),不是代码改动 → 更新时**核对游戏**(图鉴 / 官方),不核对代码。

## 记什么:一个玩法的全部面向

把玩法当一个交互系统,记录它这些面向(每个回答一个不同问题):

| 面向 | 回答 | 典型内容 |
|---|---|---|
| 定位 | 这玩法是什么 / 追求什么 / 入口在哪 | 一段话:类型(肉鸽 / 自动战斗 / 节点制 / …)、玩家目标、游戏内入口;**含难度 / 模式变体**(有哪些难度或模式;各模式差异散到对应面向记 —— 规则差异归机制、数值 / 敌人差异归数据);**含多人 / 社交交互**( coop / PVP / 排行榜,若有) |
| 机制 | 怎么运作 / 规则 / **触发条件** | 玩法级(一次性):**时机模型**(实时 / 回合 / 可否暂停)+ **自动段 vs 需手动操作段**(哪些段系统自动跑如 auto-battle、哪些段要玩家操作)+ **胜负条件**(怎么算赢 / 输)+ **随机性**(哪些元素每局 / 每回合随机刷新、哪些固定;随机源)。规则级(每条规则):运作逻辑 + 触发条件 |
| 流程 | 怎么走 / 每步做什么 / 做了会怎样 | 玩家路径 + 每步的**操作**(玩家在此做的游戏动作,如买角色 / 升级 —— 决策层,不是"点哪个 UI 元素",那是阶段 3)+ **决策点**(玩家在此做什么选择)+ **游戏内后果** + 分支 |
| 数据 | 有哪些实体 / 关键数值多少 | 涉及的实体(角色 / 装备 / 羁绊 / 敌人 / 道具 …)+ **关键数值**(见下定义) |
| 状态 | 跨局带进什么 / 局内进度怎么追踪 | **跨局持久化**(继承 buff / 进度 / 跨局继承布局 —— 容易漏故特别提示)+ **局内进度怎么追踪**(靠什么标识"进行到哪",如第几层 + boss 击杀数;玩家动作序列见流程,不重复) |
| 边界 | 什么时候能玩 / 花什么 / 给什么 | 解锁前置 + 消耗(体力 / 周限 / 次数)+ 产出奖励;**含跨模式联动**(本玩法产出 / 进度是否影响其它模式,若有) |

**关键数值 = 影响自动化决策(买 / 升 / 卖 / 选)或玩家策略判断所依赖的数值**(HP 公式 / 概率 / 消耗 / 阈值);纯展示性数值引图鉴不抄。规则内自带的数值随规则记在机制,数据面向按实体汇总关键数值,两者交叉引用不互斥

**实体全集要建模进代码(识别 / 决策依赖一类对象的全集时)**:全部 boss / 词缀 / 装备 / 卡片 / 角色这类"要认全的对象",最终落**正规模型类 + 注册表**(类型关系可查询、数据可校验、跨实体关系用引用非字符串拼接),而非裸字典 + 魔法字符串。**双源收敛**:一旦代码注册表全量建模,对应 data doc 即冗余 → 删(doc 只是"代码未全量建模"时的过渡源,留着必漂移);注册表条目标注来源(图鉴编号 / URL + 游戏版本),版本敏感数据(卡池 / 数值 / meta)显式标版本、跨版本待核。

**策略消费的数值表 / 曲线(等级→费用表 / 概率表 / 成长曲线)别自己估**:粗估表进决策模型 = 和错误观测同级的污染(下游照着算,错得自信)。采集按上面三级源;权威表拿不到 → 向会玩的用户要(口述门槛表是权威 ground truth);再不行才标「粗估待核」并让消费端降权,别静默当真值用。。

**机制 vs 流程的归属**(同一事实两边都沾时):运作逻辑(规则怎么跑,与玩家操作无关)归**机制**;玩家路径中的决策与该决策的游戏内后果归**流程**。机制记规则本身,流程引用机制结论不重抄。

**面向是内容清单**(保证不漏该记的),不是文件结构 —— 文件怎么拆见「怎么组织文件」,是另一个轴。

**(决定落文档时)每个面向先默认要写**;判定可空的标准 = 实机跟走 / 查官方时该面向确实没有任何内容(如无跨局持久化的纯单局玩法)。**空的面向也写一行「查证无此面向」**,不留静默空白(防"看起来简单就跳过")。

## 怎么收集(从游戏里提事实,边玩边记)

收集骨架(搜官方 / 图鉴理类型与流程 → 实机跟走)见 SKILL.md 阶段 1 正文;本文件只补**落到文档时**的增量:

1. 实机跟走时每到新画面记"玩家在此做什么选择 + 选择的**游戏内后果** + 进出条件"(画面清单同时产生,衔接阶段 3)。
2. **查不到的标【待验证】**,优先下次实机验证;验证通过后把标注换成来源,**别留过期待验证**。
3. **每条标来源**,格式(玩法文档专属):`来源=图鉴条目(编号/名称)/ 官方 URL / 实机观察 / 口述(会玩的用户) + 游戏版本`。
4. **机制类知识先 grep 代码数据面,再采口述**:数据注册表/常量文件的 docstring 与数据化资产里已写明的游戏明文效果,直接引用;口述只补代码面没有的部分——顺序反了,按口述建的知识在粒度/数值/产物上与库内权威数据打架,整篇返工。
5. **图用文本框线图,禁 mermaid/图形语法**(判据与理由 = od-dev-writing-skills 的 design-docs.md「图示」节)——玩法文档的流程/结构图在纯文本环境必须可读。

## 记到什么程度(治"太简单"的病根)

"太简单"不是没写,是**写得太抽象**(空话)。每个面向要具体到**能拿游戏验证、能照着判断**。用**结构模板**(填空骨架,方法论级,不绑具体游戏)替代抽象叙事:

- **定位**:`类型=[肉鸽/…] → 目标=[玩家追求] → 入口=[游戏内入口] → 难度/模式变体=[各模式差异] → 多人交互=[有/无] → 来源=[版本]`
- **机制 —— 玩法级**(整个面向填一次):`时机模型=[实时/回合/可否暂停] → 自动还是手动=[哪些段自动/哪些手动] → 胜负条件=[赢/输分别怎么算] → 随机性=[哪些每局/每回合随机、哪些固定、随机源] → 来源=[版本]`
- **机制 —— 规则级**(每条规则填一条):`触发条件=[具体条件] → 规则/效果=[具体效果] → 来源=[图鉴/版本]`
  - ✗ "某系统是肉鸽节点"(空话)
  - ✓ `触发条件=持有X状态的角色进某画面 → 效果=弹出A/B选项,A给团队某效果/B某角色接收,不选可跳过 → 来源=图鉴#123/<版本>`
- **流程**(每步填一条):`玩家路径=[第N步] → 操作=[买角色/升级/…决策层动作] → 决策点=[A/B/C] → 选A的游戏内后果=[…] → 分支=[满足X走甲路/否则乙路] → 来源=[实机+版本]`
  - ✗ "打几关就结算"(空话)
  - ✓ `第N步操作=买角色A → 决策点=买/不买 → 选'买'的游戏内后果=金币-10、角色A加入阵容、牌池中A少一张 → 分支:金币够走甲路/不够走乙路 → 来源=实机+<版本>`
- **数据**:`实体=[名/类别] → 关键数值=[HP/概率/消耗/阈值] → 来源=[图鉴/版本]`(全量实体引图鉴,只记关键数值)
- **状态**:`跨局持久化=[继承什么buff/进度,单局玩法写'无'] → 局内进度追踪=[靠什么标识进行到哪,如第几层+boss击杀数]`
- **边界**:`解锁前置=[条件] → 消耗=[体力/周限/次数] → 产出=[奖励] → 跨模式联动=[影响哪些其它模式,若无写'无']`

**填多少条**:玩法级机制填一次;规则级机制 / 流程步骤有多少就填多少条(机制有多少条规则填多少条、流程有多少步填多少步);定位 / 状态 / 边界通常各一条。

**游戏内后果是流程的核心内容**(不是独立面向):不只记"有这个交互 / 能点",还要记"这个交互在游戏内产生了什么后果" —— 这是玩法的语义,是策略 / 决策的依据。

## 怎么组织文件(简单单文件,复杂多文件)

**从一个文件开始**,所有面向写在一个 doc(总览 + 各面向)。**某面向内容膨胀到单文件难维护 / 难查 / 需独立更新时,才拆出独立文件** —— 不按复杂度等级硬分,按实际内容量。

**拆的判据**(满足任一才拆该面向):
- 该面向内容量大,单文件里找信息要翻很久(难查)。
- 该面向需要独立 / 频繁更新(如全量数据随版本变),独立出来不污染其它面向。
- 该面向是独立子系统,拆出来更清晰。

**子系统是什么**:玩法内自成一体的一块,有自己的机制 + 数据 + 流程(如战斗块 / 经济块 / 养成块)。**识别测试:这块能否脱离其它部分独立讲清楚?能 → 是子系统**。

**拆的组织方式**:按**玩法自身的结构**(玩家怎么理解这玩法就怎么组织)拆,通常按子系统,**不是**机械地按"面向"拆。拆完每个子系统文件内,检查它涉及的面向是否记全。

- **入口文件(总览 / README)永远只有一个**:玩法定位 + 流程总图(文字步骤大纲即可,串起各子系统)+ **面向 → 文件映射**(各文件负责哪些面向 / 子系统,方便跨文件核对)+ 边界。不管拆成几个文件,入口只一个。
- **全量数据(实体表)量大时独立**(它的更新频率 / 查询方式与机制不同);量小则并入机制文件。
- **全局流程**(串起子系统的玩家路径)放入口文件或独立流程文件;**全局状态**(跨子系统的局内 / 跨局)同理。
- 简单玩法(机制浅 / 数据少 / 流程短)→ 单文件足够,**别为拆而拆**。

**文档放哪 + 内容边界(重要)**:
- **落点**:项目的玩法文档目录 `docs/game/<玩法>/`(入口 `README.md` 或玩法名命名)。
- **`docs/game/` 只放游戏玩法本身** —— 玩家视角的客观事实(机制 / 流程 / 数据 / 状态 / 边界):这玩法游戏本身提供的规则,**游戏版本更新才改,与自动化代码无关**。不懂代码的人读 `docs/game/` 应能读懂(纯游戏知识)。
- **自动化实现归别处**:bot 流程(op 链 / 编排)、决策日志(why 选 X 不选 Y)、策略(怎么打)、踩坑归 `docs/develop/<玩法>/`(开发文档);进度 / 临时调研归本地 `.debug/`。
- **判据**(某条信息放哪):「游戏改了它变,还是代码改了它变?」前者 → 游戏玩法 → `docs/game/`;后者 → 自动化实现 → `docs/develop/`。这是上「核心原则」(玩法 = 客观事实、不是代码附属)的落点推论 —— 玩法文档记的是游戏事实,不是"当下怎么自动化"。

## 成品长什么样(参考:一个简单玩法的完整骨架)

简单玩法单文件即可。以虚构占位玩法为例,6 面向填完长这样(复杂玩法按子系统拆多文件,入口文件串起):

- **定位**:类型=回合节点肉鸽 → 目标=清 N 层拿奖励 → 入口=主城→玩法入口 → 难度/模式=普通/困难(数值差异归数据)→ 多人交互=无 → 来源=实机+<版本>
- **机制(玩法级)**:时机=回合可暂停 → 自动/手动=战斗 auto-battle 自动、节点选择手动 → 胜负=清 N 层胜 / 主角血归零负 → 随机=每层商店随机刷 3 张、敌人固定 → 来源=图鉴+<版本>
- **机制(规则级,示例一条)**:触发=每层末进商店 → 效果=花金可买牌 → 来源=实机+<版本>
- **流程(示例几步)**:第 1 步 操作=进玩法 → 后果=进入第 1 层;第 2 步 操作=战斗(自动)→ 后果=清敌或掉血 → 分支=血够继续 / 不够失败;第 3 步 操作=商店买牌 → 决策点=买 A / 买 B / 不买 → 买 A 的游戏内后果=金 -10、A 入阵容 → 来源=实机+<版本>;… 重复到 N 层
- **数据**:实体=角色 A/B/… → 关键数值=HP 100/层、买牌 10 金、困难 HP 200/层 → 来源=图鉴+<版本>
- **状态**:跨局持久化=无(纯单局)→ 局内进度追踪=第几层 + 剩余 HP → 来源=实机+<版本>
- **边界**:解锁前置=主线第 X 章通关 → 消耗=无体力、每周 3 次 → 产出=金币/经验 → 跨模式联动=经验计入角色养成 → 来源=官方+<版本>

## 怎么算记好了(完整判据)

**本判据只在你决定写玩法文档时用**;简单玩法口述够过阶段 1(SKILL.md 判据),不必落文档也不必满足本判据。

读完这份玩法文档,**能不能完整理解这玩法** —— 逐面向核对:
- **定位**:能照着玩 + 知道有哪些难度 / 模式 + 知道有无多人交互
- **机制**:懂每条规则的**触发条件 + 运作逻辑** + 知道哪些段自动哪些段手动 + 知道胜负怎么算 + 知道哪些随机哪些固定 + 知道时机模型(实时 / 回合)
- **流程**:知道每步做什么(决策层动作)+ 每个决策点的选项与**游戏内后果** + 分支条件
- **数据**:知道涉及的实体 + 关键数值(影响决策 / 策略的)
- **状态**:知道局内进度怎么追踪 + 跨局带进了什么
- **边界**:知道什么时候能玩 / 花什么 / 给什么 + 产出是否影响其它模式
- **证据**:分清哪些是事实哪些是推断

哪条做不到 = 还漏,补到做到。

## 证据纪律(见 SKILL.md,本文件不重复)

事实 vs 推断分区、多样本核实见 SKILL.md「跨阶段不变量 · 证据纪律」。**来源标注格式**(图鉴条目 / 官方 URL / 实机观察 + 版本)是玩法文档专属,见上「怎么收集」。本文件强调其中一条:**玩法文档的漂移来源是游戏版本更新**,更新时核对游戏(图鉴 / 官方)不核对代码 —— 玩法变不变由游戏决定,不由代码。
