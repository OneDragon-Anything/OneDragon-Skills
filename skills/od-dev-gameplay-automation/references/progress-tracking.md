# §1 三池结构(调研/流程/策略三类任务池)的 gameplay 实例化

## §1.1 调研池(`调研/玩法/` + `调研/技术/`)
- 玩法调研=疑问单步任务(搞懂一个机制/数值;产物→玩法建档);**用户口述=最高权威来源**;
- 技术调研=方法选型疑问(产物→设计文档/ADR);
- 怎么调研(深度检索/领域映射)→ 本 skill 与 references/gameplay-recording.md,进度侧只存疑问状态+结论指针。

## §1.2 流程池(`流程/`)
- 按**游戏流程结构**组织(阶段→画面→子态),新分支归属自明;
- 画面=独立目录(screen-onboarding 硬规则:建档 9 步非叶子);op 任务挂画面目录内(判据→write-operation);
- 轻修复(存量期:已有东西的补全/修复)不建目录,总览一行节点+**实机验证锚点必挂**;
- app 编排环节判据 → write-application。

## §1.3 策略池(`策略/`)
- 一个病灶/一条改进=一个目录,内含**诊断→设计→实现→sim 验证→实机验证**链(环节按病灶复杂度可裁剪,**验证环节不可省**);
- 总览按**策略分层**挂指针(分层各玩法自定义:如意向→评分→执行/配装→路线→释放);
- 轻调参(阈值/权重)不建目录,总览一行(改了什么+sim 数字+commit);
- 策略方法论(客观指标/A/B 纪律/策略需求清单)→ 本 skill 策略节。

## §1.4 三池互相触发生成任务(涌现登记)
实机/sim/口述发现新东西 → 判性质入池:不懂的→调研/画面或 op→流程/行为或数值→策略。**某池完成时检查是否应在别的池生成节点**(跨池触发:调研结论常生成策略工作项)。

# §2 防偏离门(gameplay 特化,loop 每轮必过)

> gameplay 特化的防偏离门;通用自检(跨阶段不变量、进行中工件≤1 的通用部分)见 od-dev-progress-tracking §8。防止自主 loop/agent 漂离主线。

- **定位五元组(硬门,必填)**:焦点必填 `做法X / 节点Y(工件) / 子项Z / 判据N / 本轮动作W`。
  - **判据 N**:画面节点填子态子判据 ①-⑤;**非画面节点填 §3 对应 skill 模版的完成判据**。
  - 假绿焦点豁免(画面级):`做法X / 画面Y / 对象类 / 动作W`。缺一 = 不合法。
- **产物落点校验(硬门,git diff 机械校验;只防最高危的「策略前置」漂移)**:画面节点的 **op 子任务**(§1.2 画面子任务②)的改动**不得触碰策略行为模块**(评分/权重/搜索/选择);该子任务产出 = 一个 op 节点,读字段→存局内状态。策略行为代码算,**局内状态对象字段定义不算**(**实例须在根索引/决策日志列出本项目具体算/不算的策略行为模块路径**)。触碰 → 属策略行为(收尾策略节点),不是画面 op,得过下面策略锁。
- **策略行为锁**(改策略行为模块先过三解锁):
  - (解锁一·半硬)**改动策略读取的每个「从画面读取的字段」,其权威源画面的对应子态子任务①-⑤ 全已过(子态级)**。**非画面读取字段(代码内部派生值)豁免,不追溯**。**策略不得依赖罕见态子态才能读到的字段**(罕见态走中性 fallback;需真值等晋升后解锁)。字段→权威源画面→子态的映射**必须记入决策日志(D-NN)供复核**(格子状态可机械查;映射靠 review;**字段登记在哪个子态由 op 实际读取的子态决定**)。
  - (解锁二·硬)做法二端到端跑通有观测回路;(解锁三·硬)客观指标已定义。
  - **权威源画面**:该信息最完整/最准的画面(完整形态),登记在**根索引的跨画面权威源映射表**(进度方法派生;每画面要读信息清单在 screen doc)。

# §3 叶子任务类型 → skill 模版映射(gameplay 专属)

> 进度方法论**不发明判据,只组织各 skill 的模版成任务树**。**通用叶子类型**(画面建档 / operation / run_op / 代码测试 / 分支覆盖 / UI坐标检测 / app编排 / 端到端 / 罕见态)见 od-dev-progress-tracking §11;下表是 **gameplay 专属**叶子类型(通用表没有的)。

| 叶子任务类型 | skill 模版 | 该 skill 提供的完成判据 |
|---|---|---|
| 子态流转表 / 要读信息清单 | od-dev-screen-onboarding(产出 screen doc) | doc 内"状态流转/要读信息"节 |
| 假绿/全集建模 | od-dev-screen-onboarding §图鉴采全 | 策略需认全的对象类全集建模 |
| 玩法建档/数据采集 | od-dev-gameplay-automation §0/1 + 游戏内图鉴 | 机制+流程+决策点;图鉴全量建模 |
| 设计(op链/配置/策略框架) | od-dev-gameplay-automation + build-craft §找兄弟/§设计 | 复用清单+op链+配置口+客观指标 |
| 策略迭代 | od-dev-gameplay-automation §7 | 客观指标+A/B到目标 |
| app 编排 | od-dev-write-application | const/run_record/config/factory/app 五步+自检 |

> 通用叶子表「画面建档(初步/完整)」已统一为单一「画面建档」(不分档,探索/实现同标准,见 od-dev-progress-tracking §11)。

# §4 事件长尾(events.md)

做法二(收件)+ 收尾(闭环)运行中持续冒出的新分支收件箱(同构 gameplay §8 探索式迭代)。分节:主收件箱 / 广义降级区(可复现待排期)/ 已知局限暂搁。
- 条目:`类型/归属画面或handler/fixture/代码测试/来源(建档已知/运行时新发现)/状态`。
- **降级流转**:条目停留超**降级阈值**未三过 → 按可否复现移入广义降级区(可复现→待排期子区;无法复现→暂搁子区)。暂搁条目停留超**最终阈值**仍未复现 → 决策日志记「已知局限」+ events 标最终态。
- **清理(正常分支)**:handler+fixture+测试**三过** → 补齐①-⑤迁入画面子态子节点 → events 删条目。
- **清理(罕见态特殊路径)**:判据表罕见子态行保持 `罕见态`(**不晋升正常子态**,走不完 ③);events 留广义降级区靠运行时撞;撞到且能完整①-⑤ → 该子态从 `罕见态` 变①-⑤全已过(晋升)+ events 删。
- **全新独立画面晋升**(非既有画面子态/overlay):先建画面节点(子态流转+①-⑤骨架)→ 走①-⑤ → events 删条目。
- **收尾退出判据**(同构 gameplay §8):连续 N 次 `run_standalone_app` 无新 event 涌入。阈值(M/N/降级/最终)按玩法单局回合数定,实例在根索引给出。
