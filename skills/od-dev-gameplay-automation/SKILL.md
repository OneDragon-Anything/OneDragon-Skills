# 新玩法自动化开发 playbook(OneDragon 框架)

把「自主开发一个新玩法的自动化」拆成**两套做法**:**探索设计**(走一遍、产出设计草案)+ **实现循环**(逐画面实测、任务树生长)。**全程守「看(analyze)→ 动(click/key/run)→ 等(sleep)→ 验」循环**;**别凭猜硬写** —— 凭猜只覆盖一种情况、漏另一种,必回归。

> 通用方法论(不绑具体玩法)。两套做法本质不同(探索 = 线性脑力走一遍 / 实现 = 逐画面循环实测),**不混作一条线性序**,各按本套标准。为什么是两套而非一条 0-9 线性序(以及 0-9 为何降为认知地图)见 [design/ADR-0006](design/decisions/0006-two-pass-skeleton-exploration-vs-implementation.md);what 见 [design/two-pass-skeleton.md](design/two-pass-skeleton.md)。

## 两套做法(执行骨架)

> 全景参考见文末「0-9 认知地图」(**非执行序**,建立认知用);**执行按下表两套做法**。

| 做法 | 做什么 | 出口判据 |
|---|---|---|
| **一·探索设计**(线性走一遍) | ① 先确认能玩(常驻/限时/能实机/未过期,最易漏)→ ② 玩法建档(机制/流程/决策点/画面清单/数据)→ ③ 画面建档(探索期,完整标准但标进行中)→ ④ 找兄弟读代码(复用/丢弃清单)→ ⑤ 流程设计(op链/配置)+ 策略设计(方向/客观指标/配置口) | 设计草案产出:主流程画面已建档(进行中)+ 已知分支画面在清单 + op链设计 + 策略方向(复杂玩法另出策略需求清单,见「策略」) |
| **→ 切换** | 设计草案产出 → 进实现。**看出口判据,不看做法一节点聚合状态** —— 它滞后到做法二中后期才 `已过`,属预期,不是"不能往下"的信号 | — |
| **二·实现循环**(逐画面,任务树活) | 每画面闭环〔①详细建档(补全探索期)→ ②写op → ③实测 → ④代码测试 → ⑤分支覆盖(含假绿/罕见态)〕;新发现画面/子态/分支 → 加任务 → 循环;**所有画面 op 写完后 app 编排**(串成可跑 app,`run_standalone_app` 前置) | `run_standalone_app` 端到端通 + 已知事件全覆盖 |
| **收尾** | 策略调优(A/B 到目标;含「打不过先精确诊断卡在哪一步」)+ 测试文档(ruff/测试仓/docs) | — |

> 进度记录(任务树状态机 + 防偏离门)按 **od-dev-progress-tracking**;两套做法的任务树实例化(分纲)见 `references/progress-tracking.md` §1。

### 做法一·探索设计(走一遍,产设计草案)

- **先确认能玩**(最易漏):玩法常驻/限时(限时可能已结束 → 只能"研究+骨架",没法实机验证);能实机打开(客户端版本/入口还在);有无反作弊/锁光标/全屏独占(影响 controller 能否操作)。
- **玩法建档 = 一切的起点**:面对全新玩法,**第一件事是搞懂玩法本身,不是急着写代码**。先搜官方+攻略/wiki 理清类型(肉鸽/自动战斗/手动/节点制)、一局流程、决策点、自动 vs 手动部分、胜负奖励;再实机跟一遍(或看视频),边走边记每画面进出条件 + "玩家在此做什么"。深度(6 面向 + 单/多文件组织)见 `references/gameplay-recording.md`。
- **画面建档(探索期)**:实机跟走本身就是画面建档的开始 —— 每碰到画面记进出 + 存 fixture + 建 screen_info area(**automation 所需信息 area,不只动作按钮,含 bot 要读的数据/反馈/策略输入**);**画面建档"做什么"单一源见 `od-dev-screen-onboarding`**。⚠️ 探索期认知有限,按**完整标准**做但**标 `进行中`**(产物标成熟度「待实现期验证」)—— 不是"做粗版",是"尽力完整但诚实承认可能不全";后续设计/策略发现缺 → 实现期补全 → 推进 `已过`。
- **找兄弟 + 读现有代码**:定复用/丢弃清单(`references/build-craft.md` §找兄弟)。注:探索期建档是"实机跟走理解画面"在前,找兄弟的复用指导主要服务实现期的完整建档补全。
- **流程设计 + 策略设计**:op 链/状态机/配置(`build-craft.md` §设计);策略设计见下「策略」。

### 做法二·实现循环(逐画面,任务树活)

**流程驱动 + 逐画面微循环**(每画面闭环稳定才进下一个,见 [design/ADR-0003](design/decisions/0003-flow-driven-per-screen-micro-loop.md)):从玩法入口出发,按游戏实际流程顺序,每画面〔①详细画面建档(补全探索期,`od-dev-screen-onboarding` 完整标准)→ ②写 op(`od-dev-write-operation`)→ ③`run_operation` 实测 → ④代码测试 → ⑤分支覆盖(遇预料外补建档+补分支,`references/runtime-iteration.md` + write-operation 预料外调研)〕→ 该画面闭环 → 进下一个。所有画面 op 写完后 **app 编排**(factory/config/GUI/节点图,`od-dev-write-application`),再 `run_standalone_app` 端到端验。

**loop 运行时须能从跨玩法偏离恢复**:bot 无人值守跑(loop / `run_standalone_app`)时 `analyze` 命中**非目标玩法**画面 → loop 的未匹配状态分派须**导航回目标玩法入口**续被打断的工作(**禁** stall / 盲重试 / 走通用 fallback 点空白 ESC 卡错玩法 / 停下等指示)。判据复用 `od-dev-screen-onboarding` 跨玩法偏离协议;loop 调度层落法见 `references/runtime-iteration.md`。**与任务进度防偏离(`references/progress-tracking.md` §2,dev 焦点纪律)不同维度,别混**。

**任务树是活的**:实现期不断发现新画面/子态/分支/事件 → 加任务节点(progress-tracking §5),循环到端到端通 + 事件全覆盖。探索期已建的建档节点,实现期**复用并推进到 `已过`**(不重建);新发现子态新建。

### 画面建档:一套完整标准,不分档

**画面建档"做什么"单一源在 `od-dev-screen-onboarding`**(analyze→视觉大模型→建档→缺口→建模→归档;UI 区域坐标 → od-dev-ui-region-detect)。**不分"初步档/完整档"** —— 每次都按完整标准做;探索期与实现期的差别只在**认知完整度**(探索期尽力完整但标 `进行中`,实现期有设计/策略认知后补全),不是两套建档标准。本 skill 只管"画面建档在两套做法里的位置"(探索做、实现补全、何时触发),不重复建档方法论。

### 策略:设计在探索、调优在收尾

- **策略设计(做法一⑤)**:用**客观指标**衡量(round/HP/gold/羁绊激活层数/胜负),别凭感觉;**A/B 对比**比直觉可靠,优化找**甜点**不是极端化;策略**给配置口**(优先角色/阵营偏好/激进度)别写死。
- **复杂/策略重玩法:策略需求清单(checklist)** —— 策略要观测层读 X、要决策点设计 Y、要数据建模 Z,自动化才能把策略接上(策略和各层是需求关系)。复杂玩法的策略设计**额外产出策略需求清单**,把策略对自动化的需求列全:① **观测层**要读哪些字段(+ 权威源);② 有哪些**决策点**(+ 各点设计 / 实现状态);③ 要建模哪些**数据**(+ 完整度);④ 留哪些**配置口**(+ 已接否);⑤ 每项分清**纯逻辑能做(只是没接线)vs 真卡游戏数据(做不了)**,别笼统"卡验证"。清单**当 checklist**:实现期(做法二)照它补(该 read 的 read、该设计的决策设计、该建的数据建)+ 调优期(收尾)照它调权重,不漏。**判据**:简单玩法(策略轻 / 交织浅)原来三条(客观指标 + A/B + 配置口)够,**不强制**出清单;复杂 / 策略重玩法(策略与多层深度交织)才出 —— 别一刀切。
- **策略调优(收尾)**:观测回路通后(`run_standalone_app` 能采到每回合掉血/胜负/金币),A/B 迭代到目标。**"打不过"先精确诊断卡在哪一步**(警告?锁阵?出战禁用?被某机制阻塞?),别笼统归因"策略差" —— 往往一个具体小动作(升等级/卖弱角色)就破墙。

## 跨阶段不变量(每阶段都守)

**证据纪律(下结论别凭单点)**:
1. 验证 OCR 读取器/运行时行为**跨多样本**,别凭一张图 —— 跑实机后看 telemetry/日志的统计分布(如 `grep -o '"<field>": [0-9]*' file | sort | uniq -c`);`analyze_screen` 全屏 OCR 与区域 OCR(`get_ocr_result_list(rect=...)`)可能行为不一致,要分开验(全屏命中 = 该处有字,不等于区域 OCR 读得到);异常值(garbage)是误读信号,别忽略。
2. 逻辑推断也要**交叉验证**,别拿未证实假设当论据("某读数不可能是 X,所以读到 X 必是 bug" —— 可能有你没考虑的状态/机制理解错);结论立在硬证据(诊断 + 代码流)上。
3. 写 docstring/结论/文章前分清"多样本观察到"还是"单次推断";单次的标"待核实",别写成既成事实。

**知识维护(边干边补)**:文档没写、或与实际矛盾、而你在干活时又需要它 = 知识缺口,补上 —— 能查官方文档/工具说明的**先查,别凭猜试错**(API/模型用法/坐标系/grounding 格式,查文档比反复试错快得多);能确定答案的提议补 docs(只补会重复用到的);确定不了的问用户。**游戏数据/描述/原生数值优先官网 + 游戏内(图鉴/词条)**(权威源);只有"攻略/玩法技巧"这类主观总结才信第三方网站。**遇工具/API/模型行为反常,先查文档** —— 这条比任何具体技巧都重要。

**调试纪律**:bot 卡死/失败时**先读日志再动手**,别凭猜改或盲点坐标 —— 日志常直接暴露根因(OCR 没读到锚点/节点循环/命中错屏)。op 级调试 / 信息密度(多 log 多截图)/ 预料外画面调研 / 运行时不确定性 / 重复建op 的完整方法论见 `od-dev-write-operation`(探索式主线 + `references/runtime-craft.md`,op 级运行时技术 single source)。

**区分两种"卡住"(路由不同,别混)**:
- **op 执行失败 / 报错**(技术故障:OCR 没读到 / 节点循环 / 命中错屏)→ 先读日志,见 `od-dev-write-operation` 调试纪律。
- **卡在状态不清 / 未建档画面,自己不知怎么出去 / 推进**(认知卡住:覆盖层 / 弹窗 / 不知怎么进来的子屏)→ 别干卡或盲点,触发 **`od-dev-screen-onboarding` 的「卡住画面协议」**(回溯怎么进 → 系统找出口 → 穷举交互观察 + 交互前后状态对比,禁干卡)。这是画面认知缺口,读日志解决不了,得建档补。

**框架级踩坑**(click 与鼠标移动无间隔被判拖拽、MCP 异步、ONNX 异步、配置生效、录屏、GBK 日志等)见 `od-dev-write-operation/references/framework-pitfalls.md`(single source)—— 遇 op 点不中/行为怪先查那里。

## 协作 skill(深度细则 defer,不重复)
- **写 / 改 / 调试单个 Operation**(节点图 / round 结果 / `round_by_*`)+ **探索式开发主线 + op 级运行时技术(信息密度 / 调试 / 预料外调研 / 重复建op)+ 框架踩坑** → `od-dev-write-operation`(op 粒度地基,本 skill 引用其 `runtime-craft.md` / `framework-pitfalls.md`)
- **循环驱动玩法(loop 每轮重新发现状态)的 op 结构选型**(flat loop vs node-per-op / committed-but-verifying / 节点作用域预算防卡死)→ `od-dev-write-operation`(做法二实现结构选型 + 迭代时查,引用其 `references/loop-driven-op-structure.md`)
- 画面建档 / screen_info area 维护 / 图标按钮模板建模 → `od-dev-screen-onboarding`
- UI 区域坐标检测(槽位网格/图标按钮阵列/卡牌阵列)→ od-dev-ui-region-detect
- bug 已知故障机制、决定怎么修(修哪里/根因多深/临时 vs 永久)→ deciding-a-fix skill(项目内)
