# 两套做法骨架(探索设计 / 实现循环)

> 设计存档(给维护者 / reviewer,不进智能体执行上下文)。why 见 [ADR-0006](decisions/0006-two-pass-skeleton-exploration-vs-implementation.md)。本文件讲 **what**:骨架长什么样、各 skill 分工、怎么落地。
> 经框架负责人 4 轮修正收敛(2026-08-09):① 探索与实现是两套本质不同的做法,不统一成一套;② 半成品归产物不归进度;③ 画面建档"做什么"单一源在画面建档 skill;④ 画面建档不分初步/完整档,每次按完整标准做,探索期标未完成。

## 背景:为什么从 0-9 重组

当前 SKILL.md 的 playbook 是 **0-9 按活动类型切的线性阶段**(玩法建档 / 找兄弟 / 画面建档 / 设计 / 实现 / 验证 / 策略 / 迭代 / 测试)。实战暴露三个问题:

1. **同一活动承载两套标准,位置含糊**:画面建档列为阶段 3(设计前),但它**贯穿探索和实现** —— 探索期是"认知有限下的尽力建档",实现期是"有设计/策略认知后的补全"。塞进阶段 3 一个位置,标准打架(到底要初步还是完整?)。策略列为阶段 7(独立),但策略是"设计期设计 + 收尾期调优",不是独立阶段。
2. **实操骨架被埋**:progress-tracking §10 分纲已隐含两套做法(阶段 1-3=探索 / 4-5=实现),但标成"0-9 映射反转"+ 降在 reference 里。实际项目(cw_dev)照搬显眼的 0-9、忽略 §10 → 焦点漂到策略(阶段 7)、画面建档卡在"要完整过才能设计"。
3. **探索和实现本质不同**:探索是**线性脑力**(走一遍、产出理解 + 设计草案、半成品);实现是**逐画面循环**(实测驱动、任务树生长)。塞进一个线性序列,活动阶段承载冲突标准 → 内容分歧。

## 两套做法骨架

### 做法一·探索设计(线性走一遍,产出设计草案)

- **先确认能玩**:常驻 / 限时 / 能实机 / 未过期(原阶段 0,最易漏)
- **玩法建档**:机制 / 流程 / 决策点 / 画面清单 + 数据采集(角色 / 装备 / 数值 / 词缀全量建模,独立可追踪子节点;`gameplay-recording.md`)
- **画面建档(探索期)**:实机跟走,主流程画面按**完整标准**建档(`od-dev-screen-onboarding`)。⚠️ 探索期认知有限,产物(画面doc)标成熟度「待实现期验证」,任务标 `进行中`(详见下「探索期建档标未完成」)。**不是"做粗版"**,是"尽力完整但诚实承认可能不全"。
- **找兄弟 + 读现有代码**:复用 / 丢弃清单(`build-craft.md` §找兄弟)。注:探索期建档是「实机跟走理解画面」在前,找兄弟的复用指导主要服务做法二的完整建档补全,故列画面建档后
- **流程设计**:op 链 / 状态机 / 配置(`build-craft.md` §设计)
- **策略设计**:方向 / 客观指标 / 配置口
- **出口判据**:主流程画面(入口 → 核心循环 → 结算)已建档(标 `进行中`)+ 已知分支画面在清单(标待实现期补)+ op 链设计 + 策略方向 —— 即「设计草案产出」
- **产出 = 设计草案**(整体未完成,待实现期验证 / 补全)

### 切换点:设计草案产出 → 进实现

### 做法二·实现循环(逐画面,任务树活)

[ADR-0003 流程驱动 + 逐画面微循环] 每画面闭环(①建档 → ②op → ③实测 → ④代码测试 → ⑤分支覆盖,含假绿 / 罕见态,详见 progress-tracking §1.2 不变):
- **详细画面建档**:回头补全探索期的建档(这次有设计 / 策略认知,知道要读哪些字段),`od-dev-screen-onboarding` 完整标准
- **写 op**(`od-dev-write-operation`)
- **run_op 实测**
- **发现问题**(新画面 / 子态 / 分支)→ 加任务(progress-tracking §5)→ 循环
- 该画面闭环 → 进下一个

所有画面 op 写完后:
- **app 编排**:把 op 串成可跑的 app(factory / config / 节点图,`od-dev-write-application`)—— `run_standalone_app` 的前置(必须在出口验证前)

**出口判据**:`run_standalone_app` 端到端通 + 已知事件全覆盖(progress-tracking §11/12)

### 收尾

- **策略调优**:A/B 迭代(观测回路通后,客观指标到目标);含「打不过先精确诊断卡在哪一步」(现 SKILL.md §阶段 7 的运行时诊断,归这里,非做法一的策略设计)
- **测试 + 文档**:ruff + 测试仓 + docs

## 0-9 降为认知地图

0-9 **不再是执行骨架**,而是**认知地图** —— 讲"玩法自动化开发涉及哪些事"(科普 / 全景),agent 建立全景认知用。**执行按两套做法**(SKILL.md 两套做法表 + progress-tracking §1 实操骨架)。两者关系:先读 0-9 认知地图建立全景 → 按两套做法执行。**不再用"映射反转"硬凑"不矛盾"**。

**SKILL.md 结构(治本:防 agent 又把 0-9 当执行序)**:重写后 SKILL.md = **两套做法表放最前作执行骨架** + 跨阶段不变量;**0-9 不再以"总流程阶段表"形态出现在顶部**,改为靠后的「全景参考(非执行序)」块 + 显式标注「认知地图,执行按上面的两套做法」。根因是 cw_dev 照搬顶部显眼的 0-9 表漂移 —— 若重写后顶部仍是 0-9 表,等于没改。

## 探索期建档标未完成 + 半成品归产物

- **探索期画面建档**:按完整标准做,但任务标**`进行中`(待实现期补全 → `已过`)** —— 不标 `已过`(完整度未验证),也**不用 `部分过`**(`部分过` 是父节点聚合态,叶子建档任务不能用,见 progress-tracking §3)。产物(画面doc)标成熟度「探索期建档,待实现期验证完整度」。后续设计 / 策略发现缺 → 实现期补全 → 推进 `已过`;若探索期已误标 `已过` 后才发现缺 → 走 progress-tracking §6 回退。用现有状态机,**不新增状态词**。
- **半成品归产物**:设计草案 / 代码的成熟度(草案 / `# 未验证`)是**产物属性**,记在产物里,**不进进度状态机**。状态机只管完成度。
- **做法一 / 做法二建档节点的复用关系**(防重复建 / 防误判回退):做法一已建的**画面 / 子态建档节点**,做法二**复用并推进到 `已过`**(不重建);做法二**新发现的子态**(探索期未遇)→ 按规范**新建**子态级建档节点。画面节点里 ① 建档是**前置依赖(引用指针)**而非聚合子任务 —— 画面节点聚合只算 ②op / ③实测 / ④测试 / ⑤分支覆盖,① 是它们的前置。由此做法一的建档子任务要等做法二补全才 `已过` → 做法一(父)节点滞后到做法二中后期才聚合 `已过`,属正常(非回退、非漏做)。⚠️ **做法一是否进做法二看「出口判据(设计草案产出)」,不看做法一节点聚合状态** —— 它滞后到做法二中后期才 `已过` 属预期,不是"不能往下"的信号。

## 分纲(原 §10)重组后形态(`references/progress-tracking.md`)

§10 从"10.1-10.5 五阶段(playbook 映射)"重组为**两套做法子树**(对齐 SKILL.md 两套做法表):

- **做法一·探索设计子树**:玩法建档 + 画面建档(探索期,标 `进行中`) + 找兄弟读代码 + 流程设计 + 策略设计。出口 = 设计草案。
- **做法二·实现循环子树**(递归核心):逐画面〔详细建档(推进做法一已建节点 → `已过`;新发现子态新建)+ 写 op + 实测 + 代码测试 + 分支覆盖 + 发现问题 → 加任务〕+ app 编排。出口 = `run_standalone_app` 端到端通 + 事件全覆盖。
- **收尾子树**:策略调优(A/B)+ 测试文档(app 编排归做法二,出口验证前)。

**目录结构**(示例,项目可自选命名):从 `1_玩法建档 / 2_初步探索 / 3_设计 / 4_逐画面 / 5_端到端` → 按两套做法维度 `探索设计 / 实现循环 / 收尾`(或保留编号重映射)。**删原 §10.2「初步建档」**(探索期建档进做法一,完整标准标 `进行中`);原 §10.4「逐画面」并入做法二(建档从"首次完整"改"补全做法一进行中节点")。

**编号**:原 10.N 的"playbook 阶段 X"标注全删(解除映射反转);阶段内编号按两套做法重排。
