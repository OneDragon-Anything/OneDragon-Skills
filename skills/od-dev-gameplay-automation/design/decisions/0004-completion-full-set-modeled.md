# 0004. 完成判据补「认全的对象要全部建模」+ 防静默 fallback(假绿)

- **Status**: accepted
- **Date**: 2026-08-06

## Context

实现阶段逐画面微循环的**完成判据**(`references/build-craft.md` §实现 point 3 + [0003](0003-flow-driven-per-screen-micro-loop.md))原只校验 **mechanics**:area 建了 + op 读取 + `run_operation` 实测 + 代码测试 + 主要分支覆盖。不校验该屏**要认全的对象**(识别 / 决策依赖的一类对象全集,如全部 boss / 敌人词缀 / 装备 / 角色 / 卡片 / 选项)在代码里是否**全部建模**。

**假绿路径**:某屏要认全某类对象,mechanics 全过,但底层注册表 / model 只建了这类对象的一部分 → bot 认不出没建的那些 → **静默走中性 fallback**(返中性值 / 走默认分支),不报错、不 log,要等实机跑到那个没建的对象才暴露。现有判据把这个状态当"已完成"。(实例:某玩法一个注册表只收了该类的 36/83,47 个静默走中性 —— 仅作说明,不入 skill 正文。)

通用的:任何 SR/ZZZ 玩法,只要画面要认全某类对象(少一个都不行)都有此风险,非某玩法特异、非模型/环境特异。

## Decision

**本 ADR 针对「策略需要按全集最优」的情况。** 若策略不需要最优,另一条合法路是**简化策略**(无脑选固定位置)绕开全集识别 —— 不采全、不踩假绿(见 `build-craft.md` §实现 ⚠️「两条路」)。下面针对"需要最优"补两层:

1. **完成判据加维度**:若该屏要认全某类对象(识别 / 决策依赖其全集),完成 = **这些对象在代码(注册表 / model 类)全部建模**,不只 mechanics 全过。(`build-craft.md` §实现 point 3 + ⚠️ 假绿 note。)
2. **防静默 fallback**:注册表 / 评分查不到对象(命中已建之外)时至少 `log warn`,把"没建全"从静默中性变成可见信号 —— 即使没建全,也能在 log 里及早发现,不用等实机撞。

## Decision Drivers

- **mechanics 全过 ≠ 真完成**:该建的对象没建全时 bot 静默降级,现有判据发现不了 → 假绿比"没做完"更危险(看着 done 实则埋雷)。
- **静默 fallback 是放大器**:中性值 / 默认分支不报错,把"数据缺口"藏成"运行正常",延后暴露到实机(贵)。
- **与既有「采全」的关系**:`od-dev-screen-onboarding` §5 已有「采全」管**模板 + 数据采集穷尽**(滚动 / 翻页 / 全角色全装备);本条是**认全的对象要全部建模**接进完成判据 + 防静默 —— 采全是**采集侧**,本是**完成判定 + 运行时防御侧**,三者互补。

## Considered Options

### A. 完成判据补「认全的对象要全部建模」+ 防静默 fallback(本决策)
- ✅ 堵假绿:判据要求建全 + 运行时 log warn 双保险。
- ✅ 与采全分工清晰(采集 vs 完成判定 + 防御)。

### B. 不补,判"采全(screen-onboarding §5)已覆盖"
- 否决:§5 采全是**采集侧**(建库时穷尽),不是**完成判定**(实现闭环时校验)也不是**运行时防御**(没建全时怎么办)。三者不同;假绿正是因为判据没这维 + 运行时静默。

### C. 只补完成判据,不加防静默 fallback
- 否决:判据是"写时校验",但对象可能后补 / 漏建;运行时 log warn 是兜底防御。两者互补(写时尽量全 + 运行时漏了可见)。只补判据 = 漏了仍静默。

## Consequences

- **正向**:要认全某类对象的屏不再"mechanics 全过就当完成";没建全时 log warn 及早暴露,不用等实机。
- **代价**:实现时多一步"确认该类对象建全"的校验;运行时多 log(已建之外命中)。
- **推翻它会碎什么**:退回 B → 假绿继续;退回 C → 判据补了但运行时漏建仍静默。
