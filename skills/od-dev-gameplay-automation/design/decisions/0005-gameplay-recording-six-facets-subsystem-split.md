# 0005. 玩法建档深度细则:把玩法当交互系统记 6 面向 + 单文件起步按子系统拆

- **Status**: accepted
- **Date**: 2026-08-08

## Context

阶段 1「玩法建档」是"一切的起点" —— 先搞懂玩法本身才能自动化。但 SKILL.md 阶段 1 正文只有一段(理清类型/流程/决策点/自动手动/胜负 → 输出机制口述 + 画面清单),**没说怎么把理解固化成完整可复用文档**。实战痛点:玩法文档普遍"太简单"(写得太抽象、缺细节、缺关键数值、缺跨局状态);复杂玩法(子系统多 / 实体多,如大型肉鸽)单文件装不下。缺一套"怎么完整记录一个玩法"的方法论。

阶段 3「画面建档」已有 `references/screen-identification.md` 深度细则作参照;阶段 1 缺对应的深度细则。

## Decision Drivers

- **玩法是客观事实**:与代码无关,源是游戏本身(图鉴/官方/实机),不是代码 —— 记录方法要钉死这点(防拿代码当源、防玩法与代码耦合漂移)。
- **完整不漏**:用户痛点是"太简单" → 要有面向清单保证该记的都记到(机制到触发条件、数据到关键数值、流程到选择+后果)。
- **复杂玩法可扩展**:简单玩法单文件够,复杂玩法(子系统多)要多文件组织 —— 方法论要弹性适配。
- **渐进式披露**(见 [ADR-0001](0001-staged-playbook-progressive-disclosure.md)):阶段 1 深度进 references/,不堆 SKILL.md 正文。

## Considered Options

1. **玩法记录进 references/(阶段 1 深度细则)** vs 写进 SKILL.md 正文 vs 独立成 od-dev-gameplay-onboarding skill:
   - 写进 SKILL.md:否 —— always-on 该留最小集,深度细则按需读(ADR-0001)。
   - 独立 skill:否(当下)—— 玩法记录是阶段 1 的一个子部分,不是独立工作流(不像 screen-onboarding 是独立 5 步流);且和阶段 1 正文(画面清单产出)紧耦合。若将来玩法建档方法论膨胀到自成体系(多 reference / 多 ADR),再拆。
   - 进 references(选中)—— 与 screen-identification.md(阶段 3 深度)对称,符合现有模式。

2. **6 面向(交互系统切分)** vs 更少(4 面向)vs 更多(8 面向)vs 无框架按需记:
   - 无框架:否 —— 没有清单保证 → 容易漏(正是"太简单"的根)。
   - 4 面向(如合并定位/边界/状态):否 —— 定位/边界/状态是独立问题(能否玩/怎么进;花什么给什么;跨局带什么),合并会模糊。
   - 8 面向(如随机性/影响独立成面):否 —— 随机性归机制、影响归流程更自然(它们是机制/流程的内容,不是独立维度)。
   - 6 面向(选中)—— 对应"交互系统"的经典切分(目标 / 规则 / 动态 / 组件 / 状态 / 边界),每个回答一个不同问题,覆盖"这是什么 / 怎么运作 / 怎么走 / 有什么 / 到哪了 / 何时玩"。

3. **文件组织:单文件起步 → 膨胀才按子系统拆** vs 固定按面向拆 vs 固定按复杂度等级拆:
   - 按面向拆(机制.md / 数据.md / …):否 —— 跨面向关联难查(查"某角色的机制+数据"要跨文件);且简单玩法被强拆。
   - 按复杂度等级硬分(简单=1 文件 / 复杂=多文件):否 —— 边界武断(多少算复杂?),弹性差。
   - 单文件起步 → 膨胀才按子系统拆(选中)—— 判据驱动(难查/独立更新/独立子系统才拆),按玩法自身结构(子系统)组织,简单玩法不强制拆。

## Decision

`references/gameplay-recording.md` 写成阶段 1 深度细则:

- **核心原则**:玩法是客观事实,源是游戏(不是代码);玩家视角;事实 vs 推断分区;版本更新核对游戏不核对代码。
- **6 面向内容清单**:定位 / 机制(含自动 vs 手动、胜负、随机性)/ 流程(含决策点、游戏内后果、分支)/ 数据(实体 + 关键数值)/ 状态(重点跨局持久化)/ 边界(解锁/消耗/产出)。面向是内容清单,不是文件结构。每个面向默认要写;确实无内容才空,空写"查证无此面向"。
- **怎么收集**:搜官方/图鉴理骨架 → 实机跟走每画面记玩家做什么+后果+进出条件 → 查不到标【待验证】→ 标来源。
- **记到什么程度**:用结构模板(填空骨架)替代抽象叙事,治"太简单"。
- **怎么组织文件**:单文件起步,膨胀(难查/独立更新/独立子系统)才按玩法自然结构(子系统)拆;入口文件永远一个;全量数据量大时独立;简单玩法别为拆而拆。
- **完整判据**:读完能完整理解玩法(覆盖全部 6 面向)。

接入:SKILL.md 阶段表阶段 1"深度细则"列指向 `references/gameplay-recording.md`;判据对齐(文档开头说明 SKILL.md 判据是最小 bar"能口述"、本文件是完整 bar"记成文档",两者不冲突)。

## Consequences

- **正向**:玩法有完整记录方法(治"太简单");复杂玩法可多文件扩展(用户明确诉求);结构模板让"具体到能验证"可操作;接入 SKILL.md 非(孤儿);与 screen-identification.md 对称。
- **代价**:6 面向对简单玩法略重(用"可空判据 + 经查无"缓解);结构模板多(但保证可执行)。
- **边界**:玩法记录(阶段 1,玩家视角事实)≠ 画面建档(阶段 3,画面怎么识别)≠ 策略设计(阶段 7)—— 三者层次不同,流程的游戏内后果是策略的**输入**但不是策略本身。
- **推翻它会碎什么**:删"6 面向"→ 没有完整性保证 → 回到"太简单";删"客观事实/源是游戏"→ 玩法与代码耦合漂移;删"单文件起步按子系统拆"→ 简单玩法被强拆或复杂玩法挤一文件。
