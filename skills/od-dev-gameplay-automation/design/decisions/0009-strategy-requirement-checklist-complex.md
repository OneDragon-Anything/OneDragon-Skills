# 0009. 复杂玩法策略设计出「策略需求清单」(checklist),防实现/调优漏接口

- **Status**: accepted
- **Date**: 2026-08-11

## Context

`od-dev-gameplay-automation` SKILL.md「策略设计」原只讲三件事:客观指标衡量 + A/B 对比 + 给配置口。对**简单玩法**(策略轻)够;对**复杂/策略重玩法**(策略与观测/决策/数据/配置深度交织,如 auto-battler、带 build 决策的肉鸽),「方向」太虚 —— 策略设计散在多文档 + 代码,实现期/调优期途中反复发现"策略要 X 但观测层没 read / 某决策点没设计",**漏**。

触发实例(SR 货币战争):
- 策略要按 **streak(连胜)方向**决策 → 观测层**从没读 streak** → 漏。
- 策略要按 **difficulty** 调 → difficulty **从没读** → 漏。
- **optionality 函数写好了**(纯逻辑能跑)但**没接进 evaluate**(没接线)→ 却被笼统标"卡 P0 验证",分不清"能做没接"还是"卡数据做不了"。

根因:复杂玩法里,策略与自动化各层(观测 / 决策 / 数据 / 配置)是**需求关系**(接口)—— 策略要观测层读 X、要决策点设计 Y、要数据建模 Z,自动化才能把策略接上。skill 只说策略出「方向」,没要求把这层需求显式列出来 → 实现期按画面/op 推进时,不知道策略要哪些观测/决策 → 该 read 的没 read、该设计的决策没设计 → 策略接不上(漏)。

这是**方法论级 gap**(对任何策略重玩法成立,ZZZ 肉鸽共鸣/邦布/驱动盘选择同理),非某玩法专属。

## Decision Drivers

- **防漏**:复杂玩法策略和多层交织,不显式列需求 → 实现/调优漏接口(实例实证)。
- **分清"接线 vs 卡数据"**:复杂玩法常把"能做没接"笼统标"卡验证" → 清单第⑤项强制分清,避免假阻塞。
- **不过度**:简单玩法策略轻,三件事够;不一刀切强制所有玩法产清单(overhead)。

## Considered Options

1. **保持现状(只出方向)**:复杂玩法漏接口(实例实证)(否)。
2. **所有玩法强制产清单**:简单玩法 overhead(否)。
3. **复杂/策略重玩法才出策略需求清单当 checklist(选中)**:显式列需求防漏 + 分清接线vs卡数据;判据区分简单/复杂,简单不强制。

## Decision

选 3。SKILL.md「策略」节「策略设计」项后加一条:**复杂/策略重玩法出策略需求清单**,枚举策略对各层的需求:① 观测层要读哪些字段(+ 权威源);② 决策点(+ 设计/实现状态);③ 数据建模(+ 完整度);④ 配置口(+ 已接否);⑤ 每项纯逻辑能做(没接线)vs 真卡游戏数据(做不了),别笼统"卡验证"。清单**当 checklist**:实现期(做法二)补全 + 调优期(收尾)调权重照它不漏。**判据**:简单玩法不强制;复杂/策略重玩法才需。做法一出口判据「策略方向」补「复杂玩法另出策略需求清单」。

## Consequences

- **正向**:复杂玩法策略需求显式化 → 实现/调优照 checklist 不漏接口;"接线 vs 卡数据"分清(防假阻塞)。
- **负向**:复杂玩法策略设计多一步(产清单);判据"复杂/策略重"需写者判断(策略是否与多层深度交织)。
- **边界**:清单是策略设计产出 → 进 app 设计文档 `strategy/`(落点见 `od-dev-write-application` app-design-doc);同时当 checklist(实现/调优照它)。不作进度节点(清单是设计,进度是实现,各自)。本 skill 讲策略方法论(含清单);write-application 的 strategy/ 只占位指针到本 skill。
