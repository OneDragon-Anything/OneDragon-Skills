# 0006. 骨架重组:按"两套做法"(探索设计 / 实现循环)组织,非 0-9 按活动类型切;0-9 降认知地图

- **Status**: proposed
- **Date**: 2026-08-09

## Context

SKILL.md 的 playbook 是 **0-9 按活动类型切的线性阶段**(玩法建档 / 找兄弟 / 画面建档 / 设计 / 实现 / 验证 / 策略 / 迭代 / 测试)。实战(框架负责人推进货币战争自动化,2026-08)暴露:

- **同一活动承载两套标准,位置含糊**:画面建档(阶段 3)贯穿探索与实现,塞进一个位置标准打架(要初步还是完整?);策略(阶段 7)本该是"设计期设计 + 收尾期调优",被当独立阶段 → 实际项目焦点漂过去、地基没打就调策略。
- **实操骨架被埋**:progress-tracking §10 分纲已隐含两套做法(阶段 1-3 探索 / 4-5 实现),但标成"0-9 映射反转" + 降在 reference。实际项目(cw_dev)照搬显眼的 0-9、忽略 §10 → 焦点漂策略、画面建档卡住。
- **探索与实现本质不同**:探索 = 线性脑力(走一遍、产出理解 + 设计草案、半成品);实现 = 逐画面循环(实测驱动、任务树生长)。塞进一个线性序列,活动阶段承载冲突标准 → 内容分歧。

框架负责人判定:这是**结构性根因**,不是个案。0-9 的"按活动类型切阶段"本身不适合"实现期循环驱动、半成品产出"的真实玩法开发。

## Decision Drivers

- **反映真实工作流**:探索 / 实现是两套本质不同的做法,骨架要分开表达,不假装是一条线性序列。
- **消除活动阶段标准冲突**:画面建档 / 策略不再被迫挤进一个阶段承载两套标准。
- **§10 成权威,治"照搬 0-9"**:实操骨架不再被埋成"映射反转",和认知骨架地位分清。
- **治焦点漂移**:cw_dev 漂到策略、画面建档卡住的根因,从骨架层面消除。

## Considered Options

1. **维持 0-9(现状)**:活动阶段含糊不变;§10 继续被埋;焦点漂移不治本。
2. **统一成一套"两相"骨架**(把探索 + 实现合成一个连续流程的两个相):**否决** —— 两套做法的标准 / 产物 / 循环方式本质不同,硬塞进一套统一骨架,骨架内部每个阶段要同时服务两套标准 → 正是现在 0-9 的病(内容分歧)。框架负责人明确:探索和实现是两套做法,统一会出现分歧。
3. **按"两套做法"组织 + 0-9 降认知地图**(选中):每套做法内部自然含建档 / 设计 / 写 op 等活动,各按本套做法的标准;0-9 退居科普(讲涉及哪些事);§10 解除映射反转成权威实操骨架。

## Decision

选 **3**。骨架按两套做法组织:

- **做法一·探索设计**(线性走一遍):玩法建档 → 画面建档(按完整标准,探索期标未完成)→ 流程设计 + 策略设计。产出 = 设计草案。出口 = 完整一局流程口述 + 画面清单 + op 链设计 + 策略方向。
- **切换点**:设计草案产出 → 进实现。
- **做法二·实现循环**(逐画面,任务树活):每画面〔详细建档 → 写 op → 实测 → 发现问题 → 加任务 → 下一个〕。= [ADR-0003](0003-flow-driven-per-screen-micro-loop.md) 流程驱动 + 逐画面微循环升格为"实现做法"。出口 = run_standalone_app 端到端通 + 事件全覆盖。
- **收尾**:策略调优(A/B)+ 测试文档。
- **0-9 = 认知地图**(讲涉及哪些事,建立全景),非执行骨架。执行按两套做法 + progress-tracking §1。
- **画面建档单一源** screen-onboarding(一套完整标准,不分初步 / 完整档;探索期按完整标准做但标未完成)。落实 [ADR-0002](0002-lifecycle-scope-defer-to-siblings.md)。
- **探索期建档标 `进行中`**(待实现期补全 → `已过`)**,不用 `部分过`**(那是父节点聚合态,叶子建档任务不能用,见 progress-tracking §3),不新增状态词;半成品(草案 / 未验证)归产物不进状态机。

## Consequences

- **正向**:骨架反映真实工作流;画面建档 / 策略位置不再含糊(各归各的做法);§10 成权威治"照搬 0-9";从结构上治焦点漂移。
- **负向**:0-9 从执行骨架变认知地图,需讲清"认知地图 vs 执行骨架"关系(别让 agent 又把 0-9 当执行序);两套做法的切换点(设计草案 → 实现)要写明判据,别模糊。
- **边界**:op 级技术不本 ADR 管(write-operation);玩法建档深度不本 ADR 管(gameplay-recording,ADR-0005);本 ADR 只管**骨架形态 + 0-9 定位 + 画面建档单一源归属**。
- **follow-up**:GREEN 验证 —— 用两套做法骨架从零开发一个新玩法时,是否自然按"探索走一遍 → 实现逐画面循环"推进,而非照搬 0-9 线性序。
