# 0013. 指令写意图,不写实现(规范 2 新增条)

- **Status**: accepted
- **Date**: 2026-08-27

## Context

用户与迭代方共创会话中,`od-dev-agent-autonomous-mode` checklist 第 2 步第三源的措辞经四轮纠偏演化:「③`git status` 核工作树 vs 记录」→(「工作树」与 git worktree 子命令撞名)→「未提交改动核对(`git status`)」→(大迭代已完成部分沉淀在提交里,只看未提交不够)→「`git log` + `git status`」→(为什么一定要说 git)→ 终版「查看已有改动(已提交的+未提交的),与记录对照」。

四轮中迭代方三次把命令/术语回填进指令(含妥协形态「大白话(命令)」),显示存在「具体=可执行」的强默认——判据应是删后能否照做,不是括号里有没有例子。

## Decision Drivers

- **失败真实且顽固**:同一处改动连续四轮纠偏仍回填,软提醒防不住,需要显式判据。
- **已有判据框架可复用**:规范 3「接口名两问」(删了它智能体还能照做吗)天然推广到一切实现细节,不发明新判据。
- **通用性**:任何 skill 的指令都可能嵌命令/工具名,不绑单场景。

## Considered Options

1. **不立规,归 §1.1 right altitude**(否:§1.1 管流程粒度[太脆=硬编码流程],不管「意图 vs 实现」这个轴)。
2. **扩规范 3 接口名两问的适用面**(部分采纳:判据复用该框架;但规范 3 管「名」的引用,本条管「怎么做」的实现细节,落位规范 2 指令式更近执行点)。
3. **规范 2 新增条 + writing-craft §1.12**(选)。

## Decision

选 3。规范 2 新增 bullet:指令写意图+判据,不写实现。判据=删掉该细节智能体还能照做吗(能照做=实现示例,删;照做不了=指令本体,留);术语再过「换大白话信息丢不丢」第二问;具体性放在做什么+过线判据,不是用什么做。细则(判据展开/三理由/强默认警惕「大白话(命令)」妥协形态)进 writing-craft §1.12。

## Consequences

- **正向**:通用 skill 不绑工具环境;指令更短;消除工具术语歧义诱因。
- **负向**:「指令本体 vs 实现示例」需要判断(§1.12 给判据与两侧例:环境常识类删,项目约定类留)。
- **GREEN 自验**:规则能正确分辨两侧——刚改的「查看已有改动」过(纯意图);项目 skill 里的验证层命令(某层=哪个测试集,删了 agent 不知道跑什么)也过(项目约定,指令本体)。
