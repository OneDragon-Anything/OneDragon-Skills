# 编写项目 skill

本 skill 指引编写 / 修改本生态的 skill(给 AI 编码 agent 消费的指令包)。本生态 = **OneDragon(一条龙)系列游戏自动化项目**,共用 `one_dragon` 公共包;本 skill 属其公共 skill 仓库,下文「本仓」即指该仓库。skill 的命名 / 放哪 / 挂载方式归所在仓库约定(见该仓库 AGENTS.md);本 skill 管**怎么把一个 skill 写好**。

## 1. 先对齐:这个 skill 用来做什么(动笔前必做)

拿到需求别直接开工,先和用户确认:

- **有现成工作流先提取**:当前对话已含要捕获的工作流(用户说「把这个变成 skill」)→ 先从对话历史提取:用了什么工具、步骤顺序、用户做过的纠正、输入输出格式;缺口列出来让用户补。
- **四问**(意图捕获):
  1. 这个 skill 要让 agent 能**做什么**?
  2. **什么时候触发**?(用户会说什么话、什么场景下用)
  3. 期望的**产出**是什么形态?
  4. **要不要测试**?(产出可客观验证的建议测;主观产出的通常不用——给建议,用户定)
- **该不该做成 skill**(不够格不做):技术非显然、跨项目复用、别人也受益才建。**不建**:一次性方案;他处已有标准文档;项目专属约定(→ 入口文件 AGENTS.md / CLAUDE.md 类,不进 skill);机械可校验的约束(→ 自动化,文档留给判断类)。
- **带着调研来问**:提问前先自己查(兄弟 skill、框架文档、类似实现),减少用户答题负担。
- **边界与成功标准问清、用户确认后才动笔**;随后按 §7 流程走。

## 2. 一个 skill 长什么样(产出物形态)

```
<skill-name>/
├── SKILL.md          # 必需:agent 指令,触发时全文加载
├── references/       # 按需:细则文档,agent 按需读
├── scripts/          # 按需:可执行工具,agent 跑它、不读它
├── assets/           # 按需:产出用静态资源(模板/图标/字体),agent 读/复制,不执行
├── evals/            # 按需:测试场景存档(实测任务 + 负例问法),重测复用
└── design/           # 按需:维护者档案,不进 agent 上下文
    ├── overview.md   #   设计概览(what + why)——唯一必建
    └── decisions/    #   ADR,仅经用户命令创建,默认无
```

**加载语义决定内容去哪**:
- 每次触发都要的(方法论 / 判据 / 不变量 / frontmatter)→ SKILL.md;
- 只在某步 / 某分支才要的(深度模板 / 穷举清单 / API 参考 / 长例),以及特定环节的配套物(格式模板 / 给子 agent 的指令)→ `references/`,且 SKILL.md 引用时带触发条件(「到第 Y 步读 references/X」);
- `design/` 永不给 agent 提供使用信息(它只记 why,见 §5)。

**拆 vs 不拆判据**:内容服务每次都用的核心 → 留 SKILL.md 内联(**即使长**);只服务某分支且有分量 → references/。别把「核心但长」误当情境细节拆掉。**拆分信号**:一节 >100 行只服务子场景;同段清单 3 处重复;穷举列表(抽到 references、运行时读,永不过时);反向:子节只一行折回父节。

**命名即信号**:文件名 / 目录结构本身给 agent 信号(`test_utils.py` 在 `tests/` vs `src/core/` 含义不同),组织清晰 = 少写解释。

**章节带序号**:skill 内所有 agent 会读的文档(SKILL.md 正文 + references/*.md),章节用数字编号、从 1 开始,层级以两级为主(如 §3、§3.2)。序号是精确指位的锚——跨文件引用写「见 SKILL.md §4.3」即可直达,agent 定向跳读、人 review 讨论都靠它定位;无序号的标题只能靠转述文字指位,引用易漂、搜索易错配。design/ 不强制(维护者档案,按习惯)。

**超过 100 行的 reference 文件,开头放目录**:agent 读 references 常先只读前 ~100 行判断相关性,值得才读全文 —— 中后段关键内容可能从未进入上下文(写了但不可达)。目录镜像文件真实标题(可二级一行、子节内联压缩),让 agent 预览即可定位目标节。SKILL.md 本体不适用(触发即全文加载)。

## 3. SKILL.md 怎么写

写之前想清楚加载模型:frontmatter 每次会话都在(= 触发器)→ 正文触发时全文加载 → references 按需。三层各有各的写法。

### 3.1 frontmatter(触发器工程)

- `name`:≤64 字符、仅小写字母数字连字符、不以连字符开头 / 结尾、不连续连字符、与所在目录名一致。可选字段:`compatibility`(硬环境依赖才写);`license` / `metadata` / `allowed-tools` 本仓 skill 不用。
- `description` 是 skill 调用的**主触发器**(Anthropic 官方 skill 文档:primary mechanism;agent 倾向**漏触发** skill):
  - **只写触发 + 可带一句 purpose,绝不写 workflow** —— description 一旦写了流程,agent 照它行事、不读正文。边界测试:有显式顺序标记(先…再… / 然后 / 编号 step)→ workflow,删;单个动作 / 扁平列举 / 范围关键词 → OK。负向路由里表优先级的「先 X」指向 skill 选择(调用某个 skill),豁免;指向本 skill 内部步骤的,不豁免。
  - **pushy 防漏触发**:显式列触发场景 +「凡是 X / Y / Z 都用,即使没明说要」。
  - **覆盖正文全部场景(主 + 次)**:通读正文,列全部「当用户…时」的场景,主次都进;编辑加了新职责面(新 reference / 独立能力)→ 必回头同步 description。
  - **负向路由**:对照本仓 + 挂载的全部 skill,对同 query 双触发的易混兄弟给去向 —— **外路由**(点名去另一个 skill,写**全名含命名空间**,如「→ od-dev-gameplay-automation」)/ **自路由**(拉回本 skill 主场景,写「别做 X → 先做本 skill 主场景」);有重叠兄弟时无论 skill 多简单都必须给。
  - 形式:条件触发句开头(「当…时用」/「Use when…」),别第一人称;语言按用户提问语言排(中文域中文为主、英文短语附后,不必逐句对译);长度 Anthropic 官方建议 ~100 词,硬上限 1024 字符,超 ~600 警惕冗余。
  - 写完四查:
    1. 每个正文场景都有触发词?
    2. 每个双触发兄弟都有去向?
    3. 反向测——列正文场景的真实问法(含走样措辞),凭 description 判 agent 会不会加载;
    4. 逐句跑 workflow 边界测试。

### 3.2 正文怎么组织(结构层)

- **正文骨架(按需,非强制)**:Overview(是什么 + 核心原则一两句)/ When to Use / Quick Reference(扫读表)/ Common Mistakes(常见错 + 修)。**When to Use 的划界**:触发加载的语义一律归 description(会话开始时 agent 只看得到它);正文的 When to Use 节只写「已加载后的适用性判断」(症状、何时不用、多形态之间的选择)——两者不重复。
- **含必做序列 → 开头 ordered must-do checklist**:skill 含「有顺序、漏任一步就不算完成」的必做动作序列时,开头必须给编号清单:编号 + `☐` + 祈使动作 + 一行判据 + 标「必做」,并标一句「没做完这 N 步不算完成」(completion gate)。**跳过条件 / 分支写进步骤内**(「若 X 则跳过本步」),有可跳步不因此判为无序列;**末步必须自验证**——回头核对前面每步的**结果**真的达成,查出错回到出错那步重做、再核,全过才算完成(防「试过 = 做成」);判据 / 踩坑 / 方法论留后文,主流程只放可勾动作 + 一行判据。「开头」指 skill 正文最前;**总装章自身的 checklist 随章置于文末不算违反**(头尾不变量:关键规则开头 + 收尾 recap,两条原则在此调和)。
- **头尾放不变量**(agent 对长文呈 U 型回忆,中段最弱):关键规则放开头,自检 / recap 放结尾,别把「必须做」埋中段。
- **决策点放依赖它的步骤之前**:agent 要先定的判断(何时用 / 不用、多形态 skill 的形态选择、前置条件)放在依赖它的内容之前,别埋后文(形态选择放第 6 步 → 前 3-5 步白走)。
- **流程图只用于非显然决策点 / 可能早停的循环**;线性步骤用编号列表,不用流程图。
- **token 效率**:频繁加载的正文尽量短;正文行数红线 <500 行(Anthropic 官方;超限拆 references);细节移 references;别 `@` 强制加载别的文件;去冗余。

### 3.3 怎么写每一条(句子层)

- **right altitude(粒度)**:在「太脆」(硬编码流程,换场景就废)与「太泛」(空话无信号)之间 —— 判据式:「X 条件下选 A、Y 条件下选 B」。
- **约束强度逐段校准**(同一 skill 内混档是常态,逐段独立定,实测后按症状修正):选档问句「这段操作换种做法会造成实质伤害吗?」无伤害 → 高自由(讲 why + 判据,信 agent 现场判断);有伤害 → 低自由(固定步骤序 + 禁令,别软化成建议;skill 带工具时优先固化成脚本让 agent 执行)。**默认偏高自由,锁死是例外**——连用大写禁令 / 超刚性结构 = 黄旗,先试改讲 why;但防「明知故犯」的纪律条款用禁令是对的(form-to-failure 第 1 行)。**不为特定模型调档**(「某模型会漏步 / 嫌繁」的需求经 §6 RCA(根因分析)过滤,不进共享 skill)。
- **form-to-failure(按失败类型选指令形态,形态选错会反效果)**:
  - 压力下明知故犯 → 禁令 + 合理化反驳表(软建议无效);
  - 照做但产出**形状错**(冗长 / 埋没结论)→ 正向 recipe:说产出**是什么**(各部分 + 顺序),别用禁令清单;
  - 漏掉本该有的元素 → 结构式(模板里 REQUIRED 槽位);
  - 行为该随条件变 → 条件式(挂可观测谓词)。
  禁令对塑形类失败反而更糟(agent 会和 "don't X" 谈判);别加「除非…」类例外从句重开谈判。
- **指令式 + 判据**:祈使句(「先 X 再 Y」「若 Z 则 W」),不叙述文档腔;标题写成判据本身(扫标题能读懂骨架)。
- **指令写意图,不写实现**:删掉工具名 / 命令,agent 还能照做 → 是实现示例,删(「命令写出来才可执行」是错觉);删了就不会做(细节承载项目约定)→ 是指令本体,留。术语换大白话信息不丢就换。
- **≥3 个并列项 / 步骤 / 枚举值用列表,一项一行**:长句顿号 / 嵌套编号塞多项 → 读者自己切分,切分错 = 修饰误配或漏项;有序 / 无序按顺序语义选。行内短语举例可豁免;**独立可执行 / 可勾选项必须列表**。
- **指令性枚举分支完备**(checklist 步骤 / 路由表 / 检查清单是行为规约时):一步要处理的输入有哪几种可能情况(含文件不存在 / 未命中 / 检查不过),就把每种情况的处理都写全——「读文件对齐」要写清文件不存在时怎么办;路由表带「未命中」的去向;检查项带「不过」的出口。参考性列表(知识查阅,匹配不上无害)不受此约束。
- **干净读者原则(总纲)**:默认读者 = **无会话历史的干净 agent,以及没参与编写的普通人**——大模型(包括写 skill 的你)极易输出缩写、黑话、自造复合词,对这两类读者都不可读;每句都要脱离会话可懂。具体:
  - 别用缩写、中英混杂黑话;别堆修饰造名词;首次出现的术语带一句解释;
  - 禁会话指代(「如前述 / 当时我们 / 这次开发中」);禁依赖当下状态的措辞(「当前的 X / 已完成的 Y」);
  - **写规则,不写立场**:「不照搬某体系 / 与某方法论的异同」是论辩内容,零行为指导 → 归 design/ 动机段。自检:这句话能让 agent 多做对一件事吗?不能 → 删或挪;
  - **同一概念全程一个叫法**:换名会被当**不同实体**,前后规则断链(动词同理);选领域地道词,别自造平行说法。自检:写完列核心概念词(3~5 个),逐个搜同义变体,混用即统一;
  - 总自检:随机抽一段,抹掉会话上下文,这个读者能照做吗?
- **等权选项定默认,不给菜单**:多个做法真等权(纯偏好差)→ 定一个默认 + 例外出口(「X 用 A;遇 Y 改用 B」),别并列摆开让 agent 挑(犹豫 / 漂移);有真实条件的分派(「X 条件选 A」)是判据式,不算菜单,照写。

### 3.4 特殊内容形态

- **gotchas(环境坑清单——常是 skill 里价值最高的内容)**:收**环境特有、违反合理假设、不说 agent 必然搞错**的具体事实(✗「正确处理错误」泛泛建议;✓「某数据表带软删除标记,查询必须加未删过滤,否则混入停用记录」)。典型形态:隐藏陷阱、同一实体多处名字不同、反直觉行为差异。**放 SKILL.md 正文,不进 references**(坑的触发条件 agent 自己认不出,按需文件它想不起来读;重构时别当可抽走的细节误伤)。长出来的通路:实测 / 实战中被纠正一次 → 过 §6 RCA → 沉淀一条。
- **计划先行(批量 / 不可逆操作)**:一次要改一大片、或改错难回滚(无 git 兜底的运行时数据 / 发布动作 / 批量迁移)→ 先产出**改动清单**(改哪些、各改成什么)→ 核对清单本身(目标都真实存在?必填都覆盖?有无冲突?)→ 过了才动手;校验报错列出可用值,agent 能照着自纠。git 管辖内的少量文件 → 不必,直接做。

## 4. 内容边界:写什么、引什么

### 4.1 方法可泛化,细节可具体(按角色与脆弱性定,不一刀切禁具体)

- 具体内容是**指令本体**(步骤 / 命令 / 模板 / 脚本用法,删了 agent 就不会做)→ **直接写具体**;脆弱 / 需一致的操作写死步骤序,能固化成脚本的固化成脚本;
- 具体内容是**叙事佐证**(「某项目里我们如何…」)→ 不进 skill,归 design/ 动机段,skill 只留从它抽象出的判据;
- 具体领域事实(键位 / 坐标 / 机制数值)归项目 doc,skill 引位置不复制值;
- 仍防的失败:例子的偶然细节被当成必然规则 —— 写具体步骤时自问「这步为什么存在,换个场景还成立吗」,别把本项目的偶然做法伪装成普适规则。

### 4.2 数值与调参归属

原则 / 规则归 skill(「模板匹配的判定框每边留出余量,以容忍匹配误差」);精确调参值是数据 → 默认归 doc / design(实测定值);与方法论不可分的通用约定(「余量 ≈ +10px」非某游戏专属)→ 留 skill 并标「≈,按实测调」。判据:换项目 / 换版本这值还成立吗?

### 4.3 自包含:引用规则

- **硬门**:引用 target 必须**在已提交仓库里** —— gitignored(`.debug/` / `config/` / `.claude/`)、个人本地文件、memory 一律禁(skill 是共享 artifact,引用闭包外状态 = 在别人机器 / CI / clean checkout 上不存在)。门管 skill **依赖**的内容(含 design/ 内);不管运行时产物(日志 / 截图等执行时生成物)。
- **三分场景**:
  - **一条龙框架 skill**(公共仓,被各一条龙项目安装):可引一条龙公共包(`one_dragon`)相关内容 + 本仓已提交内容;**不引任何单游戏的私有路径 / 游戏事实**(skill 会装进别的游戏项目,引了就断链);
  - **游戏项目专用 skill**(放该游戏项目的 skill 目录):只引**该项目下 git 追踪的文件** —— runtime 资产路径(skill 要读写的操作对象)+ skill 目录内自带工具;具体代码行 / 易变文档抽象化;
  - **独立发布 skill**(跨生态分发,本仓无此形态,通用兜底):禁止外引,知识内联。
- **接口名两问**:删掉这个名字,agent 还能照做吗?能 → 删(它只是示例);不能 + 它是框架地基级、几乎不改名 → **写全名**(全局可搜索:将来代码改名,一搜就发现这条要跟着改;模糊化反而不报错却已指错)。引用其它 skill 同理,写全名含命名空间。
- **防过时四档**(按引用目标的稳定性选,从优到劣):
  1. 依赖稳定契约:引地基级接口名(几乎不改名);
  2. 校验引用:用持续集成脚本自动扫描引用是否存在,目标失踪时构建报红;
  3. 单一事实源 + 运行时读:不把值嵌进 skill,指向稳定路径,令 agent 用时读当前值;
  4. 吸收自含:复制进 skill 目录(与源头会漂移,小而必须可靠的才用)。
- **引用清偿**:删除 / 改名被引用的实体(标记 / 命令 / 模块 / 脚本 / 路径)→ 全仓扫描引用点同步清偿,禁留死标记(干净 agent 照死标记操作必失败)。

## 5. design/:记录这个 skill 为什么是这样的

- **why 的三层归宿**:① SKILL.md 规则旁**内联一句理由**(第一阵地——agent 也受益,讲 why 比硬禁令有效);② overview **动机段**(第二阵地——维护者改 skill 前读);③ git commit message。ADR 是第四层异常通道。
- **overview.md 是唯一必建文件**:动机段最小必写清单(防模板化敷衍)——偏离业界惯例之处及原因 / 实测教训 / 刻意不采纳的备选;状态节(draft / validated)也住这。
- **ADR 仅经用户命令创建**(默认不立;本仓极少触发属正常,**不写 ADR ≠ 不合格**):agent 不得自行新建,认为够格 → 向用户提议。够格判据(同时满足):
  - 架构级(影响整体结构 / 跨多文件)或难逆(推翻成本高);
  - 有实质备选(≥2 个可行选项、选了一个、未来会被人问为什么);
  - 自检问句答得上:「半年后有人能从这条学到『为什么不能那样做』吗?」。
  **不提议**:内容补录 / 结构整理 / 规范套用(这些是变更日志,不是决策,commit message 装得下)。用户命令建立时,格式按 `references/design-docs.md` 写,并建 `decisions/INDEX.md`。

## 6. 测试验证

**「你以为写清楚了 ≠ agent 真能照做」** —— 唯一可靠的检验是让干净上下文的 agent 用这份 skill 真做一次活。本仓制度 = **单轮子 agent 定性实测**;不做量化评估基础设施(基线对比 / 通过率统计 / 触发率自动优化——那是高频迭代团队的工具,本仓 skill 低频修改,养不起)。

**术语**:GREEN = 实测通过(带 skill 起干净 agent 真做一次活并达标);RED = 基线(不带 skill 跑同样任务、看裸 agent 的失败,仅纠正型必做);状态两态 —— **draft**(写完未测,诚实标注,可带说明使用)/ **validated**(GREEN 过),声明在 design/overview 状态节。「完成」口径:过 §7 总装(含该测的测完),GREEN 与否用 draft / validated 跟踪。

- **何时测**:新建必测;编辑改了**实质指令**(新增 / 修改判据、流程、规范)→ 实测一轮——起干净子 agent,给真实任务 + 新版 skill,观察卡点 / 乱问 / 走偏 / 产出差,记 gap 回灌;纯排版 / 错字 / 引用修正 → 不必。
- **按两类选制度**(判据:这条 skill 的依据是「agent 默认会做错所以纠正」,还是「业界方法论本来就该这么做」?):
  - **纠正型** → pressure test(压力下守不守规矩:3+ 重压力的脚本化场景 + 抓合理化原话 + 堵漏循环);RED(baseline 看失败)必做;
  - **方法论覆盖型** → utility test(干净工作空间 + 可交互子 agent + 你扮用户只答所问 + 观察 gap + 修 + 循环);RED 可省(单一 baseline 外部效度不足——你本地看到的失败可能只是你模型的弱点)。
- **gap 回灌先 RCA(根因分析)**:通用 gap(任何合理 agent 按方法论走都会撞)才进 skill;模型 / 环境特异的怪癖不进。观察项含**约束配错**:脆弱步骤上自由发挥 / 产出跑偏 = 该段过松(提档写死);被固定流程卡住、反复问能否变通 / 绕开流程走 = 该段过紧(降档讲 why)。
- **测试场景留档**:实测任务(2-3 个真实任务)与负例问法(1-2 条「看着相关但不应触发」的 near-miss)记入 `evals/TESTS.md`,重测复用——新场景跑过后补进去,积累成该 skill 的测试资产。
- 跨仓消费场景发现 gap → 写规范反馈,格式见 `references/skill-feedback.md`。
- utility / pressure 细则 → `references/skill-testing.md`。

## 7. 创建/修改流程(总装)

> 没做完这 7 步不算完成。

1. ☐ **需求确认**:该不该建 + 四问 + 边界 / 成功标准,**用户确认后才动笔**(§1)
2. ☐ **定位**:查兄弟 skill 防重叠(重叠的引用而非重复);编辑已有 skill 先读它的 design/overview,防改出与既有设计矛盾的内容(§1)
3. ☐ **写 SKILL.md**:frontmatter → 正文 → checklist(§2-§4)
4. ☐ **写 design/overview**(§5)
5. ☐ **过完工自检**(下述)
6. ☐ **测试**:改了实质指令 → 起干净子 agent 实测一轮(§6)
7. ☐ **挂载验证**:正例问法能触发 + evals/TESTS.md 里的负例问法不误触(首轮尚无 TESTS.md 时,仅验正例触发);提交按所在仓库流程
8. ☐ **回头核对 1-7 步的结果真的达成**——第 6 步实测后若回灌修改了 skill,重过第 5 步自检再收尾

**修改时重构触发器**(遇到就重构,别只追加):重复自己 → 合并;同一条规则下例外条款累积到第 5 个 → 重新抽象;费力找 / 理解某条规则 → 结构该过一遍重构。

**完工自检**(只点名 + 链回,规则本体在各节;**任一项不过 → 回对应节修正后整单重过;涉实质指令改动 → 补第 6 步实测**):

- ☐ name 硬约束;description 只写触发不写 workflow、覆盖主次场景、易混兄弟负向路由全名(§3.1)
- ☐ 必做序列有 ordered checklist;跳过条件在步骤内;末步自验证(§3.2)
- ☐ 指令式 + 判据;无日期标注 / 过程记录 / 叙事例子;术语一个叫法(§3.3、§4.1)
- ☐ gotchas 在正文;枚举分支完备(§3.3、§3.4)
- ☐ 引用过硬门 + 三分场景;接口名两问;无 gitignored / memory 引用(§4.3)
- ☐ overview 必建 + 动机段最小清单 + 状态节(§5)
- ☐ 超 100 行 reference 开头有目录;章节带序号(§2)
- ☐ 清晰度扫描:随机抽 2-3 段,以「干净 agent / 没参与编写的人」的视角读——无未定义缩写、无黑话、无自造复合词,首现术语有解释(§3.3)
