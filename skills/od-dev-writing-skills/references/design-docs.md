# ADR 配套格式(用户命令建立 ADR 时读)

> 本文件是 `od-dev-writing-skills` SKILL.md §5 的配套物:ADR 的格式模板、状态流转与写作细则。提议判据 / 不提议清单已内联 SKILL.md §5,此处不重复;**仅当用户命令建立 ADR 时**才需要读本文件。

## 1. ADR 文件格式

每条架构决策一个文件 `design/decisions/NNNN-<slug>.md`(NNNN 从 0001 递增;slug 短横线英文小写;下一个编号照 INDEX 接排,防撞号)。模板取自 arc42(业界架构文档标准)的决策记录节:

```markdown
# NNNN. <决策标题>

- **Status**: proposed | accepted | deprecated | superseded by NNNN
- **Date**: YYYY-MM-DD(决策正式记录日;与原决策日不同则 Context 注原日)

## Context
当初面对的问题 / 场景 / 约束。不是 rationale,是「为什么要做这个决策的局面」。

## Decision Drivers
影响选择的 forces —— 要权衡什么(性能 / 可维护 / 版本鲁棒 / 用户偏好…)。无显式 driver 可省此节。

## Considered Options
备选方案 + 各自利弊。**最值钱的字段** —— 防后人重复扯皮。
重决策(多真实选项)在此逐选项列利弊;二元 / 简单决策几行带过。

## Decision
选了哪个 + 一句话为什么。

## Consequences
正向收益 / 负向代价 / 必须 follow-up。
给未来维护者最关键的一节:「推翻它会碎什么?当初接受了什么代价?」

## Links
相关 ADR(supersedes / 相关)、design 章节、外部来源。无则省。
```

- **必写**:Status / Date / Context / Considered Options / Decision / Consequences;**按需**:Decision Drivers / Links(「写多少」= 写对这条决策 applicable 的所有节 —— 按适用省略,不是偷懒)。
- **状态流转**:`proposed → accepted`;被推翻 → 新建一条,旧条 Status 改 `superseded by <新号>`、新条写 `Supersedes <旧号>`;不删旧条、不改旧条正文(只增不改的历史)。
- **合并 vs 拆**:服务同一个架构选择的子决策(如「五步顺序」+「两个必填槽位」)→ 合并进一个 ADR(作 Considered Options / 子点),别拆碎;只有独立的架构决策才各成一文件。

## 2. INDEX(第一条 ADR 建立时同建)

`decisions/INDEX.md` 一张表给全貌:

```markdown
| NNNN | 标题 | 状态 | 日期 |
|------|------|------|------|
| 0001 | design 与 ADR 分离 | accepted | 2026-08-04 |
```

## 3. 灰区裁决(拿不准够不够格时)

- **判架构级 vs 实现级**:这条决策会影响**别处**吗(别的文件 / 别处实现 / 后续多个决策)?会 → 架构级 → ADR;只影响当前这一处局部 → 实现级 → commit message。例:「检测方法按元素类型分流」影响整个 skill 流程(架构级);「平滑核用 5×5」只影响一处(实现级)。
- **别在 ADR 里拿通用写作规范当理由**:od-dev-writing-skills 的规则是对所有 skill 默认成立的**基线**,「我们遵循规范 X(见 ADR-XXXX)」= 重申基线 = boilerplate → 不够 ADR 门槛。ADR 只记**该 skill 特有**的决策;只有**故意偏离**某通用规范时,才值得 ADR 引用它说明为何偏离。

## 4. ADR 写作:默认知识外的具体要匿名 / 泛化 / 当场解释;禁会话速记式压缩词

ADR 给**没参与当时决策的维护者**看。可读性底线:**只依赖读者默认能知道的东西;默认之外的具体,匿名 / 泛化 / 当场解释。**

**默认知识范围,由 ADR 所在位置定(累加):**

| ADR 位置 | 读者默认知道的 |
|---|---|
| 公共 skill(`od-dev-*`)| 本仓 + 一条龙公共包(`one_dragon`)+ 行业通用词 |
| 项目内 skill / 子项目 | 上面 + **本项目代码 / 文档 / 约定 / 游戏事实** |

同样东西,在项目 ADR 里是"已知",在公共 skill ADR 里就是"泄漏"——具体玩法名、某 NPC、项目私有 bug 编号,写在公共 skill ADR 里,别的项目读者读不懂。

**写 / 改时,对每个具体且关键的东西(删了就读不懂的那种)判它在不在默认知识里:**

- **在** → 直接用;不显然的首次带一句解释(如 `screen_info` = 每张画面的区域 / 模板定义,框架靠它识别画面)。
- **不在** → 三招:
  1. **匿名**(首选):保留具体感,不点名。"某自走棋式玩法"代具体玩法名、"一个 NPC"代具体 NPC。
  2. **泛化**:只留通用结论。"有些游戏用非文字符号标可交互对象"代某 NPC 的 `>名字<` 标记。
  3. **当场解释**:具体有说明价值就留,框成"某项目的做法"并讲清。

**读者自检**:写完问 —— 一个合格同行,带着上面"默认知道的",没参与过当时的事,能不跳出默认知识就读懂吗?他要去翻默认知识之外的东西(别项目代码、私有 bug 表、某次日志)→ 这条漏了。

**另一半——会话速记(即使全在默认知识内也看不懂)**:写成只给自己看的简略笔记——只甩标签不讲当时情况、长串嵌套修饰、**把当时会话里临时造的压缩词当正式概念用**(写的人刚聊过觉得自然,没参与决策的读者没有这份对话记忆,词等于密码)。

- 修法:Context 先讲"当时发生了啥"再讲"决定啥";决策一句大白话放开头;压缩词要么展开成大白话,要么首次出现当场定义。
- **写完自检(逐词扫)**:全文的概念词逐个问「它在**本 skill 现行正文或读者默认知识**里有出处吗」——没有、且是本次对话临时起的名 → 展开或定义。(与 SKILL.md §3.3 干净读者原则同根:SKILL.md 的判据是「新会话读者」,ADR 的判据是「没参与决策的维护者」——两者都不在场于你写它时的对话。)

## 5. 图示:文本框线图,禁图形语法

全景图 / 架构图 / 流程图一律用**普通文本图**(code block 内框线字符拼),不用 mermaid / 图形语法——查看环境不渲染图形语法,渲染不出的图 = 不存在的图;框线图在任何纯文本面(终端 / 编辑器 / git diff / review)都可读。项目内玩法 / 设计文档的图示同判。
