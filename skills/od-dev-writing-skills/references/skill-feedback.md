# skill 反馈机制(开发中迭代优化 skill)

> 本文件是 `od-dev-writing-skills` 的 situational reference。SKILL.md「创建/修改流程」管 skill **怎么写**;本文件管 skill **写完后怎么在真实开发中持续迭代** —— 开发中发现的 gap 怎么反馈进 skill。

## 为什么单独一套机制

skill 是给 coding agent 用的方法论。**真实开发(用 skill 干活)是发现 skill gap 最好的时机** —— 但直接在开发中途改 skill 有两个坑:

1. **打碎深做**:开发是深度串行任务;瞄到个 skill 可优化就切过去改 = 频繁切上下文,凑轮次偷懒。
2. **上下文污染 + 不守规范**:开发中途带着任务包袱改 skill,容易破 4 硬规范 / over-fit(把模型特异怪癖写进共享 skill)。

故反馈机制 = **抓信号(不打碎开发)+ 干净上下文改进(守规范)+ 干净上下文验证(就地 GREEN)**。

## 反馈回路(通用方法论)

1. **开发中发现 skill gap → 别中断,抓反馈**:写一条简短反馈(哪个 skill / 观察 / 为什么是通用 gap(RCA)/ 拟改)。若是「把我卡住」的 gap,**记下卡在哪个任务**(验证步要重试它)。**反馈只抓信号** —— 别为套全套规范中断开发。
2. **自然断点 → 干净上下文改进**:起一个**隔离的子 agent**(干净上下文,不带开发任务包袱),按本 skill(od-dev-writing-skills)4 硬规范改进目标 skill。干净上下文 = 更好守规范、不被开发任务带偏。
3. **干净上下文验证(就地 GREEN)**:改进后,起**另一个干净上下文子 agent**重试「当初暴露 gap 的任务」(用更新后的 skill)。做成 = 改进生效;还卡 = 改得不够,再迭代。这比合成 utility test 更扎实 —— 拿真实 blocker 验效果。
4. **审 + 落定**:审改动的方法论合规(4 硬规范 / 没 over-fit;**验证测效果替不了方法论合规**)→ 过则定稿;不过则回炉。

## 关键判据

- **RCA 防 over-fit**(详见 `writing-craft.md` §3.1):只**通用 gap**(任何合理模型/agent 按方法论走都会撞)进 skill 正文;**模型/环境特异**(只某模型怪癖 / 某环境失败)→ 该 skill `design/decisions/` 的 ADR 记「某模型需额外哄」,不进正文;不确定 → 标「待核」。
- **份量缩放**:实质性 / 真卡住的 gap 走完整回路(改进 + 验证两子 agent);鸡毛蒜皮(笔误 / 一句话澄清)直接改,不走回路。
- **干净上下文**:改进 + 验证都用隔离子 agent(主 agent 带着开发包袱,不够干净)。
- **反馈只抓信号,严谨合规归改进子 agent**:写反馈别中断深做;RCA 定夺 / 4 硬规范自检由改进子 agent 干。

## 执行细节(各消费方仓库自定义)

具体用什么子 agent、反馈队列放哪、并发限制等**执行细节由各消费方仓库自己的 harness 决定**(如 Claude Code 的 `.claude/agents/` + `.claude/CLAUDE.md`)。**本文件只给方法论回路,不绑特定 agent 或调度** —— 各仓库按自己的 harness 落地(预载本 skill 给改进子 agent、起干净上下文验证子 agent 等)。
