# 修复决策(已定位后怎么修)

## 不变量:根因是链,介入点即方案选择
修复的难点不是"找到 bug"，而是"在因果链的哪一环介入"。**根因是一条链，不是点；选在哪一环介入 = 选方案。** 本 skill 把"决定怎么修"拆成 5 步，每步锚定一个业界方法论，产出一份可被 review 的修复决策。

## 何时用 / 不适用
- 用：bug 已定位失败机制，要在多个修法里选
- 不用：还没定位失败机制 → 先系统化定位（通用调试纪律见 `od-dev-write-operation` 调试纪律；项目专属排查判据见所在项目调试类 skill）；新功能设计 → 需求设计流程（本 skill 只管修复决策）

## 决策流程（5 步）

**0. 确认故障机制（入口）** — 能复述"失败怎么发生"？不能 → 先按系统化调试纪律定位（读证据 / 假设驱动 / 一次只改一个变量，见 `od-dev-write-operation`），定位完再回来。若根因涉及「op 走到陌生画面」,先确认画面交互认知完整(说不出全部可交互元素 → 先按 `od-dev-screen-onboarding` 建档),别在猜的画面上定修法。

**0.5 守卫类 bug 的不变量协议**（判定:失败机制是"某门/守卫/冷却/限流被绕过或未生效"→ 必走本步;普通逻辑错误不用）— 修任何守卫之前:
1. **先写不变量**(一句话:「任意两次 X 之间至少…,**无例外**」);例外必须显式列进不变量,不许在代码里隐式留。
2. **穷举旁路**:grep 该守卫的全部调用方,逐个读 `or` 豁免 / 特例分支 / 新入口,确认每条路径都被守卫覆盖——守卫放调用侧时,任何一个 `or` 短路豁免就是漏网入口。
3. **守卫放最内层唯一入口**(所有路径必经的函数头),删掉各分支/调用方的分散检查——分散的检查必然漂移。
4. **测试锁不变量,不锁行为**:①造一个「绕过场景」断言被拦;②造一个「正常场景」断言放行(不误杀);③守卫历史上已分散过 → 加源码级锁(守卫标识符在被审函数内只出现一次,再出现 = 分散回归)。

**1. 画因果链** *(RCA / 5 Whys / Fault Tree)* — 症状→直接原因→机制→包级→系统级→上游代码→流程→修复状态。每节点 = 候选介入点。**挖到 actionable 层（你有权且能修的那层），不更深。** 故障形态是「预期行为没发生/被削弱」而非「错误行为发生」时，改沿**动作链路**横着画：该动作从生成到最终执行的完整路径，逐环标注放行/掐断谓词与实际死活；多处截断同现 = 候选架构级缺位，升格设计件一次解决，不在单环打补丁。

**2. 影响面 + 可行动性** *(Impact Analysis / Blast Radius)* — 在链上标"我能修"的节点。影响面决定方案形态：全量用户 / 主依赖链 → 必须零用户操作；个别环境 → 文档可接受。

**3. 候选方案** — 在 actionable 节点生成：补系统依赖 / 锁版本或换实现 / 改代码移除问题调用 / 文档绕过 / 提上游 PR。

**4. 前提验证 + 权衡** *(Trade-off Matrix / Pugh)* — 每个候选必填：
- **前提验证**：前提是事实还是假设？最小成本证伪（下 artifact 看、跑解析、grep 全库）。前提包括**测量工具本身**：结论出自扫描/统计脚本时，先确认工具对全部已知形态可判——归入「其他/未匹配」桶的条目单列复核，静默丢弃 = 把盲区当「无违规」。
- **权衡**：[代价 / 风险 / 可逆性 / 临时-永久] 横评。
- **必填：根因链的"上游修复状态"**（已修？待发版？有意设计？）→ 决定方案是"有终点的临时止损"还是"永久拖延"。

**5. 假设驱动验证** *(Hypothesis-driven Verify)* — 精确化"失败的可观察判据"，确认介入后该判据不再成立。不是"能跑就行"——开发机有系统资源时成功可能是假绿，把判据收紧到具体路径 / 行为。

## 速查表
| 步 | 方法论 | 核心提问 |
|---|---|---|
| 0 | — | 能复述失败机制吗? |
| 0.5 | 不变量协议 | 是守卫被绕过?不变量是什么?旁路穷举了吗?守卫在唯一入口吗? |
| 1 | RCA / 5 Whys | 链上有哪些介入点?哪个 actionable? |
| 2 | Impact Analysis | 影响谁？谁有权修？ |
| 3 | Intervention Selection | 每个 actionable 节点对应什么方案？ |
| 4 | Trade-off Matrix | 前提验证了吗？上游修了吗？ |
| 5 | Hypothesis-driven Verify | 失败的判据是什么？还成立吗？ |

## 常见错误
- 直接采纳 issue 里用户的方案，不验证前提
- **守卫类 bug 只修症状入口,不穷举旁路**(判据:失败机制是"门被绕过"→ 必走 0.5;漏走的后果 = 同一守卫修 N 次,每次实跑暴露下一个漏网入口)
- 根因停在"缺某文件"，不查"上游是否已修" → 误判方案临时 / 永久
- 验证停在"能跑"，不收紧到失败机制
- 介入点前提（如"只有这一处用"）不验证就下结论
- 用带盲区的扫描/统计结果当全量结论（未匹配形态被静默当「无违规」）
