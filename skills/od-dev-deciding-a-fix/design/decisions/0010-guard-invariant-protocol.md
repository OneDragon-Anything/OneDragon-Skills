# 0010-guard-invariant-protocol

- **Status**: accepted
- **Date**: 2026-08-20

## Context

同一守卫(冷却门)修了两次仍漏:第一次把冷却检查放进目标分支内,第二次发现危机豁免路径(`or` 短路)绕过调用侧的冷却门——每次修复只验证了自己改的那条路径,没有穷举"谁会绕过这个门"。真实案例:游戏 bot 的转型冷却,同一备战轮内 60 秒两次翻转(应该至少隔 1 轮),第一次修 r87 只挡了保命分支的 with_progress 路径,第 12 局实跑又复现,第二次修 r90c 才在危机入口补上,之后第三次(r91)才真正收口为函数顶单一守卫。

病根不是"忘了某个分支",而是**修复流程缺一步**:守卫类 bug 的修法与普通 bug 不同——普通 bug 修的是"这一处逻辑错了",守卫类 bug 修的是"一个应当全局成立的不变量被多处入口中的某几个绕过";只看症状入口修,其余入口迟早再漏。

## Considered Options

1. **现状(逐入口补检查)**:哪里漏补哪里。已实证失败——分散的检查各自演化,旁路(or 豁免/特例)坐在隔壁都发现不了。
2. **调用侧统一检查**:在调用方入口做一次守卫。失败面:调用方自身有豁免通道时(or 短路),守卫形同虚设;且多个调用方 = 多份检查 = 漂移。
3. **不变量协议(选定)**:修守卫前先显式写不变量("任意两次 X 之间至少…,无例外"),穷举旁路,守卫放最内层唯一入口(所有路径必经的函数头),测试锁不变量(绕过场景被拦 + 正常场景放行 + 源码级锁防分散回归)。

## Decision

在决策流程步 0 与步 1 之间加 **0.5 修守卫/门逻辑前的不变量协议**,四步:写不变量(例外显式列)→ 穷举旁路(grep 全部调用方 + 全部豁免/特例分支)→ 守卫放最内层唯一入口 → 测试锁不变量而非锁行为(绕过被拦/正常放行/源码级单点锁)。

## Consequences

- 守卫类修复从"症状驱动"变"不变量驱动":第一次修复即覆盖所有入口,不再依赖实跑暴露下一个漏网。
- 代价:守卫类 bug 修复前多一轮穷举(grep + 读调用方),对简单守卫略显重;判据 = bug 是否属于"门被绕过/未生效"类,是才走 0.5。
- 源码级锁(标识符在函数内只出现一次)是激进手段,适用于"该守卫历史上已分散过"的场景;首次实现可只用行为锁。
