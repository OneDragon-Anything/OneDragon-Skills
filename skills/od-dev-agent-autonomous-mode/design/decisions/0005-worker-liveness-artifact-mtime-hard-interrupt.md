# ADR-0005:在飞 worker 的活性判据用产物 mtime,干预走硬时限 interrupt

- Status: accepted
- Date: 2026-08-25

## Context

实战实证:一个 worker 的代码产物 06:12 全部落完,之后 90 分钟零产物;期间编排者发过探询消息(06:39)但消息排在 worker 的下一 turn——**单 turn 不结束就永远不送达**,对 turn 内卡死完全无效;编排者以「注册表 running+之前树在动」为由未升级,直到用户第二次问「正常吗」才 interrupt。interrupt 后强制收账(交付已有产物+未完成清单)是完全可行的路径——已落盘的 diff 足够收账,缺的验证编排者自己跑更快。

## Considered Options

- **靠注册表/进程状态判断活性**:否决——running 只说明进程在,不说明在产出(卡死的长命令/空转都显示 running)。
- **探询消息作为干预手段**:否决——机制上对 turn 内卡死无效(消息永远排不上队);只适合非紧急的状态询问。
- **固定时长后必打断**:否决——长批(模拟批量/全量验证)本身合法跑 40+ 分钟,无差别打断杀正常工作。
- **产物 mtime 判活+硬时限干预(选中)**:活性=产物文件在更新(报告/代码/脚本/json);停滞 ≥20min 且探询未获回应→interrupt(消息随中断送达+上下文保留);配套「检查点交付」派单条款(长批设计报告落盘先汇报)把可交互节点前移。

## Decision

SKILL.md §2 增「在飞 worker 的活性监控与干预」条款+派单三带扩为「长批加第 4 带:检查点交付」。判据:产物 mtime 是唯一可信观察窗;「树在动」辩护只对新 mtime 有效,mtime 停止后重新计时。

## Consequences

- 正:turn 内卡死最迟 20 分钟被发现;强制收账路径明确(不依赖 worker 配合跑完);正常长批不被误杀(有产物更新就不计时)。
- 负:interrupt 有丢失未保存上下文的风险——由「强制收账指令只要求交付已落盘产物」对冲(落盘的才能收,没收的本来也拿不到)。
