# ADR-0003:值守干预按子 agent 状态分流

- Status: accepted
- Date: 2026-08-27

## Context

值守角色要判断「派出去的子 agent 还在干活吗」并在停滞时干预。两个候选信号:①子 agent 状态清单(运行中/空闲);②产物文件更新时间。干预动作两个候选:发消息询问 / 直接中断。旧模板写的是「没有产出就发消息问,问了没回应就中断」——但这依赖「问了会有回应」,而实际机制并非如此。

## Considered Options

- **先问再断(旧形态)**:否决——发往子 agent 的消息排在它的下一回合,回合不结束永远不送达;对「回合内卡死」的子 agent,探询永远无回应,「问了没回应」与「正在干活还没到轮次」不可区分,探询本身是无效探针。
- **只认状态清单**:否决——「运行中」≠ 在产出(回合卡死也显示运行中),与「进程活着≠在干活」同病。
- **状态×产物时间双信号分流(选中)**:状态清单定「能不能用消息」,产物时间定「是不是真在干活」。

## Decision

- **活性判据=产物文件更新时间**(报告/代码/脚本任一在更新),状态与进程状态都不算数。
- **干预按状态分流**:
  - **运行中** + 产物停滞 ≥20min → 直接中断(要求交出已完成部分+未完成清单,上下文保留可续),不先发消息——那轮等待纯属白烧;已落盘部分足够验收,缺的验证自己跑比干等快。
  - **空闲** + 任务没完 → 发消息催或要现状——空闲的子 agent 收消息立刻开新一轮,送达无延迟;干完了的就去收账。
- 顺带义务:状态清单用于核对名单(上下文压缩后忘了派过几个,清单是权威;多出/少了当场对上)。

## Consequences

- 正:消息机制的两种形态(排队/立即)各用在正确的一侧;干预单判据单动作(停滞→中断),无等待窗口。
- 负:20min 阈值是经验值,长任务正常思考段可能误伤——中断是软的(上下文保留可续),代价可控。
