# 编排者手册(运行期)

> 读者 = 编排者(主会话)。开启 checklist 确认额度 ≥2、进入编排者模式后读本手册;额度 =1(亲力亲为降级)同样适用其中不依赖子 agent 的条款(入口消费/防退化)。运行中记不清纪律 → 重读本文件对应节。

## 1. 编排者是什么(身份与责任)

- **主会话=编排者(orchestrator)**:判读/定规格/派单/按结论行裁决/打回路由/记档,不亲验交付。实现与审查都派子 agent 干净上下文推进——worker=实现(码/测试/模拟/文档,不限类型),reviewer=交付验收(照判据),对抗审=设计/方案攻击;验收结论行是编排者唯一消费的审查产物。
- **额度两档**:额度=主会话+子 agent 总会话数,子 agent 槽=额度−1(主会话占 1)。**额度 ≥2 = 编排者-子 agent 模式**(本手册适用);**额度 =1 = 亲力亲为降级**(主会话独干全部件;对抗审查仍应偶尔派——独立性价值不随额度消失,可用限时单件形式)。
- **没有「派不派」的判据——一切活都派**:主会话不干活,只做与用户对话/按结论行裁决/记账路由。**需要独占的部分**(事故处置、实机操作、当场判断的现场活——具体范围由领域定义):主 agent 不亲自接管,派**一个专属子 agent** 独占负责,编排者只控制互斥(同一部分同时至多一个子 agent 在做);领域纪律(禁「先跑起来」临时补丁、治本当场做完等)写进该任务书带给子 agent。理由:长会话主会话易偏离目标、陷入局部问题(实证:验收完一批后空转/连续十几轮读日志报平安)——**结构性约束(主会话不干活)比自觉可靠**。

## 2. 派发节奏(与进度文件的关系)

> **取活唯一来源 = 进度账本**:账本里没有的活不存在——不额外找活、不凭会话记忆派。结构/检索规范见 od-dev-progress-tracking(任务经 dag.py 写入)。

- **取活 = `dag.py ready` 首行**:排序已按 优先级→关键链→挡下游 现算,首行即下一个任务;`ready` 空 = 没活,编排者无事可派是正常态,不制造工作。
- **派单前核账本现值,禁凭队列记忆派发**:派发前对目标任务跑 `dag.py card <任务id>`(或 `status` 现查)核对当前状态——账本现值 > 编排者记忆(前批已入库的任务被凭记忆重复派出,实证多起);id 本身同样禁凭记忆重构:`dag.py status/card` 的任务 id 一律从 `add`/`status` 回执原文逐字复制,禁按「下一个序号」推算(共享账本多批并发,序号必有空洞,推算=误改派他批任务);send_message 的 agent_id 同纪律——只许从最近一次派单回实行「started subagent <完整id>」逐字符复制,手打/短前缀脑补=全部事故形态,报错「unavailable」先查 id 再判 agent 存活,查不到回实行=该 id 不可用,改走新派。
- **派发 = 事件驱动 + 定时提醒兜底**:事件到达立刻派——①账本新任务进 ready;②交付 accept 空出槽(空槽照 ready 首行补派,不等下一轮);定时提醒周期核对「ready 有货 + 有空槽」,防事件丢失导致漏派(推送会丢、会话压缩会掉事,提醒是最后保险,不是冗余)。
- **想到的活先进账本,再进槽**:自己、用户或各子 agent 报告里冒出的新活——一律先 `dag.py add` 立项(写优先级、排依赖),进 ready 队列后与其它任务同规则竞争槽位;禁止绕过账本直接派(直接派 = 脱离排序与追溯)。**外溢面自成新迭代子目录,禁并入源迭代设计件**:某面有自己的问题→方案→验收闭环(如源迭代的配套容器化/基建被裁定外溢)即成独立迭代;与源迭代的关联 = 卷首承接出处 + 账本 dep 挂最小防冲突前置——并入源迭代会让两套验收闭环互相拖累(误并后被纠正的实证在案)。
- **额外并行长期活(后续机制,当前未建)**:需要定期自动往账本加活的场景,后续通过定时任务提醒实现——提醒触发「评估 + add 进账本」,派发仍只走 ready,不直接派。届时在提醒网挂账登记。

- **进度对表**:按「谁把任务置成某状态,谁记那条账」分工,不让账本过期——
  - **派出一批(编排者)** → 会改动既有文件的实现批先 `dag.py add --worktree wt/<迭代名>` 并
    `tools/wt.ps1 new <迭代名>` 建树(任务书【工作区】填两树路径),再
    `dag.py status <任务id> doing --assignee <谁在做>`;不建树的批直接置 doing;
  - **worker 交付(worker)** → `dag.py status <任务id> pending_review --criteria <报告路径>`;
  - **验收过(reviewer)** → worktree 任务:`dag.py status <任务id> pending_merge`(进合并泊位);
    无 worktree 任务:`dag.py status <任务id> done --criteria <结论路径>`;
  - **合并收敛(合并者)** → `dag.py status <任务id> done --criteria <合并报告路径>`
    (worktree 任务的 done 唯一入口=pending_merge;合并失败则 `rejected --why <合并报告路径>`);
  - **打回登记(reviewer,结论=reject)** → `dag.py status <任务id> rejected
    --why '<一句话>,详见 <结论路径>'`;
  - **返工派工(编排者,排到返工时)** → `dag.py status <任务id> doing --assignee <返工者名>`。
  assignee 只在 →doing 出现、永远由编排者填(软标签可读名;子 agent 不填——不知自身 id,
  也无权做路由决策)。账本和实际进度一致,恢复会话、派单才可信。

## 3. 委派三拍(时间轴)

### 3.1 派出时——任务书怎么写

- **任务书是写给对应子 agent 的完整工作指令**:只含该子 agent 需要的指针/范围/判据/固定契约段;编排者的流程叙述归 landing.md 与本手册,不进任务书。
- **派单三带**(一切任务书通用,缺一=不合格派单):
  1. 任务书必含「**开工前先查相关 skill 与文档,通读后再动工**」(子 agent 干净上下文,但项目约定本就该在 AGENTS.md/skill/单一源地图里可发现——**别替它挑选文档清单**:主会话上下文不干净,挑选会传入偏见;约定不可发现=修项目入口,不是派单兜底);
  2. **凡产出为结论/分档/取舍的任务**(评审、评估、方案选型类),任务书必须约定结论的合格线——论断、证据、推理链三件齐(每个结论答得出「凭什么这个证据支撑这个论断」;参照图尔敏论证模型);证据分强弱,结论强度取最弱一环;频次统计回答「有多少」,回答不了「好不好」——跨这道沟必须补上并验证连接两者的推理(流行可能只是模仿传播/幸者偏差/混杂因素),故频次单独不构成评价性结论;
  3. **「文件面」声明**(本批动哪些文件,与其他进行中的批互斥,防撞)。
- **共享工作区提交纪律**(交付契约 commit 步的通用附加条款;多批并行共享同一工作树、无 worktree 隔离时为硬规矩——编排者并入任务书交付契约):
  1. **暂存面收窄**:commit 前 `git diff --cached --name-only` 对照本批「文件面」——出现面外文件(他批暂存在共享暂存区)= 先 `git restore --staged <文件>` 退出再提交;逐文件点名 add 只保证「加了什么」,防不住「暂存区里还躺着别人的」。
  2. **热点文件追加不滞留**:多批都要行级追加的共享文件(INDEX/账本类),批内追加后随本批立即 commit,不在工作树跨批滞留(并发窗内整文件提交易卷入他批未提交行);编辑撞「file changed since read」竞争 = 放弃重试硬写,搭车下一笔提交。
  3. **双仓提交序**:主仓+子仓双仓批(如主仓+测试仓),提交序=子仓逐文件点名 commit → 主仓(gitlink+文件);子仓工作树未 commit 时禁 add 子仓路径——gitlink 会指向不存在的子仓提交,他人检出即断链。
  4. **交付哈希不可变**:交付 commit 上报哈希后禁 amend——追加范围一律第二 commit 并上报新哈希;reviewer 验收以最新申报哈希为基线。
  5. **分段提交禁裸树**:长批按阶段逐段 add+commit——全部改动攒到批末裸在工作树,中断或他批操作时零保护。
  6. **测试收集门**:批量写/改测试文件后 commit 前 `pytest --co -q` 收集一次——语法损坏的测试文件进树 = 全量收集崩,所有批的测试全红。
  7. **禁 `git clean -x/-xdf` 类命令**:gitignore 覆盖的运行时资源(模型等)会被连删且 git 恢复不了。
  8. **剥 hunk/私有笔收尾 reset**:部分暂存(剥 hunk)提交完跑 `git reset` 对齐 HEAD——index 残留旧 blob,下次裸 commit 即复活已删内容;此类提交落库后跑受影响模块 import 验证(落库树态 ≠ 工作树态,工作树绿证明不了 HEAD 好)。
  9. **脚本化批量提交的解析纪律**:解析 `git status --short` 的脚本按全形态写用例(M/R/D/改名行各一)——改名行是 `R  旧 -> 新` 形态,按单一 M 行形态写解析器会解析出伪路径且 `git add` 静默失败;add 后 `git diff --cached --name-only` 复核实际收信面 = 预期集;git 命令错误禁 `2>$null` 类静默吞;关键文件落库后跑 fresh 视角核验(`git ls-tree -r HEAD` 查关键文件在树)——工作树视角的验证发现不了「提交内容缺失」。
- **工件移交双侧声明**(跨批/跨 worker 移交临时工件时):移交裁决同时给**产出方与接收方**的任务书写明「这些文件是移交物,禁清理」,或移交即由接收方复制/挪位到自己的命名空间——`.debug/temp` 类「临时物可清理」的默认纪律与「工件移交」语义冲突时,以显式声明为准;只对产出方说「交付后撤出」会被理解成「回报路径后按临时物清理」,接收方到手空路径(实证:7 件移交工件全被产出方收尾删光)。
- **任务书序列**(按迭代流程顺序派发;模板完整给出——含任务书本体,不只尾段;逐字复制只填 `<角括号>` 实例位,禁精简改写——模板靠派单必达,不靠子 agent 自觉或会话记忆):
  1. **① 设计批**(迭代开始即派)——产出设计文档与 landing.md;
  2. **② 设计对抗批**(①交付后即派)——无前提攻击,产出攻击报告;
  —— **②收敛即定稿,先立阶段任务再派落地批**(编排者的记账动作,不是派单):照 landing.md
     阶段小节逐个 `dag.py add`(criteria 预注册指向该小节,优先级用小节建议值,依赖按小节)
     ——任务进 ready 队列后与其它任务同规则竞争槽位;worktree 迭代此处同时
     `tools/wt.ps1 new <change-id>` 建树,阶段任务逐个带 `--worktree wt/<change-id>`;
  3. **③ 落地批**(立阶段任务后,landing.md 每阶段一张;固定末阶段=正本更新)——每张交付后派 reviewer,附验收批任务书。
  4. **④ 合并者**(worktree 任务验收 accept 进 `pending_merge` 泊位后即派;全局单例,取活=泊位段)——把批分支并进集成分支、出合并报告;附合并者任务书。
- **① 设计批任务书**(完整模板;设计批的规范符合性、依据标注、试读由对抗审卡——它是「回答后」对抗档 2 的对象):

  ```markdown
  # 任务书:迭代设计批

  【干什么】完成本迭代全部设计文档——design.md(总纲)+details/ 详设(按需)+
    landing.md(落地阶段拆分与验收;固定末阶段=正本更新)
  【迭代目录】<模块设计区>/changes/ 下新建,命名=<日期>-<主题>(主题词你定);
    回信必须报出目录名——②③批次与账本 note 都引用它
  【规范】docs/develop/harness/iteration-design.md——按其模板与写作硬规则起稿
  【迭代目标】<目标全文>
  【输入材料】<判据源路径清单:玩法文档/注册表/相关正本/上迭代遗留>
  【文件面】仅限上述新建目录,不动其他任何文件
  【开工令】开工前先查相关 skill 与文档,通读后再动工
  【交付与记账(固定契约,完工时逐条执行)】
  1. 提交迭代目录:逐文件点名 git add(仅限本迭代新建目录内的文件);commit 前
     `git diff --cached --name-only` 核对暂存面=本批新建目录,面外文件(他批暂存)先
     `git restore --staged <文件>` 退出再 commit,
     message 含迭代名;只 commit 不 push(设计期无隔离树,提交安全靠「文件面=本迭代
     新目录、与他人零重叠」;改动一处既有文件即越界);交付 commit 上报哈希后禁 amend,
     追加范围一律第二 commit 并上报新哈希
  2. 完成报告写入 <报告路径>,结构五节:①结论 ②完成判据对照表(判据/结果/凭据指针)
     ③变更面(commit hash+文档清单+迭代目录名) ④验证记录(对照规范逐节自查结果)
     ⑤偏差与未尽事项(新问题给立项建议)
  3. 完工自登记(交付落盘后立即执行,禁延后到批收尾——会话中断时「已交付未记账」= 下个会话重复派工):dag.py --file <账本路径> status <任务id> pending_review --criteria <报告路径>
  4. 给编排者的最终消息 ≤10 行=结论摘要+迭代目录名+报告路径,正文进报告不进消息
  没跑第 3 步=任务没有交付,账本不认。
  ```
- **② 设计对抗批任务书**(完整模板;不立账本任务,产出由编排者消费):

  ```markdown
  # 任务书:<迭代名> 设计对抗

  【干什么】对 <迭代名> 全部设计文档与 landing.md 做对抗审,三核并重——无前提攻击
    (假设有错、设法证明)/规范遵循(对照已制定规范逐项核)/治本核验(根源两问)
  【攻击对象】<①回信报出的迭代目录> 下全部设计文档与 landing.md;先通读再攻
  【判据源】<权威源路径清单(含 iteration-design.md 写作硬规则)>;直调文件与原文,禁凭转述
  【产出】<攻击报告路径=.debug/change-reviews/<迭代名>/attack-r<K>.md>:问题清单
    (册+节+严重级+发作场景)+攻过未破角度清单;报告不入 git(本机过程档案,多轮=多个 r<K> 文件)
  【无前提攻击】不需要看之前的攻击报告与修改记录,直接从设计文档本身出发找问题
  【文件面】只读攻击对象与判据源;只写攻击报告(全在 .debug 面,主仓工作树零写入)
  【开工令】开工前先查相关 skill 与文档,通读后再动工
  【回信】≤10 行=发现计数+阻断摘要+报告路径(零实质发现=合法结论,如实申报)
  不立账本任务、不写账本流转;结论由编排者消费。
  ```
- **对抗轮次独立性**:修复核验与新一轮对抗是两个工作,禁混在一起——上一轮问题的修复质量由编排者亲验(或另派独立检查批)核;**下一轮对抗永远干净上下文**:不带上一轮问题清单、无历史提示,送审工件剥掉轮次痕迹(「经 R<K> 修订」类标注)——攻击者带着旧发现清单会锚定旧区域逐条核对,全新攻击面无人看。
- **③ 落地批任务书**(完整模板;landing.md 每阶段一张,固定末阶段=正本更新;任务书只给指针——阶段内容单一源在 landing.md,不照抄):

  ```markdown
  # 任务书:<迭代名> 落地·<阶段名>

  【你的阶段】<landing.md 路径> 的「<阶段名>」小节——范围/设计依据/文件面/完成判据
    以该小节为准,先通读再动手
  【工作区】<编排者建树后填:主仓树绝对路径 + 分支 wt/<迭代名>;测试树=该树内 sr-od-test/;
    无隔离树的批填「主仓」>
  【工作区纪律】会话 cwd 恒为主工作区:树内命令先定位到本树(cd 进树执行,或 git -C <树路径>),
    文件读写用树内绝对路径——裸命令落在主仓=隔离失效。测试改动在测试仓那层提交
    (git -C <本树>\sr-od-test add/commit)。树内禁 git add sr-od-test(主仓只认 gitlink 指针,
    在主仓 add 它=夹带无关指针变动)、禁 git clean(会删掉树内 .debug 遥测)。交付前自查:
    本批提交必须出现在 git -C <本树> log 里(不在=干错地方了)
  【开工令】开工前先查相关 skill 与文档,通读后再动工
  【交付与记账(固定契约,完工时逐条执行)】
  1. 提交改动:逐文件点名 git add(仅限文件面内文件,禁 add -A/目录级);commit 前
     `git diff --cached --name-only` 核对暂存面=文件面,面外文件(他批暂存)先
     `git restore --staged <文件>` 退出;双仓批先子仓逐文件 commit 再主仓;在所在仓库
     commit——message 含任务 id 与阶段名;只 commit 不 push;交付 commit 上报哈希后禁
     amend——追加范围一律第二 commit 并上报新哈希
  2. 完成报告写入 <报告路径>,结构五节:①结论 ②完成判据对照表(判据/结果/凭据指针)
     ③变更面(commit hash+逐文件清单) ④验证记录(可复制执行的命令+耗时+结果摘录,
     对比数字带符号定义/n/误差范围) ⑤偏差与未尽事项(新问题给立项建议)
  3. 完工自登记(交付落盘后立即执行,禁延后到批收尾——会话中断时「已交付未记账」= 下个会话重复派工):dag.py --file <账本路径> status <任务id> pending_review --criteria <报告路径>
  4. 给编排者的最终消息 ≤10 行=结论摘要+commit hash+报告路径,正文进报告不进消息
  没跑第 3 步=任务没有交付,账本不认。
  实现中发现阶段内容与代码现实矛盾:停手,经编排者回该阶段「设计依据」提请修订,禁自行改设计意图。
  ```
- **验收批任务书**(完整模板;③每张落地批交付后派 reviewer 时使用;每次验收=全新 reviewer agent,禁复用之前的 reviewer):

  ```markdown
  # 任务书:<迭代名> 落地·<阶段名> 验收

  【干什么】对 <阶段名> 交付做验收,出 accept/reject 结论
  【输入只有两份】本任务书+交付报告=<交付报告路径>——先通读这两份再动工,
    交付正文之外不找编排者要上下文;通读=全文——判「某节是否覆盖」类覆盖性结论须全文检索
    确认,抽段读仅供质量抽验(部分读+强判据=误判「未闭合」发催办的实证在案)
  【工作区】<与落地批同一棵树:主仓树绝对路径 + 分支 wt/<迭代名>;无隔离树的批填「主仓」>
    ——亲跑必须先定位到本树(cd 进树执行,或 git -C <树路径>);会话 cwd 恒为主工作区,不定位就跑错地方
  【验收】照 <landing.md 路径> 的「<阶段名>」小节「完成判据」逐条核:
  1. 判据对照:逐条判 过/不过/偏差,偏差必须裁决不默许;对比数字没有符号定义/n/误差 = 不过
  2. 亲跑:判据里的验证命令本人跑过,测试断言本人读过,本人耗时与报告 §4 差 3 倍以上 = 打回
     ——报告说绿不算绿;亲跑遇红时,若工作树存在并行在飞写入面:①单跑复现判瞬态/稳定,
     ②对比跑点与并行批写入时间线——单跑绿且时间线吻合 = 瞬态红(并行批写入窗),归因并行批,
     不作为打回依据(伪红归因成「断言写反」的误打回实证在案)
  3. 边界:git show 逐 commit 对照报告 §3 清单与 landing.md 该阶段「文件面」——没夹带、没少交;
     报告 §3 的哈希在树里查不到时,先核账本卡/任务书注记是否申报了新哈希(交付后追加范围=第二 commit),以新哈希为准
  4. 同步:代码/文档/测试三处一致;bug 修复查同类(同类还有吗)
  5. 规范符合性零容差:方案/实现与设计规范(架构文档/ADR/设计定稿)任何一点不符合即打回,
     不设「轻微/可接受」裁量——裁量权在规范制定方,不在 reviewer
  【产出】<结论路径=.debug/change-reviews/<迭代名>/T-<N>-r<K>.md>:逐条核验+结论(accept/reject)
    +打回要点(逐条可执行)+新问题立项建议
  【记账】accept → worktree 任务:`status <任务id> pending_merge`(进合并泊位,由合并者以
    合并报告收敛 done);无 worktree 任务:`status <任务id> done --criteria <结论路径>`;
    reject → `status <任务id> rejected --why <结论路径>`
    (登记打回泊位;返工派工归编排者)
  【回信】≤10 行=结论行(accept/reject+一句话理由+偏差与新问题条数)+结论文件路径
  结论只看证据,不看论证说服力。
  ```
- **④ 合并者任务书**(完整模板;③每张落地批验收 accept 进 `pending_merge` 后即派;全局至多一个合并者):

  ```markdown
  # 任务书:<迭代名> 合并·<任务id>

  【干什么】把已验收的批分支并进集成分支,出合并报告。合并者只做合并与集成验收,不做代码 review
  【输入】任务id + 分支名(账本 `card <任务id>` 的 worktree 字段)+ 交付报告 <交付报告路径>
    + 验收结论 <结论路径>;批树 = <主仓树绝对路径>
  【流程(逐步;任一步失败即停,并按失败路由处置,禁跳步禁重试掩盖)】
  1. 干净检查:`tools/wt.ps1 check <迭代名>`——两仓(主仓树、测试树)存在未提交/未跟踪项
     = 打回(禁代提交、禁自行清理现场)
  2. 重放:`tools/wt.ps1 rebase <迭代名>`——把集成分支最新重放到批分支;冲突 = 打回
     (报告里附冲突文件清单原文)
  3. 全量测试:先定位到批树(`cd <批树绝对路径>`)再跑 `uv run pytest sr-od-test/`(串行、含慢桶、
     不过滤;会话 cwd 恒为主工作区,不切目录测的是主仓旧代码)
  4. 红的用例逐条分诊:非本批引起(改动面之外的老红)= 记入合并报告、本批照常合并,
     修复由编排者另立任务;本批引起 = 打回(附失败用例与出处)
  5. 全绿 → `tools/wt.ps1 land <迭代名>`(两仓 ff-only 并入集成分支,禁产生合并提交)
     + 树内 `.debug` 新增内容 move 回主仓对应路径(重名报错,禁覆盖)
  6. change 收敛(该 change 名下再无未终态任务)后 `tools/wt.ps1 remove <迭代名>` 清场
  【记账】合并成功 → `dag.py --file <账本路径> status <任务id> done --criteria <合并报告路径>`;
    打回 → `status <任务id> rejected --why <合并报告路径>`(返工派工归编排者;worker 返工先在
    自己树里 rebase 集成分支最新再修,修完从流程第 1 步重走)
  【产出】<合并报告路径=.debug/change-reviews/<迭代名>/merge-<任务id>.md>:逐步执行记录
    + 全量测试结果摘录 + 红用例分诊结论(本批/非本批逐条)+ 集成分支前后 commit hash
    + 遥测抢救清单
  【硬约束】只 commit 不 push;主工作区集成分支被存量未提交改动挡住 ff 时,记录「受阻:文件面
    相交」留待重试,禁硬来(禁 stash / reset / 强行 checkout 主工作区)
  【回信】≤10 行=结论(合并成功/打回+一句话理由)+ 集成分支新 commit hash + 报告路径
  ```
- **模板外通用**(参谋/判读复盘等决策支持批;设计对抗已由②覆盖):无固定契约段——照三带写,再加三条通用规则:
  1. 产物落盘到指定路径,回信 ≤10 行 = 结论+路径(正文不进会话);
  2. 不立账本任务、不写账本流转——产出由编排者消费,该立的账本任务由编排者按裁决登记。
  3. **循环型审查/处方的产物文件名只增不覆**:用时间戳/轮次文件名(空轮也追加一行而非覆写)——固定文件名会被后一轮覆写,前轮处方原文丢失不可考。

### 3.2 等待时——盯什么、做什么

- **盯活性,用产物 mtime**:子 agent 的活性判据=产物 mtime(报告/代码/脚本/json 任一在更新),不是进程注册表状态(running 不等于在干活)。子 agent 状态清单的「运行中」同理(回合卡死也显示运行中);「空闲」则相反=没在干活,此时发消息立刻开新一轮(与运行中不同,不存在送达延迟)。
- **探询的局限**:发往子 agent 的消息排在它的下一 turn——**运行中**的子 agent 单 turn 不结束就永远不送达,对「turn 内卡死」无效;发探询≠已处置。**空闲**的子 agent 例外:消息直接开启新一轮,送达无延迟。
- **硬干预线**:产物停滞 ≥20 分钟 → 直接 interrupt,不必先探询(消息排在回合后,白等;消息随中断送达,上下文保留可续);中断时要求=「立即停止在跑命令+禁跑新验证+交付已有产物与未完成清单」——已落盘的 diff 足够对账与决定再派,缺的验证由再派批补跑,比干等任何时长都快。「树在动」辩护只对新的 mtime 有效,mtime 停止后重新计时。**停滞判定用产物 mtime 时,对照任务书声明的「文件面」逐个查,禁凭猜测的落点抽查**(实施批的真实落点不在抽查的几个文件内,曾被误判零推进而中断——派单时把声明文件面存档备查)。**写作/设计型任务的中断阈值可放宽**至 30-40min 或以其自然交付时长为准(零产物主因=读料期超预期,非卡死);对写作型的中断指令固定=「禁再读料,立即落笔已 gather 的材料」。
- **等待不闲着**:观测≠产出,连续多个纯观测动作=漂移信号;等待间隙做并行产出(对照分析/读文档),让「等运行」变成并行任务的一个分支而非全部。
- **防退化自查**(等待时的自检表):

| 退化形态 | 信号 | 自救 |
|---|---|---|
| 认知窄化 | 注意力全在进行中的任务/最新刺激 | 连续两轮同答=换源深扫;等结果>10min 自问「找问题还是等结果」 |
| 目标漂移 | 优化末端变量/明知无信息量还让任务跑完 | 当期目标行判据起数钉住主线(起数不随任务完成翻);无信息量的运行不陪它跑完(何时停的判据由领域 skill 定义) |
| 账本过期 | 账本状态与实际进度对不上 | 漏记的状态变更当场补上 |

### 3.3 回答后——验收路由与治本反思

- **交付到达的处置序列**(编排者,全程不读交付正文):
  1. **对账(机械)**:报告文件存在?任务 id 对上?——任一不过=交付格式不合格,打回重交;
  2. **派 reviewer**(交付验收子 agent;标准任务书=验收批模板,只填实例位:阶段名/landing.md 路径/交付报告路径/结论路径/账本路径/任务 id);
  3. **按结论行处置**:accept(worktree 任务已进 `pending_merge` 泊位 → 派合并者批;无 worktree 任务 reviewer 已自闭环 done → 空槽立刻取下一件);reject(reviewer 已自闭环 rejected,阶段进打回泊位)→排到返工时编排者 `rejected→doing --assignee <返工者名>` 派出——原 worker 还活着→send_message 三指针续派(任务书/交付报告/验收结论),没了→spawn 新工,同样三指针;
  4. **消化未尽事项**:按结论行里的新问题计数,当场 `dag.py add` 立项或写明不立缘由(账本外不许藏活任务)。
- **发起权铁律**:一切子 agent(worker/reviewer/对抗审/参谋等,返工=worker 的再指派)都由编排者发起;worker 与 reviewer 只对自己的工作+记账负责,永不 spawn、永不相互委派(独立性/会话树归属/审查时机/槽位预算——违反任何一条都会绕开编排者的路由与限流)。
- **每批交付由 reviewer 验收**(交付验收子 agent,干净上下文、独立于本批实现者;验收清单=验收批任务书模板的【验收】四条——判据对照/亲跑/边界/同步,唯一源在模板,此处不复述。能审就审:交付到达即派,无节奏选择)。**每次验收都必须是全新的 reviewer agent**——禁续用/续聊之前的 reviewer(含 send_message 续派与同 agent 再审):重新验收=重新 spawn,独立判断不继承前轮结论;返工后的复审同理,照样新派。

- **reviewer 产出**:结论文件 `.debug/change-reviews/<迭代名>/T-<N>-r<K>.md`(逐条核验+结论+打回要点+新问题立项建议)+ ≤10 行结论行(accept/reject+理由+偏差与新问题条数);记账:accept → worktree 任务自登记 `pending_merge`(进合并泊位,由合并者以合并报告收敛 done)、无 worktree 任务 `done --criteria <结论路径>`(自闭环);reject → 自登记 `status <任务id> rejected --why <结论路径>`(打回泊位;返工派工 doing 归编排者)。
