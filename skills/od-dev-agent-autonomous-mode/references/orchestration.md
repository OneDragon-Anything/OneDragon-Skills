# 编排者手册(运行期)

> 读者 = 编排者(主会话)。开启 checklist 确认额度 ≥2、进入编排者模式后读本手册;额度 =1(亲力亲为降级)同样适用其中不依赖子 agent 的条款(盘点/入口消费/防退化)。运行中记不清纪律 → 重读本文件对应节。

## 1. 编排者是什么(身份与责任)

- **主会话=编排者(orchestrator),兼任交付审查(review)**:判读/定规格/派单/审查交付/裁决/记档。实现与分析(码+测试+模拟+文档,不限类型)派子 agent 干净上下文推进。
- **额度两档**:额度=主会话+子 agent 总会话数,子 agent 槽=额度−1(主会话占 1)。**额度 ≥2 = 编排者-子 agent 模式**(本手册适用);**额度 =1 = 亲力亲为降级**(主会话独干全部件;对抗审查仍应偶尔派——独立性价值不随额度消失,可用限时单件形式);子 agent 启动连崩 2-3 次=平台不稳,临时降级亲力亲为并记档。
- **派还是不派,一条判据**:实现与分析(码+测试+模拟+文档,不限类型)派子 agent;以下亲自做——①需要跨批全局上下文或代表用户责任的:与用户对话 / 交付验收(委派验收=没人验收)/ 进度记账 / 转述对比数字前的口径核验(符号定义/n/噪声底);②需要独占现场、当场判断的操作与事故处置(具体范围由领域定义;禁「先跑起来」临时补丁,治本当场做完);③单点、一次编辑能改对、不需跑验证的小件(改常量/typo/日志行——判断线=要不要跑验证或多步,要=派)。理由:长会话主会话易偏离目标、陷入局部问题(实证:验收完一批后空转/连续十几轮读日志报平安)——**结构性约束(主会话少做事)比自觉可靠**;动机是防编排职责空转,不是禁碰代码。

## 2. 派发节奏(与进度文件的关系)

> **进度文件是派发的唯一队列源**——未完成任务从进度文件了解,别靠会话记忆。账本的结构、如何检索未完成内容:见 od-dev-progress-tracking(§2 结构 / §8 恢复用 grep 未完成集,只扫 `进度.md`;行经 progress.py write 写入)。

- **事件驱动,不用定时轮**:子 agent 交付/后台任务退出/用户消息都是推送唤醒;定时轮在没新事件时=空转轮,有事件时=重复。提醒网(reminder-net.md)管「没人戳你时别忘了看什么」,不管派发。
- **形态 B 盘点候选的消费**(环境以定时直启子 agent 方式建盘点时):找活候选单到达=推送唤醒事件,与子 agent 交付同级处置——逐条裁决:可派的当场派(派单三带);缓派/不派的逐条写明原因并记回进度账本,禁只回「收到」。候选由无记忆子 agent 产出,与在飞批的冲突由编排者裁决时过滤(细则=reminder-net.md「触发形态与选择规则」)。
- **完成一件,立即取下一件派发**:子 agent 完成→验收采纳后立即取进度文件里的下一个待派任务派发,不等下一轮想起来——绑确定性事件,不依赖「记得」;派发时随手更新进度文件。
- **盘点必须重新实扫**(等待间隙找活的动作):候选件只从当轮对最新代码/文档/进度文件的实际扫描里找——打开文件、执行搜索,以当轮读到的内容作答。禁止凭记忆报告各来源状态:上一轮的结论、会话里记得的待办情况,一律不作为本轮盘点的依据;要产出「零候选」,必须当轮重新看过这些来源才能下结论(代码和文档随时在变,「跟之前一样」不是看过的证据)。自查一句话:若此刻被问「你真的去找过了吗」,每个来源当轮的搜索路径和命中能当场报出来吗?不能 = 没扫。
- **候选件从多个不同性质的来源扫**(「下一个待派」空了或被阻塞 ≠ 没有事可派):按下表逐类扫;单一来源扫不出活时换性质不同的来源,防视野收窄。领域特有的来源(校准/判读类)见领域 skill。

  | 来源 | 扫什么 |
  |---|---|
  | 代码内债 | TODO/FIXME/「未验证」注释;标注过「临时绕行+排期根治」的补丁——排期到了没 |
  | 注释缺口 | 复杂逻辑缺「为什么」注释;索引/槽位字段缺定义注释(坐标系+取值时机);依赖先验的修复没写依据 |
  | 文档同步 | 代码已变、文档/ADR/注释没跟的三同步欠账;as-built 文档里混进的状态叙事 |
  | 测试债 | 没测试锁住的关键行为;锁住旧行为副作用的断言;没过变异探针的新检查 |
  | 算法效率 | 上一操作结束 → 感知 → 决策 → 下一操作执行的全链延迟,**慢到使用者看自动化卡顿 = 立项信号**;先计时定位热点(派单三带第 4 带),量级内的固有耗时不立项 |
  | 测试等待 | 开发过程每次花大量时间等测试/批量验证跑完——高频等待的环节分档(快速集/全量)、慢环节单独提速 |
  | 重复手工 | 每次重复手敲的命令序列/固定多步操作——出现第二次即信号:该脚本化/工具化 |
  | 重构 | 重复复制的判据逻辑(该抽单源);表示与语义错位的约定层补丁;过长函数 |
  | 临时件清理 | 采集钩子样本攒够了没处理(判读→建档→删钩子);临时目录躺久的工具脚本(版本化或删) |
  | 数据缺口 | 校准数据没覆盖的桶;没消化的积压素材/报告;到了复核条件没复核的观察项 |
  | 知识回路 | 踩的坑没进防坑清单/skill 反馈;教训只留在对话里;进度记录卫生回弹(叙事又堆进来) |
- **连续两轮同答=视野收窄信号**:盘点连续两轮产出相同「无件可派」,强制换一个来源深扫(深扫=当轮真打开该来源的文件/真执行搜索,按读到的内容更新结论,不是换个说法复述旧答案)。
- **零候选升级换眼睛**:盘点当轮结论为零候选(非额度满)且有空槽 → 派一个干净上下文的找活子 agent(任务书=当前自主推进目标+进度入口,运行时从指令文件字段抄;候选带出处与理由)——盘点实扫与回顾换地复核都还是同一会话上下文的眼睛,连续零候选时换上下文重扫(reminder-net.md「三重保险设计」);子 agent 只产候选,派不派仍由编排者裁决。(本条适用形态 A;形态 B 的周期找活盘点本身就是独立上下文,其零候选即独立结论,不再二次升级——reminder-net.md「触发形态与选择规则」。)
- **进度对表**:验收/派发时随手更新进度文件(事件驱动);埋头推进数小时后进度文件停在几小时前=典型失效,发现不同步**当场改文件**(进度对表提醒兜底)。

## 3. 委派三拍(时间轴)

### 3.1 派出时——任务书怎么写

- **派单三带**(缺一=不合格派单):
  1. 任务书必含「**开工前先查相关 skill 与文档,通读后再动工**」(子 agent 干净上下文,但项目约定本就该在 AGENTS.md/skill/单一源地图里可发现——**别替它挑选文档清单**:主会话上下文不干净,挑选会传入偏见;约定不可发现=修项目入口,不是派单兜底);
  2. **凡产出为结论/分档/取舍的任务**(评审、评估、方案选型类),任务书必须约定结论的合格线——论断、证据、推理链三件齐(每个结论答得出「凭什么这个证据支撑这个论断」;参照图尔敏论证模型);证据分强弱,结论强度取最弱一环;频次统计回答「有多少」,回答不了「好不好」——跨这道沟必须补上并验证连接两者的推理(流行可能只是模仿传播/幸者偏差/混杂因素),故频次单独不构成评价性结论;
  3. **「文件面」声明**(本批动哪些文件,与其他进行中的批互斥,防撞)。
- **长批(预计 ≥40min,如批量验证/全量测试)加第 4 带:检查点交付+效率预检**——设计报告/中间产物落盘=先汇报再继续;**预计 ≥10min 的计算类任务,任务书带「先 profile 单点」指令**(计时单 seed/单用例,>5s 先优化再跑批量);子 agent 汇报「跑了很久才完成」时,第一反应=计时复现而非归因环境/体谅。

### 3.2 等待时——盯什么、做什么

- **盯活性,用产物 mtime**:子 agent 的活性判据=产物 mtime(报告/代码/脚本/json 任一在更新),不是进程注册表状态(running 不等于在干活)。子 agent 状态清单的「运行中」同理(回合卡死也显示运行中);「空闲」则相反=没在干活,此时发消息立刻开新一轮(与运行中不同,不存在送达延迟)。
- **探询的局限**:发往子 agent 的消息排在它的下一 turn——**运行中**的子 agent 单 turn 不结束就永远不送达,对「turn 内卡死」无效;发探询≠已处置。**空闲**的子 agent 例外:消息直接开启新一轮,送达无延迟。
- **硬干预线**:产物停滞 ≥20 分钟 → 直接 interrupt,不必先探询(消息排在回合后,白等;消息随中断送达,上下文保留可续);中断时要求=「立即停止在跑命令+禁跑新验证+交付已有产物与未完成清单」——已落盘的 diff 足够编排者亲验收账,缺的验证编排者自己跑,比干等任何时长都快。「树在动」辩护只对新的 mtime 有效,mtime 停止后重新计时。
- **等待不闲着**:观测≠产出,连续多个纯观测动作=漂移信号;等待间隙做并行产出(盘点/对照分析/审查),让「等运行」变成并行任务的一个分支而非全部。
- **防退化自查**(等待/盘点时的自检表):

| 退化形态 | 信号 | 自救 |
|---|---|---|
| 确认循环 | 盘点连续 N 轮「无需派」 | 四来源强制扫描+辩护带清单 |
| 认知窄化 | 注意力全在进行中的任务/最新刺激 | 连续两轮同答=换源深扫;等结果>10min 自问「找问题还是等结果」 |
| rubber-stamp | 审查只转发子 agent 数字 | 亲跑复现+行号抽查,转述前核三件套 |
| 目标漂移 | 优化末端变量/明知无信息量还让任务跑完 | 当期目标行判据起数钉住主线(起数不随任务完成翻);无信息量的运行不陪它跑完(何时停的判据由领域 skill 定义) |
| 资产腐化 | 清单/表与实况不符 | 进度对表发现不同步当场改文件 |

### 3.3 回答后——验收与治本反思

- **每批交付必亲验**(通用验收五面;领域条目在领域 skill 的交付验收节加厚):

| 核对面 | 判据 |
|---|---|
| 测试数字亲跑 | 按子 agent 声明的验证层级复现,"声称绿"不算 |
| 改动边界 | `git diff` 对照任务书声明文件集——越界文件逐个判「相关 or 混入」 |
| 数字三件套 | 凡转述对比数字:符号定义/n/误差范围;n<100 或噪声带内禁方向叙述 |
| 断言抽查 | 报告里的行号/文件断言抽查源码——子 agent 论断=可推翻假设 |
| 偏差裁决 | 报告声明的偏差逐条裁决(接受/打回),不默许 |

- **审查节奏**:有依赖的批立即审(解锁下游)/无依赖并行批可攒批合审/事故现场永远立即;**跨模块/大批量的改动 commit 后,默认再回头审一轮这批 commit**(改动间联动是否正确/有无引入回归/配套文档与测试锁是否跟上——它是后续所有批的新地基,刚落地时审最便宜);审查队列>2 或下游被卡=停派先清(rubber-stamp 比不审更糟)。
- **重要结论采信前对抗,按「采信错了的代价」分三档**(在「准备采信」那一刻做;总判据:**对抗强度与采信错了的代价成正比**——产物越重大、越难回退,对抗越多路、越早开始、越贯穿全程;攻击者一律用干净上下文,每条攻击落到可查证据;**裁决只看证据与实测效果,不看论证说服力、不看支持票数**):
  - **档 1 · 单点结论**(分析/归因/方案):
    - 什么时候做:结论已准备采信并拿去指导后续(派批/改代码/呈报)——错了后续会白干一大片;或岔路口多方案均自洽、拿不准选哪个。
    - 怎么做:派一个干净上下文子 agent,指令=「设法推翻这个结论」,附结论原文+它依据的证据面(文件/数据/提交),要求每条攻击引具体证据。
    - 什么时候不做:客观事实核验(测试结果/代码行内容——亲跑亲看即可,归交付验收);影响面小的改动(错了低成本回滚,对抗成本>收益)。
    - 为什么钉在采信前:结论被采信后会成为后续所有决策的地基,基于它做的事越多,推翻它的代价越大;「准备信」那一秒推翻它,代价只是重看一眼报告(对抗的价值随结论被采信的时间衰减,落地即发起,不等周期巡检)。
  - **档 2 · 设计稿与成批实施**(一份设计要指导多批实施):
    - 设计稿动工前先过一路独立攻击;每条反对意见必须落到具体位置(文件:行),不接受泛泛质疑。
    - 每轮修订后,下一轮攻击的**第一步是逐条复核上一轮问题的修复质量**,三选一判定:真解决/表面绕过/修复引入新问题。
    - 攻击方提不出新的实质问题(剩余意见不影响结论)才允许开始实施。
    - 实施期间**每一批都有一路攻击并行**——一批写到一半被推翻是正常且便宜的;「全部写完再统一审查」是禁手,那时推翻的代价是整批返工。
  - **档 3 · 重大方向选型**(架构/算法方向,错了代价大或难回退):
    - 不让单一作者论证到底:并行产出多路互相竞争的独立方案,然后互相攻击,再加无锚攻击(不预设任何立场,专找每个方案最薄弱处)。
    - 选型依据:**在各方案自己的证据支撑范围内,比较可达成效果的上限**——上限必须有证据链(实测数据或可推算),不靠修辞。
    - 竞争的常见产物是「删」:整体去掉某个部件比修补更优的结论,价值不低于选出赢家。
  - 通用纪律:独立性来自新鲜上下文而非换模型(默认继承主力路由即可);采信前的证据指针抽查不可省;对抗后仍无把握且影响面大=问用户。

## 4. 最近改动三审(已提交改动的事后兜底)

触发模板在 reminder-net.md(形态 A 提醒编排者 / 形态 B 直启子 agent,只启用其一)。本节是编排者侧的裁决细则:

- **审集口径**:固定回看窗口=调度间隔(默认 45 分钟),与水位文件机制二选一——固定窗口零维护,水位文件精准但只有编排者能设(子 agent 任务书禁带水位读写)。
- **豁免**:纯机械面(类型注解/导入/日志文案/纯注释)不触发三审,既有交付验收够用;豁免清单在裁决时留痕备查。
- **裁决纪律**:成立发现逐条记账派修;不成立发现也要记一行为什么不成立——「为安静而改」和「为省事不改」是同一个失职的两面。
- **测试面特殊闭环**:「可删/可并清单」必须编排者批准后才执行;删前跑全量测试证覆盖不降;套件规模的观察指标=快速集用时与用例数(持续只增不减=膨胀警报)。
- **与其他对抗的关系**:本角色是已提交改动的事后兜底;「采信前对抗」档 1 管采信前、修复双审的方案审管实现前——三道闸各守各的门,不互替也不重复。
