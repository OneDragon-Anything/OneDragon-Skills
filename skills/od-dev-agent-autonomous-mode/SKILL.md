# Agent 自主推进模式(通用框架)

> **术语约定(本 skill 全文)**:**收账**=审查子任务交付并采纳(验收动作,含亲验测试/边界核对;反面=只看报告就采信);**强制收账**=中断卡死的子任务后要求其交付已完成部分;**陪跑**=明知无信息量仍让任务跑完;**窄化**=连续多轮用同一视角找活导致视野收窄;**补位**=子任务完成后立即取下一个待派任务派发。

> 用户授权 agent 长时间自主决策、持续向目标推进、不逐项询问。本 skill 是运转框架:开启仪式 → 编排者(orchestrator)-worker 编排 → 派发/审查/治本三纪律 → 提醒网与资产组 → 防退化自校准。**核心哲学:结构性约束 > 自觉**——凡靠「记得」「自省」维持的纪律都会在长会话注意力衰减中失效,必须变成机制(清单格式/锁/提醒角色/代码化检查),让违规无法静默发生。

## ☐ 必做 checklist(没做完这 6 步不算开启完成;每步链后文 §)

1. ☐ **对齐三源状态**(§1):领域操作 skill → 进度树(运行状态单一源)→ 工作树核对,三方一致才继续;**并查专属任务的自主推进资产,有则按它实例化细项、无则按 §1 实例化规则自建**——**必做**
2. ☐ **开启仪式三件套**(§1):状态行更新(**改入口文件前过 `od-dev-writing-agent-instructions` checklist**) / 迭代入口建好(走 od-dev-progress-tracking §2.5 迭代启动 checklist) / 提醒网创建(时刻错开+间隔不同量级)——**必做**
3. ☐ **建/校准资产组**(§4):交付验收清单+点名册存在且匹配当前阶段——**必做**
4. ☐ **第一波派发**(§2):主会话=编排者(orchestrator),兼任交付审查(review);空 worker 槽(=额度−1,主会话占 1)按「关键路径件+独立性最高件」分发,派单带前置阅读——**必做**
5. ☐ **确认保留件边界**(§2):实机操作/事故现场处置/记档裁决/亲验/与用户对话归主会话——**必做**
6. ☐ **设早停判据**(§6):无信息量局/形态死局/修复待加载=停,禁止陪跑——**必做**

## 1. 冷启动序(对齐+仪式)

- **三源对齐顺序固定**:①领域操作 skill(怎么干)②进度树/任务状态文件(干到哪了)③`git status` 核工作树 vs 记录(有出入先查清——可能躺着并发会话或挂起批的改动,勿回退勿 stash)。判据:三方状态能互相印证。
- **实例化规则(骨架→血肉)**:本 skill 只给通用骨架;开启时先查专属任务有没有自定的自主推进资产(领域 skill 的自主推进入口/专属进度区的实例目录页/审查清单等)——**有则按它填充具体细项**(迭代入口的当期目标行与判据/提醒网落点/审查逐批节/哨兵脚本组/验证分层命令都是专属的);**没有则按本 skill 方法论自行思考构建**对应细项(建完即成为该任务的专属资产,后续会话复用)。判据:通用条款每一条都要能能回答「在这任务里它具体是什么/落在哪个文件」。
- **三件套**:①状态行(并行度/目标/授权范围)写入口文件;②迭代入口(工作状态三小节+当期目标行)建好(od-dev-progress-tracking §2.5 迭代启动 checklist);③提醒网(见 §5,创建时刻彼此错开+间隔取不同量级,防齐发信息稀释)。目标切换时更新②的当期目标行(§6)。**⚠️ 改入口文件(含状态行更新)前先过 `od-dev-writing-agent-instructions` 的 checklist**(判层/判层内归属/指令本体/纯度自检/改动流程)——自主模式会高频更新状态行,入口文件是常驻 token 成本,别越写越肥;方法论细节往本 skill 沉,入口文件只留状态与指针。
- **不用 goal 类定时轮工具**(事件驱动模式):worker 交付/哨兵 exit/用户消息都是推送唤醒;定时轮在没新事件时=空转轮,有事件时=重复。若环境只有定时轮,降级为心跳用。

## 2. 编排者(orchestrator)-worker 编排

- **主会话=编排者(orchestrator),兼任交付审查(review)**:判读/定规格/派单/审查交付/裁决/记档;实现与分析(码+测试+模拟+文档,不限类型)派 worker 干净上下文推进。理由:长会话主会话易偏离目标、陷入局部问题(实证:收账后空转/连续十几轮读日志报平安)——**结构性约束(主会话少做事)比自觉可靠**。
- **额度语义**:额度=主会话+子 agent 总会话数;用户保证并行度,agent 不预留缓冲不因担心超发减少派发,派就是了;启动失败连崩 2-3 次=平台不稳,降级单 worker 模式(主会话亲力亲为+1 个独立性最高的子 agent 做对抗审查)并记档。
- **派单三带**(缺一=不合格派单):①行为面批必带「前置阅读」节(领域权威文档路径——子 agent 干净上下文,文档在它世界里不存在,不带=凭猜乱来);②判定类批必带「判据来源」节(以效果/机制审查为主体,统计只作佐证——统计只是快一点的筛选,不是知识本体);③「文件面」声明(与其他在飞批互斥,防撞)。**长批(预计 ≥40min,如模拟批量/全量验证)加第 4 带:检查点交付+效率预检**——设计报告/中间产物落盘=先汇报再继续;**预计 ≥10min 的计算类任务,任务书带「先 profile 单点」指令**(计时单 seed/单用例,>5s 先优化再跑批量——自动化产品的慢是缺陷不是成本,判例:10min 预期的 A/B 跑了 90min,两轮卡死才被 profiling 暴露);worker 汇报「跑了很久才完成」时,编排者第一反应=计时复现而非归因环境/体谅。
- **在飞 worker 的活性监控与干预**(编排者的运行时责任;产物=唯一可信观察窗):
  - **活性判据=产物 mtime**(报告/代码/脚本/json 任一在更新),不是进程注册表状态(running 不等于在干活);
  - **探询消息的局限**:发往 worker 的消息排在它的**下一 turn**——单 turn 不结束就永远不送达,对「turn 内卡死」无效;发探询≠已处置;
  - **硬干预线**:产物停滞 ≥20 分钟**且**探询未获回应 → 直接 interrupt(消息随中断送达,上下文保留可续);强制收账指令=「立即停止在跑命令+禁跑新验证+交付已有产物与未完成清单」——已落盘的 diff 足够编排者亲验收账,缺的验证编排者自己跑,比干等任何时长都快;
  - **「树在动」辩护只对新的 mtime 有效**——mtime 停止后重新计时,不沿用上次观察结论。
- **进度记档 / 数字三件套核验**(凡转述对比数字:符号定义/n/噪声底) / 交付亲验 / 与用户对话。
- **主会话保留件边界**(需要跨批上下文或对用户纪律的感知):实机操作 / 实机事故现场处置与治本(实机单跑道,现场独占;禁「先跑起来」临时补丁,治本当场做完含采集/停机 hook)/ 上述记档核验亲验对话件。

## 3. 工作分类与三纪律(派发/审查/治本)

### 三类工作(普适关注框架——**定义归 od-dev-progress-tracking**,这里只列摘要+触发机制)

> **边界**:三类工作(主线任务/周期改进/持续运行)是任何推进模式都该关注的认知框架,完整定义在 progress-tracking §1;**本 skill 特有的是它们的机械化触发器**(指导模式靠人自觉,自主模式靠下面这套)。

| 类型 | 摘要(完整定义见 progress-tracking) | **自主模式的触发机制** |
|---|---|---|
| **主线** | 关键路径交付件,有终点有依赖 | **依赖驱动**:前件收账解锁后件,收账即补位(§3 派发纪律) |
| **周期改进** | 降低未来风险的洞察件,单个一次性/类周期性 | **周期扫描**:四来源盘点(15min)+大 commit 后默认 review+深度巡检(2h 派 agent) |
| **持续运行** | 无终点只有健康态的运转 | **健康监控**:值守兜底(10min)查,异常才介入 |

### 派发纪律(治等待窗产能塌缩——「在飞的链最显眼,空闲额度不可见」)
- **收账即补位**:worker 完成通知到达 → 审查+落库后**立即**取迭代入口主线小节的「下一个待派」补一件(§4 消费协议),不等下轮盘点——绑确定性事件,不依赖「记得」。
- **盘点=产出型(四来源扫描,周期改进的主要供给)**:每轮盘点必须从四来源扫出 ≥1 个候选件;真没有才许写「扫描了 A/B/C/D 来源,零候选」——**扫描痕迹留下,禁一句「无需派」**:
  - **来源A 挂账/哨兵噪声**:挂账项+历次报警被「已知形态」挡掉的(每个都是未消费的待验证事件);
  - **来源B 文档/卫生债**:进度文件超阈值归档/文档欠账/反馈队列新条目;
  - **来源C 效率损耗**:重复出现的等待或手工操作——判据:**同一等待第三次出现就该建批**;
  - **来源D 语料/数据缺口**:模型训练样本计数/采集钩子积压/数据缺口清单。
- **辩护带清单**:「全阻塞于在飞件」类辩护必须附**阻塞件名单**(列名)——列不出=无效辩护,立即回四来源扫。
- **连续两轮同答=窄化信号**:盘点/校准连续两轮产出相同「无件可派」,强制换一个来源深扫。
- **大批 commit 后默认动作=review 评估**(跨模块主批级);review 交付积压>2 → 停派新单先消化。

### 审查纪律(不因模式松懈)
- **每批交付必亲验**:测试数字亲跑复现(按 worker 声明的验证层)、行号断言抽查、数字三件套(**符号定义/n/噪声底**——n<100 或噪声带内禁方向叙述)、偏差逐条裁决。**worker 论断=可推翻假设**,转述前核原始口径。
- **审查节奏**:有依赖的批立即审(解锁下游)/无依赖并行批可攒批合审/事故现场永远立即;审查队列>2 或下游被卡=停派先清(rubber-stamp 比不审更糟)。
- **分层验证**:开发循环跑快速集 / 批次收尾加受影响域 / **全量只在 commit 前一次**(全量当每轮默认=纯等待损耗);每层耗时实测后写进交付验收清单的验证条款(层定义/命令/判据)。

### 治本纪律
- **≥3 次同型=框架级症状**:逐次消费是兜底,改判据才是治本(判例:静默报警单窗判据在某等待段必然误报→双窗确认)。
- **用户点破=泛化触发器**:具体问题=一类问题的样本——修单点外必派同类排查(把问题模式抽象成检查维度,系统性扫全部同类实例),必要时固化为 review 固定检查面。
- **建资产必建维护回路**:每次建新资产(清单/表/协议)问「它的维护回路是什么」——答不出就补(与「报告要有消费者」同构;判例:审查清单只有建版没有校准,漂了一夜)。
- **模拟先行,sim 盲区第一反应=治盲区**:能用模拟验证的不上实机;模拟不敏感的维度,第一反应是喂真值语料扩校准(把校准层逐步换成真机制),不是绕过盲区用实机试错。

## 4. 资产组(建+维护)

两类清单别混——**迭代入口主线小节管派发(下一个派什么),「交付验收清单」管收货(交付来了怎么核)**;先后关系=先验收(能不能收)→ 收了 → 扫入口主线小节(下一个派什么)。

### 迭代入口的消费协议(派发侧;入口结构归 od-dev-progress-tracking §2.5)

> **与 od-dev-progress-tracking 的边界**:入口的结构规范(三件套/工作状态三小节/状态记法/多迭代三层)归该 skill;**本 skill 只定义对入口的编排接口的消费协议**(触发器/补位/盘点/对表)。编排接口三件:①**主线小节的「下一个待派」**(全树唯一活动指针);②**当期目标行的判据起数**(目标进度,由判读评估更新);③**持续运行小节的健康线**。并行期旧进度文件分工由停用条件管(新制能独立回答「下一步派什么」→旧制降级为运行日志)。防偏离分工:progress-tracking 管文件层面跑偏(流水账/状态失真),本 skill 管行为层面跑偏(干等/窄化/陪跑,§5 行为校准)。

消费方式:
- **收账即补位**:worker 完成→收账后立即取主线小节的「下一个待派」派发,派发时随手更新入口;
- **判读后更新判据起数**:验证局判读结算时改当期目标行(如「起数 1/3」)——目标进度只在判读时动,不随任务完成翻;
- **周期改进/持续运行**:盘点扫描它们找活/查健康(触发器见 §3);
- **维护回路**:收账/派发/判读时随手更新(事件驱动)+**进度对表提醒**(45min)查偏移(含判据起数与实况一致吗)——埋头推进数小时后入口停在几小时前=典型失效,对表发现的不同步**当场改文件**。

### 交付验收清单(验收侧)

| 核对面 | 判据 |
|---|---|
| 测试数字亲跑 | 按 worker 声明的验证层级复现,"声称绿"不算;全量只在 commit 前一次 |
| 改动边界 | `git diff` 对照任务书声明文件集——越界文件逐个判「相关 or 混入」 |
| 数字三件套 | 凡转述对比数字:符号定义/n/误差范围;n<100 或噪声带内禁方向叙述 |
| 断言抽查 | 报告里的行号/文件断言抽查源码——worker 论断=可推翻假设 |
| 偏差裁决 | 报告声明的偏差逐条裁决(接受/打回),不默许 |

### 分层落位三问(资产内容放哪)

资产内容①换领域成立吗(通用性)②换协作者/协作模式成立吗(受众——个人工作台不进团队共享资产)③该进版本库吗(共享性)。个人流程编排权归个人入口文件,通过指针引用团队资产(领域 skill/docs)与实例资产(本地工作目录)——**个人层=驱动程序,团队层=数据,实例层=工作目录**。

## 5. 提醒网(schedule 角色集)

间隔彼此错开且量级不同(防齐发=信息稀释);**提醒放角色不放当期细节**(防过期误导),**不放状态查询**(状态走事件通道)。基础角色:

| 角色 | 间隔级 | 类型 | 盯什么→怎么查→答什么 |
|---|---|---|---|
| 值守兜底 | ~10min | **自执行** | 盯后台任务与运行环境是否健康。查:①长跑的程序(对局/构建/测试)还在推进吗——看它的输出文件更新时间,不是看进程在不在(进程活着≠在干活);②派出去的子任务(Worker)最近 20 分钟有产出文件更新吗——没有就发消息问;问了还没回应就中断它,要求「交出已完成的部分+列出没做完的」。答:每轮必执行,给出「健康/已干预」结论 |
| 派发盘点 | ~15min | **自执行** | 盯**「还有没有其他该做的事」**+**审查积压**(产能的专职提醒)。查:①待审的交付积压几件——**>2 件就停止派新单先清审查**(盖章式审查比不审更糟);②从四个来源扫候选件——A 挂账与报警记录(被「已知问题」挡掉没处理的);B 文档与卫生债(进度文件超长/反馈积压);C 重复劳动(同一等待或手工操作出现第 3 次);D 数据缺口(训练样本数/采集积压)。答:必须给出 ≥1 个**现在就能派**的候选件(不依赖任何在飞链)派出去;扫出的候选被阻塞时继续扫下一件——「暂缓一拍」不是盘点结果,槽由可派件填充,不等被阻塞件;实在没有,写下「扫了 A/B/C/D,各是什么状态」——禁止只回一句「无需派」 |
| 行为校准+产能质询 | ~40min | **自执行** | 盯自己的注意力与辩护质量(对「还有没有事」的二次兜底,与 15min 盘点形成双保险)。查四问:①刚才 10 分钟是在「找问题」还是「干等结果」(只有看状态没有产出=干等);②当前主线还在朝目标推进吗;③闲置的任务槽——**答案是一次发散搜索,不是一个理由**:先横向枚举「现在还有哪些不依赖在飞链的事可做」(四来源扫),搜出就派;「某任务在等 X」「暂缓一拍等下一事件」永远不是空槽的终止答案(任务会等,槽不等——被阻塞的只是某一件活,不是这个槽);终止态只有两种:已派,或零候选+扫描痕迹;④连续两轮回答相同=思维窄化信号,强制换一个来源深扫。答:逐问回答,第③问答枚举结果而非辩解 |
| 文档对照 | ~41min(与上行错峰) | **自执行** | 盯判断的依据是否权威。查:最近对玩法/业务做的判断、定的方案、派的批,是对照**领域权威文档**(需求方原话/设计定稿)得出的,还是看着现状代码猜的?「代码这么写」≠「这么写是对的」。行为类批的派单指令里带了「前置阅读」文档清单吗?答:每个近期判断给出「对照了哪条原则」或标记「没对照,补读」 |
| 进度对表 | ~45min | **自执行** | 盯迭代入口与各 app 池任务树**是否还反映现实**,偏了当场纠正(不是只标记)。查:①主线小节——实际做完的销;新冒的挂;「下一个待派」还是真的下一个吗;**当期目标行判据起数与实况一致吗**(判读结算后忘了更新=目标层漂移)。②持续运行健康线——现状和记录一致吗。③交付验收清单——最近验收发现「该查的项没有」=过期,当场补。答:所有不同步**现在改文件**;埋头推进数小时后入口停在几小时前=典型失效 |
| 深度巡检 | ~2h | **派 agent** | 盯需要**独立视角**的工作(提醒只做触发器,触达后派干净上下文的子任务,主会话只收裁决——自己审自己会带偏见)。查:①反馈队列逐条审(是通用问题还是项目特例?根因分析成立吗?);②实例层的结论哪些值得晋升进 skill/文档(主会话自己扫会觉得「刚写的都重要」)。答:裁决清单;轮空也要写「扫了什么」 |
| skill 遵循回看 | ~50min | **自执行** | 盯**最近的操作是否落在 skill 辖域内被规范管**。查:上一周期做过的操作(判读/派单/改码/写文档/收账/实机)逐个问「这个操作属于哪个 skill?当时遵循它了吗?」——**重点扫「当时根本没想到有 skill 管」的操作**(纪律失效的最常见形态不是知道规范没遵守,而是没意识到这动作有规范;识别出关联=重新加载该 skill)。答:没遵循的当场补检查或记反馈;给出「最近操作的 skill 映射清单」 |

**提醒词的写法(用户可见的持久化文本)**:提醒列表的原文会直接显示在用户界面上,用户随时可能读到——提醒词不是 agent 内部速记。写每条提醒词时按一句话判据自检:**「用户冷不丁看到这条提醒,能读懂它在提醒什么吗?」**答不上=重写:要点用大白话;自造的流程速记词(对工作环节的压缩说法)要么换成直白说法,要么当条带一句定义。**细节不进提醒词**:具体查什么/怎么答留在本节各角色行,提醒词只承担「触发 + 一句大白话要点 + 指向角色行的指针」——细节进提醒词会过期(上方条款管的),速记进提醒词会看不懂(本条管的),两条互补。

**自执行 vs 派 agent 的判据**(哪些提醒给编排者、哪些要派 worker):触达后**几分钟内可出动作且判据可内化**的(查状态/扫表/自问/触发预定义响应链)→ 自执行;**需要干净上下文或长时间专注**的(独立审查/偏见敏感的裁决/批量材料处理)→ 提醒触达后**派 agent 执行**,编排者只收裁决——提醒本身只做触发器,不承载这类工作(带着主会话上下文做=偏见污染)。**边缘情况**:语料积累类触发(「样本又够一批了」)不单独设提醒——并进派发盘点的四来源 D 扫描。

**skill 遵循回看的原理**(为什么事后回看优于事前自查):自主推进的纪律失效,最常见形态不是「知道规范但没遵守」,而是「做的时候没意识到这个动作有 skill 管」——行动瞬间最兴奋最想跳步,事前自查恰在此时最不可靠;事后回看没有行动冲动干扰,且违规已发生也能被抓。识别出「操作↔skill」关联本身就是重新加载该 skill 的触发器。与四来源盘点/进度对表同构:都是事后回看发现盲区,不靠事前自觉。

**「还有没有其他该做的事」的双保险设计**:15min 派发盘点是专职提醒(必须产出候选件或扫描痕迹);40min 产能质询第④问二次兜底(检验「没有事」这个结论本身)。两者有意冗余——盘点防「没扫到」,质询防「扫了但用同一双眼睛看到同样的东西」(连续两轮同答=窄化信号)。

**长任务自校准(防重心漂移)**:行为校准问「监控动作的产出密度」——观测≠产出,连续多个纯观测动作=漂移信号;等待间隙做并行产出(模拟对照/判读/审查),让「等运行」变成并行任务的一个分支而非全部。

## 6. 早停与收口

- **早停判据**(无信息量运行不陪跑):形态死局/验证已得/旧代码运行且修复待加载=**无条件早停重开**;验收线跌破(如关键血量线)=停+判读,不陪跑到终局。
- **判读锚点事前写**:实机验证前写预测(改了什么→应见什么),跑完核对——事后解释人人会,事前预测才是验证。
- **目标切换与迭代封存**:当期目标判据全达 → 换下一目标行(归档旧行)+交付验收清单对齐新阶段;整个迭代(分支/功能)完结 → 迭代目录封存(入口状态改已封存,不再追加),下次开工走 od-dev-progress-tracking §2.5 迭代启动 checklist 开新目录。

## 7. 防退化自检(模式失效的形态与自救)

| 退化形态 | 信号 | 自救 |
|---|---|---|
| 确认循环 | 盘点连续 N 轮「无需派」 | 四来源强制扫描+辩护带清单 |
| 认知窄化 | 注意力全在在飞件/最新刺激 | 连续两轮同答=换源深扫;等结果>10min 自问「找问题还是等结果」 |
| rubber-stamp | 审查只转发 worker 数字 | 亲跑复现+行号抽查,转述前核三件套 |
| 目标漂移 | 优化末端变量/陪跑注定失败局 | 双层目标(过程量优化/验收量报警)+早停判据 |
| 资产腐化 | 清单/表与实况不符 | 进度对表提醒+建资产必建维护回路 |
