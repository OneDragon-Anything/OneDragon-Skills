# 探索文档模板(app-explore 探索记录)

> 落点 `.debug/temp/app-explore/<yyyy-MM-dd-<简述>>/`(gitignore 临时区,寿命 = app 开发期)。SKILL.md §1 产出 requirement.md,§2 产出 flow.md,§3.1 产出 decomposition.md(拆解总表)+ `operation-flow-x.md` 系列(每个 op 一份设计书),§4.1 产出 application-flow.md。写作纪律:**正文只写当前认知的事实**——探索过程推翻了需求假设,直接改正文,不写「假设 vs 修正」的过程叙事。

## 1. requirement.md(需求与裁定,§1 产出)

- **目标**:一句话,合格判据 = 动词 + 对象 + 结果形态;周期型 app 写明运行周期(每日 / 每周 / 每月)与「已跑过跳过」的预期;
- **范围**:做什么 / 明确不做什么——真实货币充值等红线单列一条;
- **配置模型**:哪些项可配(开关 / 优先级 / 数量),每项的默认值;有优先级的写默认顺序;
- **使用与运行**:什么时候使用(手动触发 / 随一条龙日常),是否进一条龙默认组;
- **运行记录**:登记哪些业务字段(结果留痕:完成数量 / 失败明细等),重置周期(日 / 周 / 月——决定「本周期已跑过就跳过」的语义;部分失败的标记策略在这里一并裁定);
- **用户裁定**:逐条编号记录(每条 = 裁定内容),开放点的答案都归这节——这是需求的单一依据;
- **玩法知识**:从项目建档 / 官方渠道弄清的玩法规则摘要,带来源指针(文档路径 / 链接);
- **来源**:用户任务原话指针。

## 2. flow.md(流程走查,§2 产出,按走查实况记录)

四节:

- **待核实清单**:走查前预判要核实的问题,走查后逐项打勾;
- **四段走查结论**:①导航链逐跳落点画面 ②玩法段的界面状态清单(每状态长什么样 / 能读什么数据 / 有哪些分支形态)③领奖或兑换环节有无及其归属裁定(是否与玩法段交织)④返回链;**每段末尾标注现成 op 复用情况**(覆盖到哪 / 缺什么 / 无现成);
- **现场发现**:走查中发现的建档缺陷、框架缺口、与既有文档不符的玩法知识——需回填项目文档的列明出处;
- **待实机核对项**:无实机推演时,每条推演结论标注此项,后续验证逐项消掉。

事实与设计分离:画面事实(area / 路由边 / 子态形态)**即时进 screen_info 与画面 doc**,本文件只记流程,不做建档的第二份记录。

## 3. decomposition.md(拆解总表,§3.1 产出)

- **op 索引表**:每个 op 一行——标识符、职责一句话、状态(新写 / 复用 / 复用但需修 / 样板)、设计书指针(operation-flow-x.md);「样板」= 零覆盖但结构同型可参照的现成 op,记名字与参照点;
- **读数类需求去向**:哪些识别需求做成画面识别器的结构化输出(不造读数 op),识别器挂哪个画面;
- **开放点清单**:逐条列「问题 + 倾向方案 + 待用户裁定」——§4.3 沉淀为迭代设计文档时一并裁定。

## 4. operation-flow-x.md(每 op 设计书,§3.1 产出,每个 op 一份)

对标 `od-dev-write-operation` 的需求要素与画面流转格式,这份文档就是该 op 的开发需求书(op 实现按其主线走,① 需求确定以本文档为前置,不另建双份记录;节点图将来逐跳翻译自流转线):

- **目标一句话**:动词 + 对象 + 结果形态,做完后画面 / 状态变成什么;
- **起点 / 结束画面**:画面名(来自 flow.md);
- **流转**:逐跳流转线——`<画面A> --[点 <区域>]--> <画面B>`,停留本屏的动作写 `[读 <区域>,不流转]`;分支与变体形态一并标注;
- **红线**(有则声明):真实消耗 / 不可逆操作的边界;
- **放置位置建议**:跨 app 复用 → 项目顶层 operations 包;只在本 app 用 → 本 app 的目录(带一句判定依据)。

## 5. application-flow.md(app 编排设计稿,§4.1 产出,§4.2 补全)

app 级的编排设计稿(对标 op 开发里的 nodes.md),在全部 op 实现并单独验证后写;**独立成文件,不覆盖 flow.md**(那是走查事实记录,这是设计稿):

- **四段落成 op 序列**:每段用哪些 op(新写 + 复用)、执行顺序;
- **分支处理**:每个子 op 的返回结果怎么分支,每种结果的处理写全;
- **失败处理语义**:每个失败点选档(中止 / 单点重试后跳过 / 继续并汇总)与失败清单的去向;
- **run_record 处理方式**(§4.2):哪些节点写哪些业务字段;周期标记裁定(预期内无事可做标完成 / 该做没做成不标);
- **config 处理方式**(§4.2):哪里读什么配置,配置值怎么影响分支;
- **中断恢复**:做不做、怎么做(可选)。

节点图按本稿翻译(app 也是 operation,同 op 的翻译纪律);本稿随后沉淀为正式迭代设计文档(§4.3)。

## 6. 生命周期

- 创建时机:§1 需求确认后建目录 + 写 requirement.md;§2 产出 flow.md;§3.1 产出拆解总表与各 op 设计书;§4.1 产出 application-flow.md;
- §4.3 沉淀为迭代设计文档后,探索目录里的对应文件**停止独立维护**——后续更新写进迭代目录里那份(单一源,防双写漂移);
- §4.3 的迭代设计文档是 app 设计的人类裁决点(对抗审查;每个 op 自身的设计确认在 `od-dev-write-operation` 主线 ④);
- 收尾:app 交付后,设计稿的持久镜像是代码本身(docstring 契约 / `@node_from` 节点图 / config 注释),临时目录内容可清理——稿已删时从代码反推现状。
