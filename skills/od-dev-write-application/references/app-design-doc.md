# app 设计文档组织(复杂 app 才需要)

> 本文件是 SKILL.md 的**按需读深度细则**:复杂 app(多 op / 分支 / 循环 / 策略 / 多子系统)才需要写设计文档;简单 app(几 op 顺序跑)代码自解释,不必写。

## 核心原则:文档记 why + 代码不直接表达的,不复述代码

app 的行为 / 架构 / 配置 **代码就是真相**。设计文档记**代码不表达的**:设计的 why(为什么选 X)、架构 quick overview(指向代码不复述)、配置口语义、流程概述。防双源:代码改行为文档不必改(行为在代码);**设计决策**改了才改文档(加 ADR why)。

**受众**:懂代码的维护者 / 续开发 AI(不是「不懂代码的人」—— 那是 `docs/game/` 游戏玩法文档的受众,见 `od-dev-gameplay-automation` gameplay-recording)。可用代码术语(op / factory / 节点链),不必游戏化解释。

## 记什么

| 项 | 回答 | 代码里有吗 | 文档怎么记 |
|---|---|---|---|
| 定位 + 目标 | app 干什么 / 成功标准 | 没 | 一段话(做什么 + 目标) |
| **设计决策(decisions)** | 为什么选 X(架构 / 流程 / 策略选型) | 没(代码只有「是什么」) | **ADR**(一个决策一个文件 + INDEX + Status;有就写没就不写)—— 核心 |
| 架构概述 | op 怎么编排 / 分层 / 为什么这么分 | 有(代码)但 overview 帮助 | 概述 + 指向代码,不复述细节 |
| bot 流程 | 节点链 / 分支 / 循环 / 异常恢复 | 有(代码)但概述直观 | **文本描述**(节点链 / 分支 / 循环 + 指向代码;不用 Mermaid —— 语法负担 + 渲染依赖) |
| 配置口语义 | 用户可配项含义 / 默认 / 影响 | 有(config)但 why 不明显 | 列配置项 + 语义(为什么这默认 / 什么影响) |
| 状态 + 边界 | 当前进度 / 已知问题 / 不做什么 | 没 | 简短(或指针到进度文件) |

## decisions 用 ADR 式(不是 append-only 大杂烩)

**ADR(Architecture Decision Record)式**:`decisions/` 目录下一个决策一个文件(`0001-<slug>.md`)+ `INDEX.md`(总览)+ 每文件 Status(accepted / proposed / superseded)。**有决策才写,没决策不写**,不强制每 app 必有。

每条 ADR:
- **决策**:一句话 what。
- **为什么**:why(用户定调 / 实据 / 权衡)。
- **备选**:考虑过什么、为什么不选(**最值钱**,防后人重复扯皮)。
- **状态**:accepted / proposed / superseded(被新 ADR 推翻标 superseded + 新 ADR 引用旧)。

**踩坑 ≠ ADR,但踩坑可能触发 ADR**:
- 踩坑 = 碰到的问题 + 解法(被动,问题驱动);ADR = 主动选型决策。
- **踩坑触发选型 / 架构决策**的(如「SIFT 占用不可靠 → 改 CV 占用检测」是「用 CV 不用 SIFT」的选型)→ 进 ADR(记 why 改)。
- **纯实现 bug 修**(如命名错位改一下)→ commit message / 代码注释,**不进 ADR**。
- **判据**:这坑的修法涉及选型 / 架构决策吗?涉及 → ADR;不涉及 → commit / insights。
- 踩坑不单独立类(没有独立「踩坑文档」),分流到 ADR 或 commit。

## 怎么组织:总分结构

**简单 app**(几 op 顺序跑):单 `README.md`(定位 + 架构概述 + 配置口)+ 偶尔几个 ADR。代码自解释时甚至不写。

**复杂 app**(多 op / 分支 / 循环 / 策略 / 多子系统):**总分结构** ——
- **总 `README.md`**:app 定位 + 目标 + 整体架构概述(op 编排 / 分层 / 模块关系,文本)+ **文件映射**(各分文档讲什么,读者按需查)+ 当前状态指针。
- **分**(按维度 / 子系统拆):
  - `decisions/` —— ADR(INDEX + 单文件)
  - `architecture.md` / `flow.md` —— 架构 / bot 流程详述(总览不够才拆)
  - `config.md` —— 配置口语义(配置多才拆)
  - `strategy/` —— **玩法 app 才有**;策略方法论归 `od-dev-gameplay-automation`(SKILL.md「策略」节),本 skill 只占位 + 指针,不展开
  - 各子系统 doc(app 分子系统时)

**拆判据**(不机械每维度一文件,按实际):某维度**内容量大 / 需独立更新 / 是独立子系统**才拆成单独文件;否则并进 README。简单 app 别为拆而拆。

## 判据(什么时候写)

维护者 / 跨 session AI 改 app 时,「能从代码快速理解设计 why 吗?」不能 → 该写。简单 app 代码自解释可不写;复杂 app(多决策 / 多子系统 / 策略层)该写。

## 落点 + 边界

- **落点**:`docs/develop/<app>/`(项目开发文档)。
- **`docs/game/<玩法>/`**(gameplay-recording):游戏玩法本身(玩家视角事实,游戏版本更新才改,不懂代码能读)。
- **`docs/develop/<app>/`**(本方法论):app 设计(自动化 why + 架构,代码改才改,受众懂代码)。
- **screen doc**(`docs/game/screens/`):画面事实(游戏提供)。
- **进度**(progress-tracking / `.debug/`):任务状态,不进设计文档。
