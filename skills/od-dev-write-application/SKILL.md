# 写 / 改 / 调试一个 Application(OneDragon)

把一个玩法的一组操作(Operation,下文简称 op)组合成一个可运行的 Application:框架自动注册、带配置、能单独运行或进一条龙批量运行(一条龙 = 框架把多个 app 按顺序批量运行的日常模式)。

`Application` 继承自 `Operation`,所以**写 app 的大部分工作 = 写 op**(节点编排 / 画面查找 / 调试的完整规范都在 `od-dev-write-operation`),本 skill 只讲 app 这一层多出来的东西:

- **app_id 身份 + 运行记录**(`AppRunRecord`,按日 / 周周期自动重置;一条龙靠它判断「本周期已经跑过,跳过」)
- **约定式自动注册**:把 factory(应用工厂类,框架靠它实例化 app)与常量文件放到约定目录,框架自动发现并注册,不需要手工登记
- **独立的画面识别作用域**:每个 app 一套自己的画面识别配置,互不干扰
- **生命周期钩子**:框架在 app 运行前后自动调用,用来更新运行记录、发送通知

**改已有 app**:先按 §10.1 的分类表判断问题在哪一层;小改动可以不走 §1-§5 的完整流程。

## 1. 需求理解

动手写代码之前,先彻底搞清楚两件事:**用户要什么**、**这个玩法在游戏里是怎么回事**。需求理解对所有 app 都是同样的完整步骤。

1. **明确用户要什么**:
   - 范围:这个 app 做什么、明确不做什么(例如不碰真实货币充值);
   - 配置:用户可以配置什么(每个功能的开关、优先级、数量等);
   - 规则:资源不够时怎么办、失败了怎么办、什么算完成——这类规则逐条向用户确认;
   - 使用与运行:什么时候使用(手动触发、随一条龙日常)、是否进一条龙默认组、运行记录登记什么(哪些结果要留痕:完成数量、失败明细等)、运行记录的重置周期(每日 / 每周 / 每月——决定「本周期已经跑过就跳过」的行为)。
2. **弄清玩法本身**:这个玩法在游戏里的规则与流程。优先读项目里的玩法文档与画面建档;项目没有记载的,去官方渠道(如米游社)调研,不要凭印象猜。**调研到能回答这几个问题就算够**:玩法是什么类型(肉鸽 / 回合 / 节点制)、一局大致怎么流转、玩家在哪些点做选择、奖励结构长什么样;**调研后仍有歧义的(比如玩法身份都对不上),列成开放点问用户,不要自选一个假设往下推**;
3. **产出**:确认要做这个 app 后,建探索目录 `.debug/temp/app-explore/<yyyy-MM-dd-<简述>>/`(目录不入版本库,寿命 = app 开发期),把以上内容写成需求文档 `requirement.md`——探索期各文档(需求 / 流程走查 / op 拆解总表与设计书 / app 编排稿)的模板见 `references/explore-docs-template.md`。用户确认过的规则逐条记进文档的「用户裁定」节——口头约定会漂移,写成文档才有唯一依据。

## 2. 流程探索

**先看 app 流程的通用解剖——四段式骨架**(摸流程按它组织,知道要摸什么;编排设计(§3)也按它落),起点和终点都锚在主界面(通常是进入游戏后停留的第一个画面;各项目有现成的「回到主界面」收尾 op):

| 段 | 做什么 | 要点 |
|---|---|---|
| ① 导航段 | 从当前画面走到玩法画面 | **简单档**:先统一回主界面,再从主界面前往玩法画面——起点固定,绝大多数 app 用这一档。**精细档**:入口先识别当前画面,若已经在导航路径上,就从当前位置继续走(中断恢复能力);适合流程长、容易崩、用户经常中途接管的 app |
| ② 玩法段 | 真正的玩法操作 | 各 op 按顺序或分支执行 |
| ③ 领奖 / 兑换环节 | 玩法结束后的结算领取 | 有没有这段由玩法决定,不要默认都有 |
| ④ 返回段 | 回主界面 | 保证一条龙里下一个 app 从主界面干净开始 |

- 玩法与领奖同屏交织的玩法(领完奖励立刻产生新的可玩内容,例如领完委托马上空出一个派遣位):领奖段可以并入玩法段,同一组节点按「识别 → 领取 → 再识别 → 继续」的顺序执行,不必强行拆成两段;**走查时裁定归属并记进 flow.md**。归属随玩法机制的实际形态走,以走查结论为准——玩法改版后重新裁定,不按先例硬套。
- 单独运行或进一条龙批量跑,都从主界面开始、回主界面结束;app 之间在主界面交接;
- 「检测游戏窗口并进入游戏」由框架自动插入(构造参数 `need_check_game_win=True` 时),app 里不写打开游戏的逻辑。

**探索范围再确认**:基于 §1 对玩法的理解,先判断这是不是**长流程玩法**——判据:玩法内画面与状态多到一次会话摸不完,或单局时长长、深入后退出路径复杂(对战、肉鸽、楼层推进类)。给出自己的判断与推荐,与用户确认后再开工:

- **长流程**:本次探索只摸到「**玩法入口 + 进入后的中断退出链**」为止——摸清从玩法内任意深处退回主界面的完整路径(退出确认面板、暂离语义、结算怎么收尾、最终落在哪)。这是 app 异常退出处理的底座(返回段与兜底收尾全靠它),也是后续每轮迭代轻量验证的通道(§5),更让探索本身随时能安全脱离;更深的画面留给 §5 迭代实现循环逐个推进。无实机推演退出链时,至少把这几样推演出框架:退出控件在哪、有没有退出确认、进度是否保留、退出后落在哪个画面——全部标注待实机核对。
- **短流程**:全程走查一遍,本节走完即够。

范围确认后,摸流程的手法**全量沿用 `od-dev-write-operation` §2**,此处不重复(含走查时逐段查现成 op、只摸未知段)。app 层只有三点差异:

1. **走查顺序按上方四段式骨架**:导航链每一步落在什么画面 → 玩法段有哪些界面状态 → 领奖或兑换环节有没有、归属哪段(交织规则见上) → 返回链;
2. **走查目标是为 §3 编排设计供料**:除画面事实外,重点记每个画面**能读到什么数据、有哪些分支形态、各状态怎么进入怎么退出**;
3. **产出**:结论写进同目录的 `flow.md`(模板见 `references/explore-docs-template.md`,每段带现成 op 复用标注)。

没有实机条件时(例如只做预先设计),可以凭已有认知推演流程,但推演前先完成 §1 的玩法调研(推演结论要有依据),每条推演结论都要标注「待实机核对」,并把这些核对项并入后续的验证阶段(§7 第 3 条)。

## 3. 设计:op 拆分与编排

### 3.1 op 拆分设计

输入 = flow.md(流程走查);产出 = 拆分方案——**每个 op 一份设计文档 `operation-flow-x.md`**(x = 序号,放探索目录)。先想清楚:摸出来的流程该拆成几个 op、每个 op 负责什么、怎么拆才方便复用、方便 AI 经 MCP 调用。

**拆分判据**:
- 复用以 §2 走查时 flow.md 的逐段标注为输入,这里只做打包决定:**全覆盖**(已有 op 就是这件事)→ 直接复用;**大半覆盖** → 扩展它(加参数 / 加分支,完整版常比裁剪新建更稳);**部分覆盖** → 抽公共子 op 供新旧共用,或新 op 包一层调它;**无覆盖** → 新建,能说出理由(职责不同)。覆盖度之外,留意**同型样板**:别的玩法里结构同型的 op(零覆盖但写法可直接参照),在拆解总表里记一笔「样板」供实现参考;
- 值得做成独立 op 的:AI 调用方能单独调用它完成一件有意义的事(MCP 是框架把 op 暴露给 AI 调用的接口),且构造参数只用简单类型(数字 / 字符串 / 布尔,以及这些类型的列表)——参数太复杂 AI 就传不进来;
- **读取状态类需求**(调用方想知道游戏状态,而不是执行动作):优先把识别逻辑做成画面识别器的结构化输出(框架的 `ScreenRecognizer` 机制:识别器挂在画面上,画面识别接口的返回结果会自动带上识别出的数据与字段说明),不要为了读数据专门造一个 op。识别器怎么写参照框架现有的识别器样板;识别器对应的画面建档归 `od-dev-screen-onboarding` 管;
- 一句话塞两件事 = 拆成两个 op;已有的 op 一律复用,不重写。

**每份 operation-flow-x.md 写什么**(对标 `od-dev-write-operation` 的需求要素与画面流转格式——这份文档就是该 op 的开发需求书,节点图将来逐跳翻译自它):
- **目标一句话**:动词 + 对象 + 结果形态,做完后画面 / 状态变成什么;
- **起点 / 结束画面**:画面名(来自 flow.md);
- **流转**:说清这个 op 的画面流转——逐跳流转线 `<画面A> --[点 <区域>]--> <画面B>`,停留本屏的动作写 `[读 <区域>,不流转]`;分支与变体形态一并标注;
- **红线**(有则声明):真实消耗 / 不可逆操作的边界;
- **放置位置建议**:跨 app 复用 → 项目顶层 operations 包;只在本 app 用 → 本 app 的目录(带一句判定依据)。

实现 op 时按 `od-dev-write-operation` 主线走,其 ① 需求确定以本文档为前置信息,不另建双份记录。拆解总表(op 索引 / 读数去向 / 开放点清单)写进同目录 `decomposition.md`(模板见 `references/explore-docs-template.md`)。

### 3.2 逐个 op 实现与验证

按 §3.1 的拆分方案**一个一个来**:每个 op 以它的 operation-flow-x.md 为需求书,走 `od-dev-write-operation` 主线实现,`run_operation` 单独验证通过才算完成,然后进下一个。**复用的 op 也一样:跑一次 `run_operation`,确认它在当前游戏版本仍然有效**(跨版本复用、他人写的 op 尤其要跑)。

**是否给 op 单独做迭代设计,可以问用户**:复杂 op(多画面 / 多分支 / 有策略含量)值得先按项目的迭代设计流程出设计文档再实现;简单 op 直接写。

## 4. app 实现

前提:§3.2 的 op 已逐个实现并单独验证。**app 的本质也是 operation**,本章把 app 从设计稿实现到**能注册、能运行**,并验证流程串联的正确性;业务字段与配置项在实现步(§4.4)与节点图一次落地;GUI 见 §8(app 完成后再考虑)。

### 4.1 写 application-flow.md

app 级的编排设计稿(对标 op 开发里的 nodes.md):把四段式骨架(§2)落成具体的 op 序列——每段用哪些 op(新写的 + 复用的)、执行顺序、每个子 op 返回结果怎么分支处理、失败处理语义。**独立成文件,不覆盖走查的 flow.md**(那是事实记录,这是设计稿);模板见 `references/explore-docs-template.md`。

**编排语义参考**:

| 语义 | 写法 |
|---|---|
| 顺序(默认) | `@node_from` 依次串接 |
| 分支 | 子 op 的返回结果就是分支依据,每种结果显式处理(`od-dev-write-operation` §3.4) |
| 循环 / 重试 | 循环结构的选型与实现(`od-dev-write-operation` §3.1) |
| **失败处理(必须设计)** | 某个 op 失败后,整个 app 是停下还是继续做后面的?失败怎么汇总上报?app 最终状态怎么报?——必须在设计时明确决定并写进 application-flow.md,不允许写代码时随手定 |
| 中断恢复(可选加分项) | 入口先识别当前状态,已经在玩法中就直接接着做——程序崩溃、重启、人工接管后能从任意状态继续。日常自动化用不上;流程长、易崩、常被人工接管的 app 才值得做(与 §2 导航段的精细档同一适用判据) |

失败处理的最小参考(按失败点选档,可以组合使用):

- **中止**:入口、导航失败——后续步骤无从谈起,直接以失败结束;
- **单点重试后跳过**:单个子项重试后仍失败,记入失败清单,继续处理其余子项,不阻塞整体;
- **继续并汇总**:失败清单写进运行记录的业务字段和结束通知,呈现给用户。

### 4.2 补充 run_record 与 config 的处理方式

在 application-flow.md 里把这两样的设计补全(它们与节点图一体——节点运行时要写 run_record、要读 config,设计期就要定,不是实现时才想):

- **run_record**:流程的哪些节点写哪些业务字段(完成数量 / 失败清单等);**周期标记的裁定**——存在失败项时标不标「本周期已完成」:标了,一条龙本周期不再重跑(漏掉补做的机会);不标,一条龙会自动重跑补漏。判例:跳过分两种,标记相反——「预期内的无事可做」(配置全关、本周期没有可处理的内容)照常标已完成,避免一条龙反复空跑;「该做没做成」(有可处理的内容但失败了)不标,让一条龙下个周期重跑补做;**终止型目标**(目标本身内含终止条件,如「打到打不过为止」)终止条件达成属预期内完成,照常标;
- **config**:流程的哪里读什么配置(开关 / 优先级 / 数量),配置值怎么影响分支(如按优先级排序循环、被关闭的项跳过)。

### 4.3 写迭代设计文档

**固定步骤,不问要不要**:把前面的探索产物(requirement / flow / operation-flow 系列 / application-flow)沉淀成正式的迭代设计文档,放项目设计文档区的迭代目录(落点与写法按所在项目的文档规范);按项目流程走「写设计 → 对抗审查 → 修改优化 → 实现后更新正本」。最小骨架(项目规范没细说时照此搭):

```
<项目设计文档区>/<app_id>/changes/<迭代名>/
├── design.md          # 迭代总纲:动机 / 范围 / 验收判据 / 待实机核对清单(核销表)
├── requirement.md     # 需求 + 用户裁定节(开放点获答后回填)
├── flow.md            # 流程走查(四段式 + 逐段复用标注 + 待核对项)
├── operation-flow-*.md  # 各 op 设计书
├── decomposition.md   # 拆解总表(op 索引 / 读数去向 / 样板 / 开放点)
└── application-flow.md # 编排设计稿(分支 / 失败处理 / run_record / config)
```

**沉淀之后,探索目录里的对应文件停止独立维护**——后续更新写进迭代目录里那份(单一源,防双写漂移);§5 各轮说的「更新 flow.md / application-flow.md」都指迭代目录里的。

### 4.4 实现

把迭代设计翻译成代码:

- **app 类**:继承项目的 Application 子类,`@operation_node` + `@node_from` 节点图(节点内调用子 op,子 op 的返回结果就是节点的分支依据,每种结果显式处理——`od-dev-write-operation` §3.4);节点图按四段式组织(§2),交织玩法的领奖并入玩法段;
- **注册件**:const(`APP_ID` / `APP_NAME` / `DEFAULT_GROUP` / `NEED_NOTIFY`)+ factory(继承 `ApplicationFactory`)——**不注册就无法运行验证**,各只有几行;
- **run_record + config**:按 4.2 的设计一次落地(与节点图一体,不留空壳);
- **Context 接线**(特殊情况才):外部要直接访问 app 的 config / 运行记录时,在项目的 Context 配置加载里挂上(通常 factory 就够)。GUI 放最后,见 §8。

### 4.5 串联验证

目标是验证**流程串联的正确性**:四段走通、分支走对、失败处理按设计生效。

1. **重启 MCP server**(改了任何 Python 代码都必须做——服务进程缓存了已加载的代码与 app 实例,不重启跑的还是旧代码);
2. **注册确认**:app 出现在可运行列表(工具 `list_applications` 或图形界面);不在 → 查自动发现规则(`references/factory-and-discovery.md`);
3. **`run_standalone_app` 实机跑一遍**,主界面起止:每个 op 依次跑过、分支走对——全部 op 已各自验证过,这一步失败锁定在串联与状态流转上。想更轻也可以先尝试 `run_operation` 直接跑 app 节点图实例,跑通了再走 `run_standalone_app` 的正式通道。

深入细节(自动发现规则 / 配置与 GUI / 运行记录 / 第三方插件 / 打包)见 `references/` 对应文件。

## 5. 迭代实现循环

**触发**:§2 裁定为长流程的玩法才走本章;短流程 app 跳过,直接进 §7(需要策略时先走 §6)。**进入前提**:§4 完成——app 骨架可运行(入口段跑通 + 中断退出链可用)。**收敛目标**:requirement.md 目标覆盖的推进路径全部可自动执行;循环开始前与用户确认「覆盖到哪算完」。

### 5.1 轮次划分:以玩法的推进单元为单位

一轮迭代 = **游戏内这个玩法的一个推进单元**——肉鸽的一层、回合制的一个回合、对局的一个阶段。不以 UI 画面数划分:一个推进单元可能跨多个画面流转。向用户授权时报清楚本轮覆盖到哪个推进点。

### 5.2 每轮迭代的标准动作

1. **向用户报本轮推进单元与预期产出**,确认授权(真实消耗逐次确认);
2. **摸该单元**:手法全量沿用 `od-dev-write-operation` §2(逐跳微循环建档 + 纠档 + 变体枚举),结论更新进 flow.md;
3. **增量设计**:新单元的 op 拆分(operation-flow-x.md / 复用判定)+ application-flow.md 更新(接入点、分支、失败处理);
4. **轮次设计记录**:在 app 的迭代目录(§4.3 沉淀的那个)下为本轮建轻量子目录(目标 / 摸查结论 / 设计 / 验证判据);
5. **实现**:新 op 走 `od-dev-write-operation` 主线;
6. **验证,尽量少验**:新 op 先单独 `run_operation` 验证;接入验证**从最接近的玩法内起点跑到新单元完成,然后走中断退出链退回**——不重复跑已验证的前缀(§2 先摸中断退出链在这里兑现:它既是异常退出的底座,也是每轮轻量验证的通道)。「最接近的玩法内起点」的构造:手动把号带到该状态,或用已有 op 直达;
7. **重新设计编排**(§5.3,每轮收尾必做);
8. **提交**:本轮的代码 + 建档 + 文档单独 commit——**app 始终保持可运行前缀**,任何时刻停下来都是一个能跑的 app。

### 5.3 重新设计编排

追加式生长会让节点图长成补丁堆——每轮的新节点硬挂到旧图上,流转越来越歪,后期没人敢动。所以**每轮收尾必须重新审视整体编排,以治本的方式改好,而不是挂补丁**:

- **审视什么**:
  - 节点归并:新单元的节点与旧节点是否职责重复(同一画面判定散在多处、可合并的相邻流转);
  - 段重划分:四段边界是否还成立(新单元该并入玩法段,还是值得独立成段);
  - 循环结构:推进单元的循环是否该改选型(结构选型见 `od-dev-write-operation` 的循环章节——选错会结构性卡死);
  - 失败处理与恢复:新单元引入的失败态,是否被现有失败语义覆盖;入口恢复能力是否要跟上(玩法深处多了,中断后从头跑太贵;适用判据同 §2 导航段精细档)。
- **怎么改**:先改 application-flow.md(编排的单一源),节点图随之重构——节点图是 application-flow 的翻译,不是独立演化的实体;
- **改多少决定要不要单独迭代设计**:小改(节点归并 / 微调流转)直接改 application-flow 与代码;大改(段重划分 / 循环结构改选型 / 整体重组)值得为这次重构单独出一份迭代设计文档(同 §4.3 的流程),做不做咨询用户;
- **重构后验证**:重跑一遍当前深度,确认可运行前缀没被改坏。

### 5.4 未知状态与运行期发现

- 摸不到的形态(随机态 / 罕见态)记未知项不硬等,留给运行期:停机钩子捕获(`od-dev-stop-hooks`)或现场建档(`od-dev-screen-onboarding`),下一轮迭代补上;
- 跨会话的多轮迭代用 `od-dev-progress-tracking` 记进度账,防丢上下文。

### 5.5 收敛

主流程推进单元全覆盖 + §7 端到端验收通过 → 循环结束。游戏版本更新改变玩法形态时,再启新迭代。

## 6. 策略设计

**初版不做策略**:app 初版编排与 §5 迭代推进期,需要策略的位置先用**随机数或固定方案**占位,把流程跑通放在第一位。

**引入时机**:迭代中发现占位方案无法完成流程,或者认为需要更好的策略换取更好的脚本体验时(短流程 app 没有迭代循环——端到端验收后发现占位不行,同样适用),才做策略设计。

**设计顺序**:

1. **从简单方案开始**:贪心算法,或通用但不追求极端情况的算法——能跑通、覆盖大多数局面就够了;
2. **再考虑配置性**:适配不同玩家账号需要哪些配置(优先偏好 / 激进度等),做成配置项;
3. 按此设计:策略落在 op 内部逻辑的,改对应 op(走 `od-dev-write-operation` 的修改路径);落在 app 编排层的,更新 application-flow 与节点图;大改走 §4.3 的迭代设计。

**数据来源**:策略实现所需的游戏原始数据,从游戏官方 wiki 或游戏实机录取,不凭印象编。

## 7. 端到端验收

实现完成后的最终验收:

1. **`run_standalone_app` 完整跑一遍**,验证产品化行为:运行记录状态正确(成功标「本周期已完成」/ 失败按联动裁定不标——一条龙靠它判断跳过或重跑补漏)、结束通知按 `NEED_NOTIFY` 发出;
2. **一条龙确认**:要进一条龙的 app(`DEFAULT_GROUP=True`)出现在一条龙的运行列表里;app 之间的衔接由「主界面起止」结构保证(§2);
3. **核销流程探索欠下的债**:流程探索时标注「待实机核对」的每一条(§2 无实机推演条款),在这一步逐条核实——不核销,这些错误假设会静默留在代码里。

**用假画面回放做流程测试不是必做项**:各 op 自己的测试已在各自开发时完成;app 层的串联测试,编排里**有条件分支或循环**(子 op 多结果分支 / 循环推进)就值得补——用录制的画面序列回放整个 app 流程,锁住串联结构;纯直线串联可不补。

## 8. GUI

**整个 app 完成(端到端验收过)后再考虑**——界面是壳,不是运行的前提,别在流程没跑通时先做界面。

- **默认形态**:进一条龙运行的应用,只做一个配置页面,挂在一条龙的应用设置列表里(各项目 GUI 框架有现成的配置界面模式,照现有 app 的写一个即可);
- **独立 GUI 入口**:只有特殊需要才做(应用需要专属的操作台 / 状态展示 / 手动触发面板),**做不做与用户确认**。

## 9. MCP 配置工具

app 的配置写规范(`YamlConfig` 子类,写法见 §4.4 与 `references/config-and-gui.md`)后,**框架的通用配置工具自动能读写它**——agent 经 MCP 就能查配置结构、读当前值、改配置(如 AI 助手替用户改开关 / 优先级 / 计划清单),不需要 app 自己开发配置工具。本章要做的只是**验收它真的好用了**:

1. **`describe_config` 看结构**:字段名 / 类型 / 枚举合法值 / 列表项结构 / 只读项,对 agent 是否清晰——字段语义靠配置类里的注释与 describe 输出传递,含糊的补;
2. **`get_config` / `set_config` 实测一轮**:读默认值 → 改一项 → 读回确认;改完下一次运行立即生效(不需要重启);
3. **适合暴露的形态**:开关 / 数字 / 枚举 / 短列表这些简单字段;计划类清单用列表项工具(增删改插,见框架的 add / update / delete 配置项工具);运行态字段(如运行次数)设为只读,不给写口。

## 10. 修改与调试

先判断问题在哪一层,再动手:

### 10.1 症状分类表

| 问题在哪一层 | 去向 |
|---|---|
| 单个 op 内部(节点流转 / 识别 / 读数) | `od-dev-write-operation` §9 修改与调试 |
| 串联层(编排顺序 / 分支路由 / 主界面衔接) | 本 skill:回 §4 改 application-flow 与节点图 |
| 产品化层(配置 / GUI / 注册 / 运行记录) | 本 skill:查 §4.4 对应步 + reference |
| 用户反馈的运行失败(你不在运行现场) | `od-dev-debug-automation` |

### 10.2 app 常见症状速查

| 症状 | 根因方向 | 处理 |
|---|---|---|
| app 跑完第一个节点就「成功」结束,后面的节点全没跑 | 没有入边的节点不会执行(`@node_from` 串接缺失;**声明顺序 ≠ 执行顺序**) | 补串接边 |
| 一条龙里 app 之间衔接失败 | 首尾 op 没回主界面 | 修编排,保证主界面起止(§4.1,原则见 §2) |
| 一条龙跳过了这个 app | 运行记录 `is_done`(本周期已完成 / 上次状态残留) | 查运行记录(`references/run-record.md`) |
| 改了代码行为没变 | MCP server 缓存了 app 实例 | 重启 server 再验证 |
| app 不在可运行列表 | 自动发现失败:同目录有多个 `_factory.py` / `_const.py`、`APP_ID` 重复、目录位置错 | 查注册(`references/factory-and-discovery.md`) |

## 11. 必守规则

1. **`APP_ID` 全局唯一**(重复注册会被框架拒绝),且与运行记录里的 app_id 一致。
2. **同一个目录只放一个 `_factory.py` 和一个 `_const.py`**(多了,这个目录会被框架整个跳过)。
3. **factory 必须实现 `create_application`**;需要运行记录再实现 `create_run_record`(不需要的 app 可以不实现)。
4. **app 类继承项目的 Application 子类**(各项目通常有特化子类,自带默认的进游戏入口),构造时传 `app_id` 和 `run_record`。
5. **改 app 代码后必须重启 MCP server 才生效**(框架缓存了 app 实例)。

> app 的节点图与画面操作调用同守 `od-dev-write-operation` 的全部规范(节点边显式串接 / 导航独占节点 / 等待时长显式声明 / 节点图完整性三查),本 skill 不复述。

## 12. 边界

- 写 / 改 / 调试**单个 Operation** → `od-dev-write-operation`(app 复用它)
- 画面建档 / screen_info 维护 → `od-dev-screen-onboarding`
- 用户反馈的运行失败排查 → `od-dev-debug-automation`
