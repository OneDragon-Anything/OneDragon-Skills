# ADR-0004:交付-验收记账协议——review 态、多方自记账与文件存在门

- Status: accepted
- Date: 2026-09-09
- Amends: 0003 的两处——状态机五态扩为六态(新增 `review`);第 6 条「单写者纪律」废除,改为多方自记账+账本级锁。0003 的其余部分(事件流正本/图运算/建模纪律)全部延续。

## Context

自主推进编排者上下文过载事故(2026-09-08/09 实证:编排者被盘点候选单、事故与审查流水灌满上下文,裁决-派单停摆)驱动「编排者瘦路由」重构:编排者只派单与路由,实现、审查、记账下沉到专职子 agent(worker/reviewer)。

旧模型两处不适应:

1. **五态没有「做完待验收」的位置**——done 的语义是「验收过」,worker 做完、等验收只能停在 doing,账本与实际错位;「待验积压多少」不可查。
2. **单写者纪律(子 agent 不写账本,编排者代记)让每笔交付/验收都过编排者的手和上下文**——正是过载源;且交付报告与验收结论主要活在会话消息里,换 session 即失效,违背 0003 的「读者无关」承诺。

## Considered Options

- **note/criteria 约定模拟「待验」(不加状态)**:否——流转合法性脱离机器校验,「打回必带 why」「验收必带结论」退化为自觉;「待验积压」变成扫目录的脆弱信号。
- **worker 开工自领 doing(自填 assignee)**:否——assignee 语义是「任务归谁做」=路由决策,worker 无权也无从填(任务书先于自身持久 id 存在);且先 spawn 后记账的窗口里,编排者重启会看不到「已派出」,有重复派发风险。
- **reviewer 直接登记打回(review→doing)**:否——→doing 必带 assignee,「返工给原 worker 还是新工」是路由决策,reviewer 不该猜。accept 无此问题(done 不带 assignee),故 accept 自闭环、reject 回编排者的不对称由状态机必带字段自然导出。
- **编排者继续代记全部账**:否——记账动作本身轻,但「编排者必须在场解读每个事件才能记账」把交付/验收重新耦合进主会话上下文,过载复现。

## Decision

1. **六态状态机**:新增 `review`(已交付待验收)。流转:doing→review(交付,必带 criteria=交付报告指针,worker 登记);review→done(验收过,必带**新** criteria=验收结论指针,交付报告不算数,reviewer 登记);review→doing(打回,必带 why=原因+结论路径,编排者登记);review→dead。done→todo 与 review→doing 为仅有的两条回边。
2. **多方自记账替换单写者纪律**:谁把任务置成某状态,谁记那条账——→doing 编排者(填 assignee)/→review worker/→done reviewer。写安全从纪律改为**账本级锁文件**(O_EXCL 原子创建,等锁 10s,残留锁按 mtime>60s 强拆,写入 fsync);并发追加另需处理 Windows 删除挂起期的 PermissionError(语义=锁被占,重试)。
3. **assignee 收紧**:只在 →doing 出现,永远由编排者填(软标签可读名)。子 agent 不填——不知自身持久 id,也无权做路由决策。review 态保留交付者 assignee(打回派返工的线索)。
4. **文件存在门**:上述三条自登记流转的指针/路径必须指向真实存在的文件(相对账本目录解析,兼容绝对路径;形似路径不存在、或纯文字凭据均写入打回);check 重放对 review 态做同款存在性扫描。信任锚从「编排者亲验」转移为「文件存在性的机械证明」。
5. **交付物双目录**:`reports/`(worker 完成报告,五节结构)与 `reviews/`(reviewer 结论)与账本同级,命名 `T-<N>-r<K>.md`,返工轮次递增不覆盖;账本 criteria/note 只存指针,交付=文件而非会话消息(最终消息退化为 ≤10 行摘要+路径)。
6. **log 命令+返工熔断**:`log <id>` 输出事件时间线与交付/打回计数;同一任务打回 ≥3 次=规格问题,停派返工,立「规格重审」新任务(新 id,note 注明承接)。

## Consequences

- 正:worker/reviewer 自登记后,编排者从记账与验收解读中解放(只读 ≤10 行结论行);交付/验收凭据文件化,换 session 可重建(0003「读者无关」延伸到交付层);假登记在写入时被打回;账本+文件双源一致性有 check 机械守门。
- 负:①多方并发写依赖锁文件机制自身正确(残留强拆是兜底;锁竞争不可自愈时写入暂停,需人工拆锁);②reject 后账本停留 review 直到编排者路由——编排者长时间缺席时待验任务积压在 review 态,由兜底对账扫描兜住;③「先登记后补文件」的操作顺序被非法化,先写后登成为强制;④`todo→done`/`doing→done` 补记不受文件门约束(门只卡自登记流转),两种 done 的凭据强度不同是已知且接受的差异。
- 复活条件:锁文件机制在高并发下出现不可自愈的竞争 → 升级为 OS 级文件锁(msvcrt/fcntl)。
