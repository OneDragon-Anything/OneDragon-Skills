# 运行时工艺(探索式开发的 op 级技术,reference)

> 本 skill(`od-dev-write-operation`)的 situational reference。SKILL.md §8(必守不变量)与 §9(修改与调试)留判据;本文件给 op 级运行时技术的完整展开:信息密度 / 调试纪律 / 预料外画面调研 / reader 输出契约 / 钩子代码手法 / 画面定型门。`od-dev-gameplay-automation` 的生命周期视角也引用本文件(单源,不重复)。

## 1. 信息密度论:一次实跑榨取最多信息(多 log 多截图的根因)

探索式开发里,**每次实跑都在暴露建档缺口**(没预期的状态 / 分支 / OCR 误匹配 / 坐标漂移)。故每次跑的"信息密度"必须拉满 —— 别"跑一次只为找一个坑":
- 每个决策点(购买 / 选择 / 升级 / 部署 / 事件分支等一切"读屏后选动作"处)记:OCR 到什么、评估了哪些选项、选了哪个、为什么、点了哪、结果如何;关键分支**存 debug 截图**。
- **判据:实跑后看日志就能复盘整局每个决策点发生了什么**(不用重跑猜);做不到 = 日志不够,补。
- 目的不只是"失败时定位根因",更是**让一次实跑暴露尽量多的问题**,而非每次只测一种情况。
- 验证通过后逐步去掉临时日志 / 截图(减运行时开销)。
- **初期接触玩法时尤其要堆满**:对机制 / 画面 / 时序理解最浅的阶段,信息密度拉满收益最大。

## 2. 调试纪律:先读日志再动手

bot 卡死 / 死循环 / op 失败时,**先读日志**,别凭猜改或盲点坐标:
1. **读日志**(MCP server 日志,项目 `.debug/` 下):看卡住时实际 OCR 到什么、走到哪个节点、决策状态(等待 / 重试 / 失败)。日志常直接暴露根因(OCR 没读到锚点 / 节点循环 / 命中错屏)。
2. **日志解释不了 → 补日志**:若日志只记 OCR、没记点了什么坐标 / click 是否成功 / 走哪个分支,就在决策点补日志(OCR 摘要 + 点击坐标 + click / 分支结果)+ 临时存图(`screenshot()`)。**不可观测 = 不可维护** —— 否则下次同样卡住还是黑盒。
3. **结合日志 + 玩法知识形成假设**:日志给客观事实,玩法知识给假设方向(「会不会要多次确认」「会不会前置条件没满足」「会不会 click 后紧接鼠标移动被判拖拽」),验证。
4. **假设驱动的修改纪律**:动手改前把假设写明(「根因是 X,改 Y 应见 Z 变化」);**一次只改一个变量**(同时改两处,成了不知哪处起效、败了不知哪处惹祸);**修根因不修症状** —— 确认根因后才修,别散弹枪式连续试补丁。
- **反例**:bot 卡住 → 不看日志,直接盲点坐标试,没成又换坐标 —— 定位不了根因,改了下次还卡。

## 3. reader 输出契约:实读 / 兜底 / 推算必须可区分

画面读数器(reader:OCR 数值 / 模板识别 / 状态读取)的返回值会被下游当事实消费(遥测 / 策略决策 / 校准对拍),输出必须自带可信度信息,否则一次兜底就能污染整条数据链。

- **来源标记**:reader 返回值带来源 —— `实读`(本次 OCR/识别真实命中)/ `兜底`(启发默认值:上一轮值 / 常量 / 近似推断)/ `推算`(由已追踪状态派生)。判据:**事后只看遥测,能否区分实测值与兜底值**;不能 = 契约缺失。兜底值要么不进遥测,要么单独打标。
- **单调守卫必须配物理跳变上限**:对「只增不减」字段(等级 / 金币 / 轮次)加单调守卫时,必须同时拒绝物理不可能的跳变(一次跳变超过单位动作物理上限 = 误读,拒收而非接受)。只防倒退不防暴跳的守卫,会把一次大误读**永久锁死** —— 后续所有真读都被它吃掉,且表面看数据完全正常。
- **兜底是暂时占位,不是静默常驻路径**:启发兜底的触发要落一行「需关注」日志(可 grep);兜底长期高频触发 = reader 本身有问题(区域/阈值/时机),去修 reader,别让兜底变成事实上的实现。

> 消费端呼应:策略 review 时「数据依赖真实性(读的字段是实读还是兜底)」是必审项,见 gameplay-automation `strategy-craft.md` T3;遥测不带兜底值见同文件 T2。

## 4. 预料外画面 → 调研"怎么交互进来的" + 建档(探索式循环的"补建档 + 补分支")

bot 跑到代码没预期 / 没 handler 的画面(点卡开出详情、误点进设置、过渡叠层)时,**别只 ESC / handle 掉就完事** —— 这正是探索式循环里"发现未预期 → 补建档 + 补分支"的一步:
1. **回溯入口**:看日志 / 截图,定位**上一步代码点了什么**导致进这屏(哪个 click / nav、点的 UI 哪个元素)。典型:想点某张卡选中,却点中卡上**会触发别的交互的元素**(立绘 / 图标)→ 游戏打开详情页(对该元素的固有交互)。
2. **建档该画面**:记**入口**(从哪来:什么动作 / 条件触发)+ **出口**(怎么回 / 推进)+ **为何出现**(游戏机制)。进 screen doc / insights。
3. **修代码不再误触**:根因是"click 落到会触发别的交互的元素上" → 调 click 目标(避开该元素,点同卡的非触发区),或调交互顺序。
- **判据**:遇未建档 / 未预期屏 → 先问"上一步点了啥 → 落哪个 UI 元素 → 游戏对该元素啥交互" → 建档 + 改 click 避开。只 ESC 不调研 = 同样误触下次还发生(黑盒)。

> 搞清画面**全部交互行为**的完整探索协议(回溯怎么进 / 系统找出口 / 穷举每个可交互元素并观察 / 交互前后状态读取对比 / 禁干卡)见 `od-dev-screen-onboarding` 的「卡住画面协议」 —— 本节聚焦 op 级"回溯入口 + 改 click 避免误触";"把认知不完整的画面行为摸清"归建档方法论(画面行为探索 single source 在那)。

## 5. 运行时不确定性 → 开发时预留日志 + 截图开关

自动化开发(游戏交互)比普通软件**不确定性大得多**:UI 变 / 时序抖动 / 加载延迟 → **TDD 锁不住运行时问题**(TDD 只锁纯逻辑)。故功能开发时关键决策点**预留充足日志 + 临时截图开关**,前期跑失败一次就能定位根因,不用反复重跑猜。验证通过后逐步去掉(减运行时开销)。

## 6. 重复的手动操作 → 尽早建成 op

开发 / 测试中**手动做了 2+ 次的导航序列**(退出对局:Esc→放弃→结算多页→大厅;或进玩法入口),**尽早建成 op**(放 `operations/`,`run_operation` 一键调):① 不用每次手动点 N 按钮;② 可复用(刷开局 / 测试 / 回滚);③ op 有重试 / 超时 / 日志(比手动可靠)。**判据:同一手动操作做 2 次 → 第 3 次前建成 op**。

## 7. settle-then-dispatch(画面定型门):等画面定型归 op 代码,不归 agent

**根因(agent 可观测性约束)**:人类开发者能看着画面、数出「主屏渲染后约几秒弹 overlay」;agent 经工具调用往返慢、拿到的只有离散快照,**无法知道下一画面何时出现**。故「看画面等它定型」必须**编码进 op**(op 循环每迭代都在采样 = 代码在"看着画面";agent 侧 `sleep` 是猜时长,游戏时序一变就碎——agent 侧加长 sleep 这类点状修是本缺位的典型变形)。

**适用判据**:实机录屏 / 多帧存证确认画面存在「**渲染主体先出、判定性 overlay 后弹**」时序(游戏 UI 常见),且分发 / 判定锚点可从将弹的 overlay 下透出(半开帧 = 主体在、判定性内容未弹,锚点照常命中 → 识别对了但状态没定型)。锚点选型优先**只在定型后存在的元素**(overlay 自身 / 后弹内容):半开帧它自然不命中,稳定门的「连续命中」从第一帧就只在定型后起算——比拿透出的主体锚点再补计时更直接。消费点两处:

- **op 入口 / 出口门**:入口等预期画面**出现且定型**才开始动作(入口识别别只查一次——刚切换来时主体可能已渲染、子态没弹完);出口等目标画面**定型**才 `round_success`(转移信号可被半开帧满足,纯「信号出现过」在过渡态上会假阳;出口验证纪律见本 skill SKILL.md ③节点卡「动作后验证」与 ⑤ until 语义,本门补过渡态洞)。**等不到 = 异常退出**:`round_retry` 计节点预算兜底退出(与「点了≠成了」的兜底纪律同构),别无限 `round_wait` 烧全局预算。
- **分发层稳定门(flat loop / 主 loop 的"截屏→分类→选 handler")**:同一分支跨迭代**连续命中达稳定窗**才派发(相位首命中时间戳 + 上一轮分支标志);分支切换 → 重计时;链式 overlay(弹完一个又弹下一个)→ overlay 分支优先检查,消化完回主屏**重计时**逐个走,别把连续弹窗当已定型。

**与坑 8(瞬态残影假阳)分流**:失败帧的配对截图里是**上一步动作的残留动画**(读到的还是旧世界)→ 坑 8,动作前 fresh 重读;是**新画面主体已渲染、判定性 overlay 还没弹**(新世界没弹完)→ 本节,加定型门。同是过渡帧问题、机制相反,别混着修。

**与既有等待原语分工**:坑 2 sleep / `round_wait` = 动作后一次性等(猜时长,agent 侧);出口验证 = 验转移信号**出现过**(可被半开帧满足);本门 = **循环观测到子态定型**(测时序,op 侧)。三者正交互补。

**升格纪律**:同一画面切换处的点状修(agent 侧 sleep 加长 / 同帧关键词门 / 特效探针)已做 ≥2 次 → 停止继续堆近似,升格本门(手工近似累积 = 缺抽象的信号)。

## 8. 钩子触发停 bot 留画面(随机 / 珍贵态当场建档)

**场景**:bot 自主跑(造数据 / 测流程)时遇到**会话内造不出、珍贵、需当场建档**的随机态(罕见配置 / 罕见 overlay / 特定词缀组合),错过不知何时再遇。光存图离线建会漏(穷举交互验行为 / 实时 analyze / 点后跳转必须当场)→ 钩子检测到 → **触发停 bot 留画面**给 AI 当场建档。**判据(哪些态当场建 vs 离线建)见 `od-dev-screen-onboarding` 随机 / 条件态节**;本节给 op 级实现。**钩子生命周期判据(临时捕获 vs 常驻兜底两分类 / flag 三要素契约 / 停机→留证降级治理)与停机现场处理协议 → `od-dev-stop-hooks`**(本节只管代码手法)。

**标准做法(临时钩子,建档后回滚)**:
1. **钩子位置**:目标 node 方法**最前、click 前**(检测在改变状态前);或画面判定 / 状态读取函数。
1a. **埋钩子前置评估(先看游戏当前停在哪)**:钩子按「检测到目标态就停」工作,**不看是谁把画面带到触发态的** —— 若埋钩子时游戏**正好停在触发屏**,则每个新 run 一进来就命中钩子 = **必停**(且秒停形态极易被误判为「外部拦截」,误导排查方向)。埋之前确认当前画面不在触发态;在 → 先手动导航离开,或接受首个 run 必停。
2. **前置门(先于 reader 检测;采集 / 停机两类钩子通用)**:reader 跑前先验**画面态锚点**(该画面 screen_info 的锚点 area / id_mark 命中);不命中 → 直接走原逻辑 —— 非目标画面态上 reader 的「全 miss」是空读伪信号,不是目标态出现。两类钩子的定义与分流判据(**采集钩子** = 检测到目标态只存样本图、bot 继续跑;**停机钩子** = 存 sentinel 停 bot 留画面)见 `od-dev-gameplay-automation` runtime-iteration「随机态钩子分流判据」。锚点命中判定的原语(画面级 `is_target_screen` / area 级 `find_area`)见本 skill SKILL.md ⑤「op 内工具箱」+ `references/round-by-helpers.md`「非节点上下文」节。
3. **检测到目标态 → 存 sentinel + 调框架停 + return 保画面**:
   ```python
   @operation_node
   def 某node(self):
       if self._screen_anchor_hit():  # 前置门:画面态锚点命中,reader 的检出才算数(空读≠信号)
           state = self._detect_target_state()
           if state == TARGET:  # 钩子(临时,建档后删)
               self.save_screenshot(prefix='target_state')
               # sentinel 必须自描述(禁裸态名):接管者/诊断者一眼知是自家钩子停的、钩子在哪、怎么收尾
               Path('<临时目录>/target_state.flag').write_text(
                   f'HOOK-STOP: 我的临时停机钩子停的(非故障/非人工/非外部)。'
                   f'钩子位置: {__file__} 某node; 态={state}; 时间=... 。'
                   f'现场处理: 点开该元素确认身份,按画面建档流程补档。'  # 可执行处理步骤(接管者照做就能处理;缺了它接管者只能瞎猜,审计最常见不合格项)
                   f'处理完: 删钩子代码 + 删本flag。')  # 临时目录路径由项目自定,但埋钩子的与接管的 AI 必须用同一路径(写死常量,别两处各猜)
               self.ctx.run_context.stop_running()  # 框架公共停(下一轮 loop 顶见 STOP 退出)
               return self.round_wait(status=f'目标态:{state}')  # return 不 click,画面原样保持
       ...原 node 逻辑...
   ```
   ⚠️ **sentinel 内容禁裸态名**(`write_text(state)`):裸态名的 flag 对后来者零信息——不知道是谁写的、还是不是活的;自描述内容(「这是我的钩子停的 + 钩子位置 + 收尾动作」)让任何接管者 / 诊断者不用 grep 就能定位。同理,停机时**写一行带特征的日志**(如钩子名前缀),死亡时刻日志一 grep 就中(排查序见 `od-dev-debug-automation` §1「run 被停→判死因」)。
4. **AI 接管建档(停机现场处理协议——含禁绕过清单与 flag 缺要素的类型默认流程,见 `od-dev-stop-hooks`)**:`get_run_status`=STOPPED + sentinel(flag + 截图)在 → **sentinel 必需**(区分「遇目标态停」vs「故障 / 手停」,纯 status 不够)→ `analyze_screen`(sentinel 截图,无需游戏在线)+ 视觉大模型 + 当场跑建档流程(接管时画面可能已被游戏动画 / 结算推进走 → 只剩存证截图时走 `od-dev-screen-onboarding`「随机 / 条件态」节的**停机后画面已流转降级路径**)→ 完了**删钩子 + 重启 MCP server(代码生效)+ relaunch bot**。⚠️ **删钩子 ≠ 删 flag**:删钩子代码后 sentinel flag 仍躺在磁盘上,必须一并删——陈旧 flag 会让下一个诊断者误判「还有活钩子 / 目标态又出现」(反复出现的产物 = 活的生产者,他会 grep 写入者、发现钩子已删、再困惑一轮)。收尾清单:**删钩子代码 + 删 sentinel flag + ruff 确认无残留**。

**升级路径(反复暂停恢复才做)**:框架有原生 PAUSE(loop sleep 不跑 node + 超时豁免)但 MCP 未暴露 → 加 pause/resume MCP tool = 保运行态 + 真 resume,语义更干净。替代手段为什么不行:`round_wait` 不计 retry(可用 `wait`/超时参数控制节奏,不适合做"停住等接管"的 latch —— 自建 flag 判断"该不该继续"很脆弱);节点内 `raise` 异常会消耗节点 retry、重试耗尽后转 FAIL 让流程**继续往下走**(丢掉想保的画面),也达不到"停住"的目的。
