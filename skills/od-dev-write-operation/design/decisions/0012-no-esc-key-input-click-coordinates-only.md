# 0012. 画面操作以点击为主:禁用键盘 ESC,其余按键尽量不用(手机模拟器端前向兼容)

- **Status**: accepted
- **Date**: 2026-08-27

## Context

原必守不变量 #3 是软约束(「预料外画面别只 ESC」),实际代码里 ESC / 按键用法持续累积,且已实机出事:

1. **语义漂移事故(常发)**:同一 ESC 键在不同画面语义完全不同——有的屏是「关面板」(安全),有的屏是「弹中断确认」(危险,备战屏实证多次)。写 op 的人对当前画面的 ESC 语义判断错一次,就是一个破坏性动作。
2. **死循环事故(2026-08-27,W286 触发)**:返回大世界 op 的对话态守卫把全屏 UI 的面板文字误判为对话选项,反复点空白推进陷入死循环;排查确认该画面只有坐标控件可走,按键路径毫无必要。
3. **平台前向约束(用户定调,本条主因)**:项目未来要适配**手机模拟器端**——模拟器无键盘,一切画面操作靠点击。PC 端今天多用一个键,就是明天多一处适配返工;点击路径从现在起就是唯一目标形态。

## Decision Drivers

- **模拟器端点击为主**(主因):键盘输入与目标平台根本不兼容,不是风格偏好而是前向兼容要求。
- **坐标是单义锚**:screen_info 建档的控件坐标「一点就是那一处」,不存在跨画面语义漂移;ESC 是全局单键,语义由当前画面单方面决定,op 无法在按键前验证语义。
- **可验证性**:坐标点击后可读屏验证目标画面;ESC 的效果面(它到底关掉了什么)经常无法在不点击的情况下预知。
- **已有基建零增量**:项目约定本来就是「检测/点击坐标进 screen_info area」(见写完自检),坐标方案不需要任何新设施。

## Considered Options

1. **保留软约束 + 逐案人工判断**(现状):每次写 op 都要重新判断当前画面 ESC 语义,判断成本反复付,错一次就是事故;两次实机事故证明判断会错。
2. **ESC 绝对禁令 + 其余按键尽量不用,一律优先坐标点击**(选中):ESC 是最突出违例直接禁;其余按键(移动/交互键)对模拟器同样不兼容,「尽量不用」给大世界移动这类暂无点击替代的场景留过渡口,确需用要注释声明。规则零歧义,自检可机器化(grep `esc()`)。
3. **按画面白名单放行 ESC**(折中):维护「哪些屏 ESC 安全」的白名单。白名单本身随游戏版本漂移(画面改版语义即变),维护成本高且错了照样出事;且模拟器端最终仍不能用,放行=延迟返工。

## Decision

选 2。SKILL.md 三处落地:必守不变量 #3 升级为「画面操作以点击为主」(ESC 绝对禁令 + 其余按键尽量不用 + 「找不到可见控件 → 报告等裁决」的出口,防被逼着违反);写完自检加「零 ESC + 按键最小化」检查项;跑偏信号同步。存量代码里的 ESC / 按键调用点按各项目自己的节奏迁移,本 skill 只管增量约束。

## Consequences

- **正向**:画面操作形态与模拟器端目标形态一致,适配成本从「全量改」降为「只补触屏交互细节」;关闭/返回行为可建档、可验证、可复审;消除「ESC 这屏安全吗」的重复判断。
- **负向**:每个需要关闭/返回的画面都要先建档控件(建档本就是项目约定,增量主要在「以前用按键偷懒」的场景);大世界移动这类暂无点击替代的键输入要带注释声明,迁移期显式化。
- **follow-up**:各项目存量按键调用点清册与迁移由项目自排(SR 侧已入反馈队列)。
