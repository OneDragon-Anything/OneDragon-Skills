# 写 / 改 / 调试单个 Operation(OneDragon)

OneDragon 的 Operation 是**节点图状态机**:一个 op = 若干 `@operation_node` 节点 + `@node_from` 边。框架每轮截图 → 跑当前节点 → 按其返回的 round 结果沿边找下一节点。**写 op = 先把流程摸清成设计(三份文档),再把设计翻译成节点图代码。**

> 全程守「**看(screenshot/OCR)→ 动(click/key)→ 等(sleep)→ 验(再读屏)**」。别凭猜硬写 —— 凭猜只覆盖一种情况、漏另一种,必回归。

**没做完这 6 步不算完成**(改已有 op 走「修改与调试」的分诊,轻改可免走全程):

1. ☐ 需求确定:一句话目标 + 起终点 + 大致操作,确认要新建后建探索目录落 `requirement.md` → ①
2. ☐ 摸流程:agent 自主驱动实机走查,沿粗线逐跳建档落档,产出 `screen-flow.md` → ②
3. ☐ 拆节点:流转翻译成节点卡(识别→动作→验证→出口),产出 `nodes.md` → ③
4. ☐ 设计确认:向用户汇报四件套,裁定直接写 / 升级迭代设计 / 打回 → ④
5. ☐ 写代码:节点卡逐字段翻译成 round 函数 → ⑤
6. ☐ 验证:mock 快测抓结构 bug → 实机过 requirement 目标验收 → 回归测试落盘 → 最后过 §11 自检收口,全过才算完成

## ① 需求确定(纸面,不上游戏)

先收拢前置信息(用户任务原话 / 玩法文档 / app 编排上下文),**确认要新建这个 op 后**,建探索目录 `.debug/temp/operation-explore/<yyyy-MM-dd-<简述>>/`,需求写进 `requirement.md`(三份文档模板见 `references/explore-docs-template.md`):

- **目标一句话**,合格判据 = 动词 + 对象 + 结果形态:读数类说清**读到什么**;操作类说清**做完后画面/状态变成什么**。一句话塞两件事 = 该拆成两个 op。
- **起点 / 结束画面**:从前置来源收拢(上游编排给的固定起点 / 用户说的;「任意起点」也是合法需求);来源没有的,问用户 / 查玩法文档,**不许上游戏瞎摸代替问**。
- **中间大致操作**:粗粒度动词级(打开 → 读取 → 关闭),细到点哪个区域是后面建档的事。
- **红线(有则声明,普通 op 不写)**:碰真实消耗 / 不可逆操作的 op 必须显式写边界(如「零消耗,永不代点某控件」)。

**完成判据:粗流程线画得出来(起点 —大致操作→…→ 结束)。**

## ② 摸流程(沿需求粗线实机走查,agent 自主驱动)

> 开工前先加载 `od-dev-screen-onboarding`:探索全程随时触发建档与纠档,手法全归它;本章只管时机与流程。

输入 = requirement.md 粗线;产出 = `screen-flow.md` + 沿途建档。agent 经 MCP 截图/点击自主驱动走查。

### 2.1 查地图,只摸未知段

逐画面核对粗线的建档状态:screen_info 建了吗 / id_mark 齐吗 / goto 边在吗 / 画面 doc 有知识吗;兄弟 op 源码是活地图(它的入口集合与走过的路径)。→ 产出已知段/未知段清单,只摸未知段。

### 2.2 主干走查:边走边建边落

从粗线起点逐跳走,每跳一个微循环:

> 截图 → **画面核对(三分支,基准 = 当前帧 vs screen_info 档案)**:
> ① 未建档(新画面) → 按 `od-dev-screen-onboarding` 建档
> ② 已建档 · 内容一致 → 通过
> ③ 已建档 · 内容漂移(area 错位 / id_mark 失效) → 按 `od-dev-screen-onboarding` 纠档(走查即档案体检)
> → 做该画面动作(副作用三档,见下) → 目标屏 id_mark 验转移 → 记 goto 边

- 事实即时归位:yml / 画面 doc 走一步落一步,不回头补(转移证据只在发生的瞬间可见);screen-flow.md 同步长。
- **副作用三档**:可逆(导航 / 开页面 / 切页签)直接做;不可逆但有界(领奖 / 删除)先问用户;消耗 / 高危(抽卡 / 购买)**摸到消耗控件前一步停** —— 控件只读建档(定位 area 但不点击),后果画面靠用户演示或截图补。
- 中断续传:续传入口 = screen-flow.md 走到哪了。

### 2.3 枚举可控变体,不追随机态

| 变体来源 | 判据 | 处置 |
|---|---|---|
| 会话内可枚举 | 当前游戏会话内、不依赖刷新就能逐个到达(页签 / 难度选项) | **现在走全**,子态差异落档 |
| 会话内不可达 | 要等刷新 / 跨天 / 特殊前置(每日随机 / 限时活动) | 记**未知项**留给钩子,不硬等(随机态钩子捕获判据 → `od-dev-screen-onboarding` §1.7) |
| 可达但副作用不可承受 | 到达它本身要消耗 / 不可逆 | **不摸**,消耗控件前一步停,后果画面只读补 |

兜底:拿不准归哪档,**先按副作用档判断**(安全优先),副作用可承受再看会话内可达性。

### 2.4 收口

流程线闭环 + 变体枚举完 → screen-flow.md 定稿(含未知项清单)。

## ③ 拆节点(流转 → 节点卡)

输入 = screen-flow.md;产出 = `nodes.md`(节点总览 + 每节点一张卡)。

### 3.1 有外层循环的玩法,先选结构

**循环驱动** = 外层一个大循环,事先不知道跑多少轮,每轮截图判断「现在什么状态」、做对应推进,直到结束条件(自走棋对局 / 肉鸽一层 / 结算翻页)。这类玩法两种结构,**选错会结构性卡死**(推进不了的动作不记重试,无限烧到全局超时):

- **flat loop**(一个节点装整个循环,内部每轮分类选分支):每个状态是独立反应、点掉就完 → 用它;
- **node-per-op**(每个逻辑单元一个独立子 op,外层只分类委派):状态是有始有终的多阶段单元(如战斗有布阵/开打/结算)→ 用它,单元有自己的重试预算与完成检测。

实现形态(阶梯写法 / committed-but-verifying / 预算)见 `practices/loop-driven-op.md`。

### 3.2 一次流转一节点

**一个节点 = 一次画面流转;不产生流转的完整职责(读数 / 纯计算)也是一个节点。**

- 点按钮出弹窗再点确认 = 两次流转 = **两个节点,禁聚合** —— 每节点出口验证转移是纪律,节点内做两次流转等于第一次流转没验证就做第二步,中途失控无从兜底;
- 读多个数 = 零流转一个职责 = 一个节点,不拆;
- 起点集合 > 1 时,第一个节点是**入口分发**(判当前在哪屏 → 分流到各路径);
- 太细判据:拆出的部分单跑没法自验证 → 归 op 内函数 / 节点。

### 3.3 入口判定归位

- **op 首节点**:做画面级判定(`check_and_update_current_screen`),分发用;
- **中途节点**:默认不判 —— 上游出口验证已保证到达,重复判定白付开销;本节点识别项天然覆盖画面锚时可搭车判,不专门加;
- **防线归出口验证**:run 发现中途画面不对 → 修上游出口验证(锚不够强 / 没带 until),**不加中途判定当补丁**(那是掩盖流转验证的洞)。

### 3.4 复用盘点:子 op 结果 = 分支

已有 op 覆盖流转上的一段,且**它的起点集合 ⊇ 到达该段时的画面、其终点在流转线上** → 调子 op(构造传 ctx,节点内 `op.execute()`)。**子 op 的返回结果是本节点的一种识别分支**,每个结果显式写清处理,不留隐式默认:

```
- 命中 画面A → round_success(status='AT_A') → 节点B
- 都不中 → 子op 回基础画面.execute():
    成功 → round_retry(重入本节点,下轮命中画面A分支)
    失败 → round_fail(status=子op失败原因)
```

反向约束:不为复用把粒度切碎。

### 3.5 变体归位

换的是**怎么做**(同屏不同读法 / 不同点法)→ 节点内分支;换的是**做什么 / 在哪屏**→ 独立节点或入口分发分支。

### 3.6 节点卡格式(分支链)

```
## 节点卡: <节点名>
- 入口画面: <画面名>            (op 首节点标注「需入口判定」)
- 识别项: <(画面, 区域) 列表>
- 分支链(每条: 识别 → 动作 → 验证 → 出口):
  - 命中 A → 点 <区域> → until (目标画面, 锚区域) → 节点 B (status: X)
  - 命中 C → 读 <区域> → 无需验证(不流转) → 节点 D (status: Y)
  - 全不中 → <兜底动作> → 验证 → <兜底出口>
```

分支链与框架运行时语义一一对应(每轮:识别 → 分支 → 动作 → 验证 → round 结果),nodes.md 是代码的直译底稿。

### 3.7 出口与图完整性

- 多出口节点定 **status 集合**(给 `@node_from(status=)` 路由用);
- 三查:每节点有入边可达(无边节点静默不执行)/ 每分支有去向 / 意外画面有兜底出口(转导航或 bail —— bail = 放弃当前单元、带信息显式返回交还上层重新分类,定义详 `practices/loop-driven-op.md`),不许死路。

## ④ 设计确认(人类裁决点)

①②③ 全是 agent 自主推进,到此为止,向用户汇报后等裁定:

- **汇报四件套**:目标 + 起终点;流转概要(几屏几跳几变体);节点数 + 复用点 + 红线声明;**未知项清单**(顺带裁掉:哪些回②补摸、哪些带进⑥实测盯防)。
- **裁定三分支**:直接写代码(多数)/ 升级为正式迭代设计(按所在项目的迭代设计流程,三份稿作设计输入)/ 打回修正(回对应章节改稿,改完**回本节重新裁定**)。
- **agent 先给推荐**(用户拍板):倾向升级 = 涉及消耗/不可逆、多分支多回环、失败代价高、用户表现不确定;倾向直接写 = 路径单一、零消耗、读数导航类、未知项不阻塞。

## ⑤ 写代码(节点卡 → 代码)

先找职责相近的兄弟 op 抄类结构(`__init__` / `handle_init` / 节点声明);对 `@operation_node` 参数、`@node_from` 路由规则、自环陷阱等节点图机制不熟 → 先读 `references/node-graph.md`。然后逐卡逐字段翻译:

| 节点卡字段 | 代码落点 |
|---|---|
| 入口画面(首节点) | `check_and_update_current_screen(screen, screen_name_list=[预期画面集合])` → 返回画面名,据此走分支 |
| 识别项(固定位置,只判定) | `round_by_find_area(screen, screen_name, area_name)` |
| 识别项(漂移文字,last-resort) | `round_by_ocr(screen, target_cn, area=能圈则传, lcs_percent=0.7~0.9)` |
| 读数(停留本屏,不流转) | 自定义读取(`ctx.ocr_service` / reader 函数)→ `round_success(status='…', data=读数结果, wait=…)`;读不出 → `round_retry` 等画面加载 |
| 动作:点固定区域 | `round_by_find_and_click_area(screen, screen_name, area_name, until_find_all=[(画面,区域)], until_not_find_all=[(画面,区域)], pre_delay=…, success_wait=…, retry_wait=…)` |
| 动作:直点已知区域 | `round_by_click_area(screen_name, area_name, click_left_top=False, pre_delay=…, success_wait=…, retry_wait=…)` |
| 导航段(跨屏长途) | `round_by_goto_screen(screen_name=目标, success_wait=…, retry_wait=1)` —— **独占一个节点**;三类报错(起点识别失败/目标未建档/边不连续)全是建档缺口,补档不改代码 |
| 出口(status) | `round_success(status='X', wait=…)` + `@node_from(from_name='本节点', status='X')`;同族 `round_wait / round_retry / round_fail(status, wait)` |

- **until 语义**:`until_find_all` = 点击后这些区域**都出现**才算成;`until_not_find_all` = **都消失**才算成。机制:首次点击成功后开始验,验不过 → `round_wait` 后**再点再验**(不是干等)—— 锚选错会反复点,锚的选取见节点卡设计期把关;
- **wait 一律显式填**,按实机动画过渡时间;`wait_round_time` = 等待总时长减本轮已耗时,不是「再睡 N 秒」;
- **固定位置元素压倒性默认用区域识别**(坐标进 area = 单一真相源 + 不全文扫);全屏 `round_by_ocr` 是 rare last-resort —— 框架默认 lcs 0.5 是子序列匹配,关键词与别处共享 2+ 字子串即误匹配,lcs 收紧救不了全等;**坐标禁硬编码 `Point(x,y)`,一律进 screen_info area**;
- op 内工具箱(screenshot / ocr_service / 子 op / 非节点上下文原语)细节见 `references/round-by-helpers.md`。

## ⑥ 验证(三层递进,便宜的在先)

**三层分工**:mock 快测抓结构逻辑(开发内循环,与写码一起迭代);实机验证识别 / 时序 / 意外分支(实机是唯一真相源,验收在这);回归测试在实机稳定后落盘锁行为(实机会改代码,锁定测试先写就是白写)。纯函数(解析/计算)不依赖实机,写码时顺手测。

### 6.1 mock 流程快测(无实机,秒级)

测试仓的假控制器 harness 按剧本演:喂截图序列,点击落在区域就推进下一步,op 完整流程不开游戏跑完(mock 截图注入 helper 的形态见 `references/testing.md`)。⑤写完代码**先跑这个**,抓结构性 bug——节点图路由接错 / status 分流错 / 分支走反 / 翻译错误,别开游戏抓低级错误。剧本素材 = ②探索沿途截图(每跳的「画面截图 + 点击区域 + 下一画面」就是剧本原料)。

### 6.2 实机单跑

`run_operation '<op_id>'` 单跑:

- 验收基准 = requirement.md 的目标一句话(结果形态);未知项盯防 = screen-flow.md 未知项清单逐项过;
- **日志纪律**:status 写给人看的诊断句(框架每轮打它,它就是日志主体,禁写 'ok'/'fail' 废字);读数节点把读到的值落日志;retry / fail 时 `self.save_screenshot(prefix=节点名)` 存图,文件名进日志(返回空串 = 没存上,别当存上了);
- **预料外画面 / 行为 → 回②补档补分支**(不是就地硬修),循环到稳定。

### 6.3 回归测试落盘

实机稳定后锁行为:纯函数契约 + 流程分支路由。**素材进仓时机 = 写测试时**:fixture 素材从探索存证与调试截图中按断言需要挑进测试仓(需求驱动取材,不预归档),挑完才做收尾清理。纪律见 `references/testing.md`。

### 6.4 交付

交给调用方:**接入 app 编排**(→ `od-dev-write-application`)或**作为 MCP 可调单元直接用**(`run_operation` 即入口)。探索目录收尾:有价值的画面样本进正式归档,其余清理。

## 7. 最佳实践(按场景取用)

你的 op 有以下特征时,先读对应实践文档再动手;新实践 = 加文档 + 本表加一行。

| 特征 | 实践 |
|---|---|
| 外层循环不断跑、每轮重新发现状态推进(自走棋 / 肉鸽 / 多阶段) | `practices/loop-driven-op.md` |
| 列表 / 网格内 N 个同类目标要识别(角色选择 / 图标阵列 / 卡面网格) | `practices/list-grid-recognition.md` |
| 选择类画面:选项 + 推进按钮 | `practices/select-and-proceed.md` |

## 8. 必守不变量

1. **画面操作以点击为主,禁 ESC,其余按键尽量不用**:关闭 / 返回 / 退出 / 跳过一律建档后点画面控件;其余键盘确需用时注释声明键名与原因。理由:前向兼容无键盘的手机模拟器。
2. **MCP click/key 异步**:立即返回但 ~1s 才落地;操作后 sleep ~1.5s 再验,否则截到点击前画面(`references/framework-pitfalls.md`)。
3. **调试先读日志**,不盲点坐标(方法见「修改与调试」)。
4. **多样本核实**:验证 OCR / 读取器跨多样本看统计分布,别凭一张图 / 单次推断下结论。
5. **决策点多 log 多截图**:判据 = 实跑后看日志能复盘每个决策点发生了什么;做不到 = 日志不够,补(完整展开见 `references/runtime-craft.md`)。
6. **重复手动操作 2+ 次 → 尽早建成 op**(`run_operation` 一键调,别每次手动点 N 个按钮)。

## 9. 修改与调试(先分诊,再走路)

### 9.0 分诊:这次改动是什么性质?

- **A 行为不符合设计(bug)** —— 设计是对的,实现 / 档案出了偏差 → **调试路径(9.1-9.5)**;
- **B 设计本身要变**(需求变 / 游戏更新 / 改行为)—— 实现忠于旧设计,但世界变了 → **修改路径 = 重走主线**:①「改什么」= 新行为一句话;②现状核对替代从零摸(设计稿还在 → 沿受影响段实机走查对照找漂移;已删 → 从代码反推(docstring 契约 + `@node_from` 节点图)+ screen_info/画面 doc 活档案,实机核对受影响段,三分支画面核对同②);③④⑤⑥照走。
  - B 内嵌判据:改动**触碰画面流转结构** → 完整重走(探索目录重建,三份稿恢复到现状再改);不触碰(改参数 / 文案 / 换坐标)→ 改档案或代码 + 单 op 实测即可,不建设计稿。

### 调试路径(9.1-9.5)

> 铁律:**只有明确复现流程,才能修改。** 你不在场的事后排查归 `od-dev-debug-automation`。
> 日志纪律的完整展开(reader 输出契约 / 预料外画面调研 / 钩子代码手法 / 画面定型门)见 `references/runtime-craft.md`。

**9.1 定位根因(不猜)**:
① 对照偏差:日志节点流转序列 vs nodes.md 设计路径,偏离点即调查起点;
② 还原现场:最后画面状态是什么(截图 / 识别,可能未建档)+ 怎么形成的(日志回溯:从哪个正常点开始偏、偏离时的直接动作是什么);
③ 归因假设,三类之一:识别错(area 不准 / 档案漂移 / OCR 误匹配)、流转设计错(分支不全 / 锚选错)、纯代码 bug;
④ 日志回答不了 → **补观测再跑,不盲猜**:决策点加临时日志(OCR 原文摘要 / 识别命中结果 / 走了哪个分支 / 点击目标)+ `self.save_screenshot(prefix=节点名)` 逐轮存证(返回空串 = 没存上),文件名写进日志行。

**9.2 手动复现(验证假设)**:按推断的形成路径,把游戏带到同样的前置状态重放同样操作。稳定复现 → 根因成立,进 9.3;复现不了 → 归因有误 / 时序随机因素,回 9.1 再挖。

**9.3 按层修复(回主线对应步)**:识别错 → 回②补档纠档;流转设计错 → 回③改节点卡 → ⑤改代码;纯代码 bug → 直接改。一次只改一个变量,改前写明「根因是 X,改 Y 应见 Z」。

**9.4 验证与防回归**:复现路径 = 验证剧本(同样前置状态重跑,偏差消失才算修好);能稳定复现的 bug 落测试(fixture 重放复现场景 —— 复现流程是可测试性的前提)。

**9.5 调试收尾**:临时日志按价值取舍(低频决策日志开销可忽略,可留转正;高频轮次噪声去掉);**临时截图必删** —— 有价值的画面样本(新画面 / 新子态)先按建档流程进正式归档,其余全删(截图是一次性取证快照,日志是行为记录)。
