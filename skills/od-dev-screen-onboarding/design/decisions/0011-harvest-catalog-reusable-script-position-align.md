# 0011. 采图鉴模板库:脚本持久化为可复用工具 + 标签图标按空间位置对齐

- **Status**: accepted
- **Date**: 2026-08-06

## Context
§5 情形 3(采图鉴模板库:模板库来源优先游戏内图鉴 + 采全)原本只说「定位 + 裁」,没说采库脚本的**生命周期**与**标签↔图标对齐法**。一次实际采库(某分页式图鉴 —— 名字标签 + 图标网格,可滚动;采上百件模板)暴露两个 gap:

1. **脚本当一次性产物**:采完把脚本扔进会被清理的临时目录,下个游戏版本图鉴新增 / 改动实例时,要重写整套定位 + 裁剪 + 存名逻辑。
2. **标签↔图标按行索引对齐出错**:图鉴里名字与图标分两区(名字在上、图标在下,同列对应)。采库脚本按「检测到的第 N 行图标 ↔ OCR 的第 N 行名」对齐 —— 但滚动后**顶行图标被面板边裁切**(只剩半截)→ CV 漏检顶行 → 图标行索引比名字行索引少一 → **整行名贴错图**。且 x 若取名字中心对齐图标,名字长短不一(两字 vs 五字)会偏心。

## Decision Drivers
- **版本鲁棒**:图鉴每版本更新会变,采库要可重跑补采。
- **可维护 / 不重写**:重复任务的脚本应持久化,而非每次重造。
- **正确性**:标签与图标的关联必须在对齐方式上抗「CV 漏检个别行」。

## Considered Options
1. **采库脚本持久化为可复用工具**(选中)vs 当一次性产物扔临时目录:后者下版本重写整套定位 / 存名逻辑(实测重写成本不低)。
2. **标签↔图标按空间位置对齐**(选中)vs 按「检测行索引 ↔ 名行索引」对齐:后者在「CV 漏检顶行(被裁切)」时索引错位 → 整行贴错,而空间位置(OCR 名 y + CV 检测的列中心)不受单行漏检影响。
3. **存图编码**:沿用 §6 转换工具已立的 `cv2.imencode + ndarray.tofile`(非 `cv2.imwrite`,Windows 中文路径挂)约定 —— 非新决策,见 [ADR-0008](0008-bundled-webp-tool-inline.md),此处只是让采库脚本守同约定。

## Decision
两条方法论进 §5 情形 3(指令式 + 判据,非具体游戏例子):
- **脚本持久化**:采库脚本(形状轮廓定位 + 紧贴裁 + 按规范名存)存进**项目持久脚本目录**,docstring 写采集流程(图鉴源 / 解锁前提 / 滚动采全判据 / 标签对齐法),版本更新照着重跑;别扔会被清理的临时目录。
- **标签↔图标按空间位置对齐**:按 OCR 名的 y + CV 检测的列中心对齐(固定空间关系),不按行索引(顶行被裁切 → CV 漏检 → 索引错位);x 取图标列中心,不取名字中心(长短不一偏心)。

**不进 skill 的(归项目实现)**:脚本确切路径 / 命名(项目约定,如 `tools/<ns>/harvest_*.py`)、对齐用的具体偏移常量(图标中心 = 名 top − 定值,实测调参,属 doc / 代码)。

## Consequences
- **正向**:版本更新重跑补采(不重写);对齐抗「CV 漏检个别行」(整行不错贴);存图编码与 §6 一致(无第二套约定)。
- **负向 / 边界**:假设项目有「持久脚本目录」约定(skill 不规定确切位置,只说「项目持久脚本目录」);`imencode + tofile` 在 §5 / §6 两处提及(轻重复,以 §6 引用收口,可接受 —— 两处是不同操作:裁模板存 PNG vs 归档存 webp)。
- **推翻它会碎什么**:删持久化 → 每版本重写采库脚本;删位置对齐 → 滚动采库时整行名贴错图。
