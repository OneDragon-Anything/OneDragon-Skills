# 0012. 卡住画面协议:判据触发后的强制可执行探索 + 禁干卡(补 ADR-0010 执行体)

- **Status**: accepted
- **Date**: 2026-08-06

## Context

ADR-0010 补了「调试撞陌生画面 = 建档信号(非快修信号)」的触发面(`description` 被动触发)+ 建档/快修硬判据(说不出全部可交互元素 + 各自点后跳哪 → 先建档)。实战(2026-08-06,某肉鸽式玩法开发)暴露**判据之后的执行 gap**:

开发中卡在一个**状态不清的 overlay** 上连续多轮,虽知有建档协议,却既没回溯怎么进来的、也没系统摸索出口、更没穷举交互观察 —— 而是**干卡 + 无系统、无观察地盲点**(更糟:盲点还无意触发了拖拽类副作用,因没做交互前后状态对比而**毫无察觉**,直到状态被搞乱才发现)。

根因不是「不懂方法论」(ADR-0010 判据 + `od-dev-write-operation` runtime-craft「预料外画面调研」3 步都写了),而是三层:

1. **判据是抽象提问**(「能说出全部可交互元素吗」),没和「我卡住了」这个心智态直接挂钩 —— 卡住时心智上是「不知怎么出去 / 下一步干啥」,不会主动去问那个判据问题。
2. **判据触发后没有可操作执行步骤**:系统找出口 / 穷举交互观察 / 交互前后状态对比 / 禁干卡**全缺**。判据只说「该建档」,没说「状态不清的动态画面怎么把行为 map 出来」(§1-§6 的静态建档流程假设能相对静态地 analyze,但状态不清的 overlay 得**主动交互**才搞清行为)。
3. **协议形态是软叙述**,不是「压力下明知故犯」该用的**禁令 + 强制 checklist**(od-dev-writing-skills `writing-craft.md` §1.5 form-to-failure:知道规则但不做的高发失败,正确形态是禁令 + red flags,软建议反而会被谈判跳过)。

这是**通用方法论 gap**:任何玩法自动化遇状态不清画面都会卡;「卡住 → 干卡 / 盲点不观察」是任何智能体在不确定环境下的高发失败模式。非某具体玩法 / 模型 / 环境特异。判据是方法论(怎么把认知不完整的画面行为补全),非具体游戏例子。

## Decision Drivers

- **form-to-failure(明知故犯)**:协议要可被「卡住」态强制触发,而不是「知道但跳过」→ 禁令 + 强制 checklist,非软建议。
- **可操作性**:判据说「该建档」之后,要有步骤化的「怎么 map 出动态画面行为」(回溯 / 找出口 / 穷举交互观察 / 状态对比)。
- **单源 + 不漂移**:画面行为探索(搞清全部可交互元素 + 点后跳哪 = 建档)归本 skill;op 级「回溯入口 + 改 click 避免误触」归 `od-dev-write-operation` runtime-craft。两者描述同一动作的不同层面,要对齐引用、不双写。

## Considered Options

1. **只靠 ADR-0010 判据 + write-operation 3 步(不改)**:判据已存在,实战仍连续违反 → 证明 prominence(没和「卡住」态挂钩)+ 可操作性(缺执行步骤)都不足。**否**。
2. **只加软建议(「建议系统探索 + 交互前后状态对比」)**:form-to-failure 说明知故犯用软建议无效 —— agent 会和「prefer…」谈判跳过(实战正是如此:知道该建档却干卡)。**否**。
3. **强制可操作 checklist + 禁令(选中)**:判据触发后给 5 步执行序列(回溯怎么进 → 系统找出口 → 穷举交互观察 → 交互前后状态对比 → 收尾判据)+ 「禁干卡」red flag + 「卡住 = 触发信号,不是再试一次的信号」心智锚。把抽象判据和「卡住」态直接绑定。
4. **协议写进 write-operation runtime-craft(不写本 skill)**:画面行为探索本质是**建档动作**(搞清全部可交互元素 + 点后跳哪 = 建档认知),ADR-0010 已定「debug 撞陌生画面 → onboard 不 patch」= 归本 skill。write-operation 保持 op 级聚焦(回溯入口 + 改代码避免误触),加引用对齐即可。**否(归属错位)**。

## Decision

选 3(+ 对齐 4 的归属划分)。

- **画面行为探索协议**写进本 skill SKILL.md「卡住画面协议」(建档/快修判据触发后的执行体):5 步强制 checklist + 「禁干卡」禁令。
- **`od-dev-write-operation` runtime-craft**「预料外画面调研」节末加引用 → 指向本 skill「卡住画面协议」做「搞清画面全部交互行为」的完整方法,自己保持 op 级聚焦。画面行为探索 single source 在本 skill。
- **`od-dev-gameplay-automation` SKILL.md 调试纪律**补「区分两种卡住」:op 执行失败 / 报错(技术故障)→ 读日志(write-operation);卡在状态不清 / 未建档画面(认知卡住)→ 本 skill「卡住画面协议」。让「认知卡住」态在 always-on 层被显式路由(解决 prominence —— 光靠 description 被动触发不够可靠)。

判据复用既有方法论(§信息源三层 / §2 open 探索 / ADR-0009 三工具交叉),不引入新工具。step 3 穷举交互观察引用 §2 探索技巧(open 枚举 + click 验证),不重复。

## Consequences

- **正向**:判据触发后有可执行步骤;「禁干卡」red flag + 「卡住 = 触发信号」把抽象判据和「卡住」心智态挂钩;step 4 状态对比防盲点交互的副作用悄悄累积。
- **负向**:SKILL.md 变长(协议本体 ~15 行);checklist 在可交互元素多的画面执行成本不低,但「认知不完整」本就值得停(ADR-0010 已承认此代价)。
- **边界**:协议是建档方法论在**动态 / 状态不清**场景的可操作化,**不替代** §1-§6 静态建档流程,而是其前置探索 —— 认知补全后回正常建档(§3)。复用 §信息源「对齐判据」作认知完整的收尾判据。
- **未做**:把「卡住画面协议」也内联进 gameplay-automation SKILL.md(会双写);只在其调试纪律做路由指向。
