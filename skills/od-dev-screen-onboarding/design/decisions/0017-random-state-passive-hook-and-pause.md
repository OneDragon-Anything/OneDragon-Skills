# 0017. 随机/条件态:被动钩子捕获 + 触发停当场建档(非请用户帮切),自主开发默认

- **Status**: accepted
- **Date**: 2026-08-11

## Context

原「边缘状态态」节(依赖游戏条件 → 人机协作)给的处理:① doc 标「待条件」+ ② **请用户帮切**(用户调游戏状态造条件)+ ③ 后续会话补。memory `onboard-hook-capture-random-states` 记了「代码钩子 + run app 跑一遍自动存图」法(SR 模拟宇宙实证),但 skill 正文没固化,主推「请用户帮切」。

2026-08-11 skill feedback 指出三层问题:

1. **随机态是自动化开发常态,不是边缘**:几乎每个玩法都有几个会话内造不出的态(CW 实例:穿戴装备 3 件态[需 owned 多件穿戴类且不合成,补给节点随机]、祈愿试炼 overlay[备战随机出现]、read_equipped 边缘 MISS 值)。「边缘」标题误导。
2. **「请用户帮切」违背自主开发**:依赖用户在场 + 手动操作;一次只捕一个态,效率低。bot 本就要自主跑很多局(造数据 / 测流程),被动钩子让 bot 跑的过程自动捕获,零额外成本、覆盖广。
3. **只存图离线建不够(用户补充)**:珍贵随机态错过不知何时再遇,光存图离线建会漏 —— 很多建档工作必须当场(穷举交互验行为 / 实时 analyze 看动态反馈 / 点后跳转),离线只看图做不了。遇到珍贵态该**当场停下来完整建档**,钩子的作用要从「存图」扩到「检测到 → 触发停 bot 留在该画面 → 当场建档」。

三种错法(现状):卡在随机态等(阻塞)/ 硬刷造概率(空跑)/ 标「低价值跳过」(漏建)。

## Decision Drivers

- **自主开发优先**:随机态常态,主推法应不依赖用户在场(请用户帮切依赖用户,违背自主)。
- **珍贵性(机会成本)**:随机态错过不知何时再遇 → 遇到时优先当场利用机会完整建档(不只存图)。
- **当场 vs 离线判据**:该态建档要不要当场交互验证行为?要 → 触发停当场建;不要(静态画面存图够)→ 存图离线建。一刀切「全存图离线」或「全请用户帮切」都不对。

## Considered Options

1. **保持「请用户帮切」为主推**:依赖用户在场、违背自主、一次一个低效(否)。
2. **纯被动存图 + 离线建档**:覆盖广但漏当场交互(珍贵态离线建不全)(部分用,静态态)。
3. **硬刷造概率**:空跑耗资源(否)。
4. **被动钩子 + 判当场 vs 离线(选中)**:静态态存图离线建;需当场交互的态钩子触发停 bot 当场建。自主 + 覆盖广 + 珍贵态不漏。「请用户帮切」降级为可选加速。

## Decision

选 4。SKILL.md「边缘状态态」节升级为「随机/条件态」:
- 改标题(「边缘」→「随机/条件」,反映常态非边缘)。
- 加「珍贵性」段(错过不知何时再遇 → 优先当场建全)。
- 标准做法 6 步:别硬刷别卡 / 埋被动钩子 / **判当场 vs 离线**(静态存图离线建;需交互触发停 bot 当场建 §1-§9)/ 进度记进行中不当阻塞 / 绕开做别的 / 捕完回滚钩子。
- 「请用户帮切」降级为可选加速(非默认)。
- 实现细节(钩子怎么发信号 / 阻塞 op 让 bot 停在该态)是 op 层运行时技术,指向 `od-dev-write-operation` runtime-craft,本节只讲方法论判据。

## Consequences

- **正向**:随机态不再卡 / 硬刷 / 漏建;自主开发不依赖用户在场;珍贵态当场建全(不漏交互行为);覆盖广(bot 跑久自然遇)。
- **负向**:埋钩子 + 触发停需改代码 + 重启 server;判当场 vs 离线需写者按该态建档需求判断(软执行)。
- **边界**:本节是画面建档方法论;op 测试 / 玩法数据采集遇随机态同适用(gameplay-automation / write-operation 可引用,待补)。**「触发停 bot 留在该画面」的 SR 实现是项目级,不进公共 skill**(SR 侧调研待办见 SR CLAUDE.md)。
