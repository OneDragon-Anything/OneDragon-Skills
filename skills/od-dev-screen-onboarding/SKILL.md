# 画面建档(看 → 验 → 建 → 建模 → 归档)

拿到待建档的截图后,按必做流程执行。**建档完成 = 能说出当前画面全部可交互元素 + 各自点后跳哪,且产物(screen_info / doc / fixture / id_mark 测试)全落。**

**没做完这 7 步不算建档完成**(详判据见对应 §;主流程只放可勾动作,判据 / 踩坑 / 方法论在 § 里,不在此重复):

1. ☐ 判定:该建档吗(建档 / 快修硬判据)+ 排除跨玩法偏离 + 规模判定 → §1
2. ☐ 看:`analyze_screen` 客观识别 + 视觉大模型主观理解(每张截图必看) → §2
3. ☐ 验:穷举交互验证行为(探查纪律:不可逆出口最后),跳转边落 `goto_list` → §3
4. ☐ 建:screen_info(SCREEN 全建 / AREA 增量 + id_mark)+ 画面 doc(四问定归属) → §4
5. ☐ 建模:图形 / 图标截模板(文字走 OCR) → §5
6. ☐ 归档 fixture 到测试仓 + 跑 id_mark 准确性测试 → §6
7. ☐ 过 §8 自检收口,全过才算完成

## 1. 建档前判定

### 1.1 何时该建档(主动 + 被动两种触发)

1. **主动**:拿到待建档的游戏截图(建新画面 / 维护 screen_info)。
2. **被动(调试中,别漏)**:调试 / 修 / 排查 op 时,op 卡在一个你**不完全认识其交互**的画面 / 子屏 / 交互上(卡死 / 报错画面不符 / 找不到 op 假设该有的按钮)→ **先建档搞清画面,再继续改 op**。

**建档 vs 快修 判据(硬规则)**:你能说出**当前画面全部可交互元素 + 各自点后跳哪**吗?

- **能**(screen_info 的 `area_list` 已覆盖 + op 代码流转已读清)→ 画面认知完整,继续 debug / 改 op。
- **不能 / 只能猜**(有元素没建模、点后跳哪未知)→ **先建档**(走 §2-§6:analyze + 视觉大模型开放式探索 + 逐元素点击验证),别在不完整的画面认知上猜退出机制 / 套兜底结构 / 改 op。状态不清的动态画面(覆盖层 / 不知怎么进来的子屏)→ §3.3 强制探索协议。
- **跨玩法偏离**(认知完整但非目标玩法)→ 不是建档问题,走 §1.2 导航回,别停、别建档。

### 1.2 跨玩法偏离协议(cross-mode drift):认知完整但非目标 → 导航回,禁止停

bot 在目标玩法 A 运行 / 调试,`analyze` 命中**非 A 玩法** B 的画面 —— 你**认得出是 B**(认知完整),但 B **不是目标** A。这**不是「卡住」**(卡住 = 认知不完整 → §3.3 探索补全),也**不是「环境状态可忽略」**(「用户在玩」就跳过)—— 是 bot 偏离了目标,**必须导航回 A 继续,禁止停**。

判定(`screen_name` 属 B 不属 A / OCR · 视觉特征指向 B / `is_precise` 模糊但落到 B):

1. **回溯偏离源**:读日志 / op 历史 / bot 上一步动作,定位怎么从 A 落到 B(误点跨玩法入口 / 上次 bot 残留未退 / 用户手动切走)。搞清入口常直接揭示恢复路径。
2. **找 B 出口**:用 B 画面的退出 / 返回手段(查 B 画面档案的状态流转出口)回到通用枢纽画面(大世界 / 主菜单类)。
3. **导航回 A**:从枢纽走 A 的入口导航路径(查 A 的 screen doc / application 代码里的入口节点链)。
4. **回 A 继续工作**:偏离不构成停的理由 —— 导航回目标是 bot 的职责,不是中断 / 等指示的理由。
5. **建档防再偏**:偏离路径(A→B 误触入口)+ 恢复导航步骤链入 screen_info(`goto_list` / area)与 screen doc「状态流转」,供后续遇同偏离自动恢复。

### 1.3 建档规模:单画面 vs 重 app

**重 app 多子玩法**(1 app 调度多子 op、每子玩法独立画面 + `入口→子玩法→返回入口` 循环,判据:≥3 子玩法、各独立画面)→ 按 **app 维度**建档,不是逐画面零散:

1. **入口画面 + 各子玩法画面**各自建档(每画面独立 doc,或同 doc 多子态)。
2. **app 编排**(节点链 / 分支 / 入口循环)单独成 develop doc(项目的 `docs/develop/` 下),不进 screen doc。
3. **玩法机制**(目标 / 资源 / 循环)进 gameplay doc → 此时**触发 `od-dev-gameplay-automation`** 对玩法建档(不在本 skill 内直接写玩法,避免写成代码说明书)。
4. **跨画面 op 联动**(子 op 委托另一个 op,如缺料 → 跳补料):screen doc 记「跨画面流转入口」,develop doc 记编排。

单画面 / 独立 app 走 §2-§6 常规流程。

### 1.4 玩法画面:先搜攻略理解机制(再读代码 / 画面)

判据:画面属于**具体玩法**(有独立目标 / 资源 / 循环的 app,如周限 / 副本类)还是**通用流程**(大世界 / 菜单 / 任务 / 背包 / 战斗等基础 UI)。

- **玩法画面**:建档前先搜攻略 / wiki 理解「这玩法是什么、目标 / 资源 / 循环、入口 / 走哪些画面」,再读 `application/<app>/` 代码 + `analyze_screen` 建档 —— 先有玩法理解,读代码 / 画面才高效,避免凭代码猜流程、漏画面。
- **通用流程**:直接走「信息源三层」+ analyze 建档,不必深搜。

### 1.5 信息源:理解画面三层并用

截图只覆盖「当前帧看得到」的;画面背后的结构信息要另外拉。建档前并读三层:

1. **截图** → `analyze_screen`(客观 area/OCR,§2.1)+ 视觉大模型(主观布局/状态图标,§2.2)。
2. **screen_info**(`area_list`)→ 该画面**全部已建模元素**,含当前帧未显示的子态 area(如弹窗按钮)。每个 area 的 `text`/`template_id`/`pc_rect`/`goto_list` 直接说明它是啥、点后跳哪。**analyze 只返回当前帧命中的 area,screen_info 才是全集**。
3. **application/operation 代码** → `@operation_node` 链 = 画面跳转与状态流转;`round_by_find_and_click_area` / `round_by_goto_screen` 调用 = 在哪画面点哪 area。

**对齐判据**:doc 的「可交互元素」「状态流转」要与 screen_info `area_list` + 代码**逐条对齐** —— screen_info 有、doc 无 = 建档漏,补上。

**版本迁移核对(老 app / 大版本更新后必查)**:代码可能落后于游戏版本 —— 判据:**建档前核对 op 代码假设的画面元素(tab / 按钮 / 流程)在当前游戏版本还在吗**,不假设「代码 = 当前游戏」。发现不符:① doc 记版本差异 + 标「代码与当前版本不符」;② 搜官方更新说明确认改动版本;③ app 层若有占位短路说明已知情,标「待重写」。代码默认有效是建档盲区。

### 1.6 截图获取:手动分解动作,不靠跑 app 中途

跑 app / 跑单个 op 中途截图 **抓不到中间态** —— op 执行快、且会自动消费中间画面(确认弹窗被 op 自己点掉),sleep 完再截图只能看到跑完的结果。判据:**app/op 内部连续动作产生的画面,按 op 的 `@operation_node` 节点逻辑手动分解成单步** —— 读 op 代码,每步一个 `click_game` / `key_tap` / `drag` + 截图,逐步截图(在 op 会自动点的弹窗处**停下、手动不点、先截图**)。跑 app / `run_operation` 只用于「验证流程通」或「到位」。

**操作时序**:
- **操作后等动画再截图**(否则截过渡帧):底层 `click_game` / `key_tap` / `drag` **无内置等待**(等待在框架 operation round 层,MCP 不经 round)。sleep 建议值:click ~1s / move ~1s / interact 1-2s / esc ~0.5s / drag ~0.5s;move 后必须等角色到位(不等就紧接 interact 会失效)。
- **拖拽后先把光标停靠到空白惰性区再拍**:落点停留的光标会让该处元素呈**悬停渲染**(抬升/亮描边)入帧 —— 当真值帧用 = 模板/断言被伪影污染;带悬停态的帧只能作干扰样本且显式标注。

### 1.7 随机/条件态:会话内造不出 → 被动钩子捕获,不硬刷不卡

很多状态会话内**主动造不出** —— 依赖概率 / 罕见条件(稀有掉落、特定词缀组合、到期 / 材料不足 / 刷新稀有),非「导航可达」。判据:**状态依赖「资源消耗 / 时间 / 随机」而非「导航可达」= 随机/条件态**,标「待条件」,别硬刷。

**三种错法**:① 卡住等(阻塞,等不到空转);② 硬刷(主动反复跑造概率,空跑耗资源);③ 标「低价值跳过」(漏建 → op 遇上盲点)。

**珍贵性**:随机态错过不知何时再遇 → 遇到时**优先当场完整建档**(不只存图 —— 穷举交互验行为 / 实时 analyze / 点后跳转只能当场做,离线只看图会漏)。

**标准做法(被动钩子 + 绕开)**:
1. **别硬刷、别卡住**。
2. **埋被动捕获钩子**:在代码运行路径(画面判定 / 状态读取 / 事件处理函数)加**临时钩子**:检测到目标随机态 → 存图(按子态名去重存 PNG 到临时目录;中文路径 `cv2.imencode` + `ndarray.tofile`)。改代码后重启 MCP server 生效。钩子代码实现见 `od-dev-write-operation` runtime-craft「钩子触发停 bot 留画面」节;本节只讲判据。
3. **判建档方式**:**静态态**(存图够离线建)→ 钩子存图、bot 继续跑,离线 `analyze_screen(screenshot=钩子图)` 建;**需当场交互的态** → 钩子检测到即触发停 bot 留画面(存图 + 发信号),**当场跑建档流程 §2-§6**,完了恢复 bot + 回滚钩子。
4. **绕开做别的**:未遇上的随机态不卡,先推进不依赖它的活。

**停机后画面已流转(只剩存证截图)→ 离线降级**:① 离线 `analyze_screen(screenshot=存证截图)` 判画面态合法性(**非法 = 钩子误触发的证据,回头修钩子前置门**,别拿非法帧建档);② 合法 → 视觉大模型客观描述补全(原图直喂别先裁剪);③ 按 §2-§6 建档但标「离线降级:交互验证缺,待现场补」—— 别把视觉大模型推测当交互事实。

**「请用户帮切」降级为可选加速**(用户在场 + 容易切时),非默认。

## 2. 看画面(客观 + 主观,缺一必漏)

### 2.1 客观识别:跑 `analyze_screen`

`analyze_screen(screenshot=<绝对路径 或 .debug/images 图名>)`,取三样:
- **匹配画面** `screens[].screen_name` + `is_precise`(精准 / 模糊 / 无匹配)。
- **匹配 area** `screens[].areas`(area_name / 类型 `text`|`template` / 文本或 `template_id` / conf / 位置)。
- **全量 OCR** `ocr_texts`(全部文字,含噪声/动态值)—— area 维护的文字可能不全,全量 OCR 是权威文本源,与匹配 area 的文字重叠属正常,勿去重。

### 2.2 主观理解:视觉大模型看图(必需,不只靠 MCP)

**每张建档截图都要视觉大模型看一遍**(漏看会导致元素、画面边界或状态判断不完整)—— OCR 看不见:图形 / 图标按钮、布局结构、状态图标(选中态 / 已读 / 可领)、模态性(遮罩)、角色朝向 / 场景类型。**调用失败(如 400)必须重试**(换图重传 / 重新截图),不能跳过。

若用户给了**画面相关提示**,向视觉大模型提**偏向该类画面典型元素**的问题(提示指向某类画面 → 问该类的典型可交互元素 + 状态文本;无提示 → 通用问布局 / 可交互元素 / 文字 / 图标 / 当前状态 / 模态性),并明确区分**可交互元素**与**展示信息**。

**视觉大模型纪律(踩坑固化)**:
- **状态推理不可信,只信客观描述**:它「描述画面有什么」可信;「判断状态 / 作用」(已完成 / 未完成、按钮作用、是否可点)不可信(会基于看到的文字瞎猜)。提问要客观描述(「有哪些文字 / 按钮 / 图标?各自位置?哪个元素有高亮 / 颜色标记?」),别问状态推理(❌「是已完成还是未完成?」);**状态判断结合代码自己做**(看 op 代码里的判定 area / 返回标志)。
- **可交互对象判据(游戏特定的交互标记)**:很多游戏对可交互对象(NPC / 采集点 / 装置)有**标记**(名字旁符号 / 高亮 / 图标),出现即在交互范围。⚠️ OCR 常漏标记符号、视觉大模型也不懂这约定 → 双双误判「没到还要走」。判据:画面出现目标对象 + app 假设该位置可交互 → **直接试交互键**,实际选中的对象看结果画面(交互提示文本未必是实际交互对象)。**本游戏的交互标记约定归项目 `docs/game/screens/` 约定 doc,不在本 skill 硬编码** —— 建档前查它。
- **角色朝向/视角判据(盲区)**:视觉大模型不懂第 3 人称追尾等摄像机语义(追尾视角下「看到角色背部 = 角色正对前方」,它会误判「背对」)。朝向以 OCR 交互提示(如「前往 XX」)+ 实际 interact 的结果为最终判据。
- **画面信息不重复告诉视觉大模型(独立原则)**:它自己能看画面,别替它描述(「画面上有 X」)—— 你的复述 = 你的理解,可能错,反而带偏。
- **认知画面元素:开放式提问 + 三工具交叉 + 穷尽自查**:画面未知时视觉大模型单看会漏(注意力受显著性驱动,漏非显眼区域 / 非文本状态)。**开放式提问**(不预设找什么,让它自由枚举;❌诱导式窄问「X 在哪」压制输出)+ **三工具交叉**(视觉大模型视觉枚举 / OCR 文字权威源 / 点击交互验证;冲突即信号)+ **三工具都做完仍不清才问用户**。
- **怎么交互推进(认知未知画面时)**:① 首问零知识:「当前画面怎么交互才能推进?」;② 给了方式 → 试,**无效不放弃,叠加失败继续问**(「刚试了 X 没用,还有别的交互方式吗?」);答不出 → 问它「你需要什么更多信息才能判断?」,只按它说的查、只回答它要的(别假设它缺什么 —— 该补什么的决定权交给它);③ 查证来源按性质选:外部权威优先(游戏内图鉴 > 攻略网站;本地代码 / 文档可能含猜测污染,查到标存疑、与外部交叉、不一致以外部为准);④ **穷尽才升级**(它给不出新方式 + 提不出新需求 → 才问用户)。

## 3. 验交互(认知 = 能说出全部元素 + 各自点后跳哪)

### 3.1 穷举可交互元素

**area 齐 ≠ 交互验证完**:area 在 screen_info / `analyze` 命中 = 该坐标有元素(**存在**),≠ 点它跳哪 / 可不可点 / 是不是纯显示(**行为**)。逐个 click 验证才能确认行为。

**清单穷尽,别只靠视觉大模型枚举**(它单看会漏非显眼 / 小元素 / 非文本状态)—— 交叉补全:全量 OCR + 信息源三层(screen_info `area_list` 全集 + 代码 `@operation_node` 链)。**什么算可交互元素别预设**:除明显按钮 / 输入外,**头像 / 图标 / 独特图案 / 一切文本**都可能可点(开详情 / 选中 / 切换 / 拖拽)—— 每个候选都**试一次交互**确认,才能确保无遗漏。清单上每个元素还要知**点后跳哪 / 干嘛(行为)**,光认出名字不够。

**子态覆盖关系是 id_mark 设计的前置**:穷举交互时,每遇到 overlay / 子态(画面被覆盖层 / 弹窗盖住),除了记它的入口 / 出口,还要**观察并记下「它盖住父屏哪些区域 / 哪些稳定元素」** —— 这份覆盖关系是 §4.3 id_mark 设计的关键输入。判据:能说出「本画面有哪些子态 + 每个子态盖住父屏哪些元素」才算探索充分,id_mark 设计才能开始。

### 3.2 探查纪律(凡逐个交互探查都守)

- **探查顺序:不可逆出口最后**。先交互**留在当前画面的**(展开 / 选中 / 切 tab / 开子面板 —— 能返回原画面继续),把**会离开当前画面**的出口留最后;尤其**离开后回不来**的(进入战斗 / 开始挑战 / 确认推进 / 传送 / 消耗类)—— 点掉就走了,没探完的元素再也探不到。**结合本画面判断哪些交互是「回不来」的出口**(非机械规则:子菜单离开能返回、副本「开始」进战斗不可逆);判据:这交互离开后还能回到当前画面继续探查吗?能 → 可早探;不能 / 不确定 → 最后探,甚至先不交互(靠代码 / 别的途径补该元素认知)。
- **每次交互前后做状态读取对比**:交互可能**无意改变状态**(选中 / 拖动 / 消耗 / 进入子层),"画面看起来没变" ≠ "没动"。交互前用 OCR / 身份识别读关键状态(选中项 / 场面布局 / 资源数),交互后再读**对比**。盲点交互不对比 = 副作用悄悄累积你都不知。
- **禁干卡**:反复点同一处 / 反复 ESC 同一个 / 盯着画面猜 / 无观察地盲点 —— 干卡不产生新信息,只耗时间 + 误触累积副作用。**「卡住」= 触发强制探索协议(§3.3)的信号,不是「再试一次同一个无效操作」的信号。**

### 3.3 强制探索协议(状态不清的动态画面,禁止干卡)

「先建档」不是盯着画面继续想 —— 状态不清的画面(覆盖层 / 不知怎么进来的子屏)得**主动交互把行为摸清**。建档/快修判据触发(说不出全部元素 + 各自跳哪)→ 按序执行:

1. **回溯怎么进来的**:读日志 / 截图序列 / op 历史,定位上一步哪个动作落到哪个 UI 元素触发了这屏。搞清入口常直接揭示"这是误触,该回退"。
2. **系统找出口**:逐一试退出手段(ESC / 关闭按钮 / 返回 / 已知的推进按钮),**每个试完等动画 + 截图看结果**,别只试一个就放弃。
3. **穷举可交互元素,逐个交互并观察**(守 §3.2 探查纪律):每次交互后必须观察结果(截图 + OCR / 视觉大模型),记录"点它 → 发生什么"。这是把"认知不完整"补全的唯一办法;探索技巧见 §2.2。
4. **交互前后状态读取对比**(§3.2 同款,关键,别漏)。
5. **收尾判据**:循环 1-4 到能说出"全部可交互元素 + 各自点后跳哪"→ 认知完整,回正常建档(§4)/ debug;**仍卡 → 升级问用户**,别无限试。

### 3.4 交互类 area 必须 click 实锤(硬规则,视觉定位再准也不能替代)

要作为**交互点**(bot 会点它推进流程)建 area 时,VLM / 目测 / grounding 定位的坐标**必须当场 click 实锤**(点击 → 画面可观测变化)才算建档完成。**「坐标在哪」与「它是可交互元素」是两个独立命题** —— 视觉定位再准只证前者;**展示图 / 装饰性图标与真按钮在画面上无差别**,VLM 保证不了可点性。判据:纯展示 / 识别类 area(只读不点)不要求实锤;凡会被点的坐标,没有 click 实锤记录 = 建档未完成。

定位/验证的纪律:
- **同源禁令**:验证素材禁用待验坐标自裁的图 —— 拿按同一套坐标裁的模板 / 样本回投比对 = 自证循环不是证据,验证信号必须来自独立来源。
- **覆盖测试协议**:拖拽类目标逐格真拖过去并回读落位,替代静态截图逐格比对 —— 整排错位时读数可因邻卡残影恰好逐位吻合,图像比对骗得过、真实点击骗不过。

### 3.5 跳转关系是路由数据,落 `goto_list` 而非只进 doc

交互验证确认「点某元素 → 跳到某画面」后,把目标画面名写进该 area 的 `goto_list`(`upsert_screen_area` 填;目标名与 screen_info 的 screen_name 完全一致,拿不准用画面名清单工具查全量)。**为什么是硬要求**:`goto_list` 是画面路由图的边,`round_by_goto_screen`(op 层自动导航)与画面路由导航工具都靠它寻路 —— 只写进 doc 不落 area = 路由图缺边,导航报「无路径」。

- 验证边接通:用画面路由导航工具导航到本画面(从路由可达的邻居出发),能到达 = 边通;报「无路径」= 某个 `goto_list` 缺边,回补而非硬试坐标。
- **不可逆 / 消耗类出口(战斗确认 / 抽卡 / 删除)同样如实落** —— goto_list 职责是如实记录跳转关系(建档完整性,不做安全过滤);寻路会沿边自动点击,路径安不安全由使用方负责。
- 兜底画面:无匹配(`screens=[]`)时先想**兜底画面**(loading / 对话 等通用画面,无固定文字特征但结构固定):截图符合兜底结构 → 按兜底画面识别 + 建档(不必精准 screen 匹配);否则 screen_info 缺口,画面未收录。

## 4. 建档

### 4.1 子态归属四问(独立 screen_info/doc vs 父屏加 area)

先判:**独立画面**还是**已建档画面的子态**(模态/弹窗/状态,如对话框、loading/ready 子态)?遇「已建档画面出现新状态 / 变体」时,按序过四问(doc 归属同理):

1. **dispatch 判据**:这个状态变是否需要 op loop 走**不同分支**(不同节点链 / 不同 handler)?是 → 独立屏候选;否(流程只差某个按钮 / 读数)→ 父屏 area 候选。
2. **遮挡判据**:它盖住父屏 id_mark 吗?
   - **不盖** → 继续问③。
   - **盖** → 先看**父屏能否换一组不被盖的稳定 id_mark**(父屏还有其他独有稳定锚 → 换掉被盖元素,子态仍留父屏加 area);但换之前先比**区分度收益** —— 若被盖元素做「父屏含被盖元素」的双向配合正好一次区分多个 overlay(§4.3 场景①④),**留着被盖的比换锚更优,别机械能换就换**。
   - **换不掉**(父屏无其他合格锚)或**故意留被盖元素做双向区分** → 才独立建屏(§4.3「遮挡父屏 id_mark 的子态」)。「被迫独立」是穷尽换锚选项后的结论,不是遮挡一发生就触发。
3. **正交判据**:它能与其他子态**同时出现 / 叠加**吗?**正交态必须父屏 area** —— 独立建屏 = 每个组合一个屏,N×M 组合爆炸,且叠加帧哪个屏都 `is_precise` 不了。互斥态才允许独立屏。**本问一票否决独立屏(即使①②指向独立)。**
4. **粒度判据**:变的是**单元素 / 文案**(某按钮换文案、某图标出现)→ 父屏 area;变的是**整体布局** → 独立屏。

四问结论:③正交一票否决;其余任一问指向独立(②需穷尽换锚)→ 独立屏;全不指向 → 父屏 area。**问间冲突时①是主判据**(分支需求是建屏的根本理由)。**典型错法**:照抄先例独立建屏,但先例是四问全中,第一个正交态案例照抄就会组合爆炸 —— 先例碰巧全中不代表判据就是「独立」。

**配套(查找端纪律)**:跨屏正交元素(叠加态下仍要找的按钮 / 读数)的**消费端代码不得锁死单一屏查** —— 按屏查 area 在叠加态落空;应查多屏 / 或对该元素用全屏 OCR 兜底。

### 4.2 screen_info:SCREEN 层全建 / AREA 层增量

- **操作纪律:area 走 CRUD 工具,禁止手编 yml 或手改模板目录** —— 用 `analyze_screen` / `upsert_screen_area` / `delete_screen_area`(项目 MCP 后端暴露,命名空间前缀 per-project),别写 HTTP 客户端脚本;area 改动经 `save_screen` 同步合并缓存(`_od_merged.yml`),**手编不重算缓存 → 后端按旧缓存加载 = 找不到模板 / area,改了也白改**。模板改名 / 加 area 涉及多文件(目录、config、yml、合并缓存)→ 一律经工具或同步合并缓存。
- **SCREEN 层**:凡 bot 要识别 / 交互的画面都建 entry(别因"OCR 够"跳过);**其他可能出现的画面也建档保存**(至少能被识别)—— entry 价值不止 OCR 检测(is_precise 精准匹配 + 坐标单一真相源 + 区域识别地基),且 id_mark 可能误匹配,**覆盖越广,id_mark 唯一性越有把握**;过渡帧 / loading 走兜底画面(§3.5),不正式建。
- **AREA 层**:增量加(bot 用到哪个元素才加哪个 area,别堆全)。加哪种:
  - **检测要精准** → 加 **id_mark area**(§4.3)。
  - **要点固定按钮 / 读固定区域 → 加 pc_rect area(坐标的单一真相源)**。判据:**op 代码里出现硬编码 `Point(x,y)` / `Rect(...)` 去点 / 读某个固定 UI 元素 → 该坐标必须进 screen_info 作 pc_rect area**,op 经 `round_by_find_area` 判定或读 area 的 `pc_rect.center` 点击,不能留魔法常量散在代码里。理由:screen_info 是坐标的单一真相源(可视化、可校验、跨 op 复用、改一处传导)。
    - **检测用 OCR ≠ 坐标可硬编码**:即使检测用 `round_by_ocr`,只要**点击目标不是 OCR 命中的文字本身**(如检测"未达上限"但点旁边的"确认"),点击坐标就要进 screen_info。只有「点 OCR 命中的文字本身」才不需单独建 area。
  - **area 命名**:用功能名(中文,如 `按钮-确认`),别用坐标(如 `按钮-960x898`)。
  - **文本锚(text/OCR 类 area)矩形 = 整条 OCR 行的外接矩形**:识别走全图 OCR + rect 过滤,按「OCR 行矩形与锚矩形重叠率 ≥70%」筛选 —— 矩形只框行内一个短语会套不住整行识别结果,锚恒 miss。锚文本 = 该行完整文本;要短文本判别就选短且独立的行,不在长行里框短语。模板锚(裁剪匹配)无此限制。

### 4.3 id_mark 设计(画面唯一标识,贵精不贵多)

**核心目标 = 区分度(越高越好)**。框架匹配语义:某画面所有 `id_mark=True` 的 area **全命中 → `is_precise=True`**;无 id_mark → 只按命中数模糊 top_n。两种提升手段:**组合多个 id_mark**(都要命中才算精准,组合更难被别屏凑齐);**选更长 / 更独有的文本**(长文本天然子序列重叠率低,见场景②)。

**「稳定」的精确定义**:**每次进该画面(不含子态)都稳定出现 + 内容不变**(不是角色名 / 动态数值 / 随局变化的文本),**与「是否被子态覆盖」无关** —— 会被子态盖住的稳定元素**也是合格 id_mark**,且正是区分 overlay 子态的关键(场景①)。判据一句话:进父画面(无子态)时它每次都在 + 文字不变 = 稳定。

**列表 / 可滚动画面的附加判据**:id_mark 只选**不随滚动移动 / 消失的外壳元素**(屏标题、固定按钮等 chrome);列表内容会随滚动滚出视野 —— 一滚动 id_mark 就缺命中,画面判定变不精准。选前自问:用户滚动几屏后,这个元素还在屏幕上吗?

**选锚流程(有视觉能力时,四步)**——视觉负责「快」,运行时匹配负责「准」:视觉判读只是先验,**id_mark 的最终资格由运行时匹配实测定谳**(视觉说「独特/清楚」≠ OCR 读得出、模板匹配得到):
1. **视觉枚举候选**:看整屏找「独有 + 固定不变」的元素(画面标题 / 导航栏 / 固定按钮这类界面骨架)。
2. **跨帧验稳定,内容位一票否决**:取 ≥2 张**不同时间**的实拍帧,视觉对比候选区域 —— 内容一致才继续。**视觉跨帧对比是发现「内容位轮换」的唯一便宜手段**(活动 banner / 新闻轮播这类槽位,单帧看怎么都像稳定锚,换了版本就换内容);OCR 层看不出「内容变没变」。
3. **兄弟屏粗筛碰撞**:候选若是短文本 / 同家族画面共有的字样,先看兄弟屏归档帧上是否也出现,别等测试撞了再回来换锚。
4. **运行时匹配定谳**:过 §6.2 id_mark 测试(真阳性 + 无碰撞)才算选中。

**分发/分类用 id_mark 上线前过语料双向验证**:① 在本画面**全部已存档实机帧**上验证 True;② 在与它堆叠的底图/兄弟画面帧上验证 False;两向都绿才进分发。单帧扫不出合法变化源(按钮显隐/图标位移/遮挡),误杀会让依赖该识别的画面链(含退出路径)失效(实证:单帧通过的新 id_mark,语料批跑误杀 18/57)。验证脚手架 = 测试仓 screens 语料目录 + `screen_utils.is_target_screen` 离线批跑。

**id_mark 区分场景(按场景定,别只凭「独有稳定」就拍)**——选 id_mark 前先过 §4.1 四问定独立屏 / 父屏 area(归属是 id_mark 设计的前置):

- **场景① overlay 子态 vs 父屏(双向配合,真正区分不用测试豁免)**:子态(overlay)id_mark = 自己独有的标题(可 + 父屏透出的稳定元素做组合);**父屏 id_mark 故意含一个「子态会盖住」的稳定元素** → overlay 帧父屏凑不齐 → 两类帧各只一个 `is_precise`,**真正区分,不用靠测试豁免**(场景③)。
- **场景② 兄弟/同类屏共享子序列 → LCS 假匹配(短文本坑)**:框架用 `lcs_percent = LCS / len(id_mark 文本)` 做模糊匹配。**短 id_mark(如 4 字)与别屏文本共享 2 字子序列 → 2/4=0.5 ≥ 默认阈值 0.5 → 假匹配撞车**;长文本天然更不易撞(2/6=0.33 < 0.5)。解法(按优先):① 用更长 / 更独有的文本;② 收紧 lcs 阈值(如 0.7 —— 救得了「重叠≈0.5」,救不了「全等」);③ 加第 2 id_mark 组合;④ 用 area 位置区分(两屏标题 pc_rect 重叠则无效)。判据:**兄弟 / 同类屏选 id_mark 前先查文本间共享子序列**,短文本共享 → 用长文本 / 收紧 lcs / 组合,别只靠默认阈值 0.5。
- **场景③ 子态无可见独有锚 → 不设 id_mark**:某子态无独有稳定文本锚(或被它盖住的元素多)→ 不设 id_mark(id_mark 测试自动 skip;运行时靠 context / 非 id_mark area 认)。子态盖住父多个元素时,与其硬凑 id_mark,不如子态独立屏 + 无 id_mark。
- **场景④ 多 overlay 盖同一父元素 → 父用该元素一次解多撞车**:多个中心 overlay 都盖父屏同一稳定元素 → 父屏含该元素一次,全部 overlay 帧都不命中父屏 —— 一个被盖元素解多个 overlay 撞车。

**遮挡父屏 id_mark 的子态 → 建独立 screen_info(父屏名前缀)**:某子态**盖住父屏 id_mark** 且父屏换不掉被盖锚(§4.1 问②,含「故意留被盖元素做双向区分」的反向收益)→ 建**独立 screen_info**:`screen_name` = `<父屏>-<子态>`(如 `商店-购买弹窗`)。子态有可见独有锚 → 设自己的 id_mark;无可见锚(如通用弹窗)→ 不设(场景③)。

> id_mark 准确性测试:项目应提供(方法论见 `references/id-mark-test.md`,缺则照建);**每次建档归档后跑(§6.2)**,fail 即 id_mark 撞车 / 坏 / 缺。

### 4.4 坐标获取:视觉直读默认,OpenCV 只管像素级精准

- **坐标默认视觉直读**:会话模型有原生视觉就自己看图,逐元素读绝对像素坐标;没有 → **派子 agent 使用有视觉的大模型**(完整任务自包含外包,别只要「描述 / 坐标」这类中间产物再由文本侧拼装)。别猜 / 推算坐标(估算值标「待核」必须回头核);视觉坐标与既有参照(`pc_rect` / 旧假设)冲突 → `analyze_screen` 回验 / 交互实锤客观裁决,别拿未验证的旧参照否定视觉判读。
- **视觉的两条不可信线**:空间关系判断(「A 与 B 对齐 / 居中 / 重叠」)→ 用数值测量(中心距 / IoU),别靠看;颜色精确值不可信 → 定性描述(亮 / 暗、蓝调)可用来选信号,精确阈值 / RGB 由 CV 采样定(`np.mean(bbox)` / k-means 主色)。
- **OpenCV 只在要像素级精准时上**:① 模板裁剪 / 批量采库的元素定位 —— squares 多阈值几何检测(判几何不判颜色,免疫元素颜色随稀有度 / 等级变)、`HoughCircles` / 轮廓圆度(程序绘制的简单几何形边缘锐利,轮廓检测远胜硬编码坐标);② 小目标先裁切到目标区 + 放大再定位;③ 颜色阈值采样(接上条)。
- **模板去背景**:mask(`auto_mask` / `mask.png`),模板结构见 §5.2。
- **识别方案升级路径(ladder)**:经典法(CV 阈值 / 几何 / 模板匹配)撞上结构性相似负类时逐级升级,禁跳级:① 经典法在跨场景样本集上量化穷举(每法留数据,无一达标才算全败)→ ② 全败才用视觉大模型过渡判别(经典法产出候选,裁切逐个客观确认;显式标注「过渡,非终态」)→ ③ 积累结构先验(位置可判别替外观可判别)回到纯代码;画面模型覆盖后撤掉视觉调用,视觉路径长期滞留 = 该 ladder 没走完,当问题记录。

**doc 归属按 §4.1 四问同判据**:
- **独立画面** → 新建 `docs/game/screens/<name>.md`(中文 screen_name;文件名英文 snake_case、不带冒号等特殊字符),登记进 `docs/game/screens/README.md` 索引(一行)。
- **子态** → 并进父画面 doc:「何时出现/状态流转」补该子态的**入口(从哪来)+ 出口(动作→下一态)**、「可交互元素」补该态元素、「识别快照」加该态子表;不另开文件、不登索引。

**建档文档 = 稳定的画面参考(事实),不是建档过程的日志**。描述类章节只写**画面本身的事实**;**不进 doc**:测试结果(通过/失败,归测试仓)、bug/修复历史(归 commit/PR);**进「备注」并与事实分开**:开放问题、screen_info 现状缺口、易变点。判据:每句问「这是画面本身的事实,还是建档/排查过程的产物?」后者不进描述章节。

新画面 doc 结构:
- frontmatter:`screen_name` / `appears_in: [gameplay_name...]` / `last_updated`(核对日期)/ `source_image`(**归档后用测试仓相对路径 `screens/<screen>/<state>.webp`**,第 6 步归档后更新,别留临时截图名 / 只写 state 名)。
- **何时出现 + 状态流转**:出现条件 + 前后邻居;**多子态画面必须记状态流转**(每子态:入口 = 从哪来[动作/条件]、出口 = 动作→下一态),用表格或链式表达。
- **识别特征(稳定锚点)**:稳定文字 / 模板图标 / 固定图标;标注易变值(版本号 / 进度 / 公告)勿当特征。
- **可交互元素**:每个元素记**点后行为**(跳转 / 弹窗 / 消费 / 无反应 / 纯显示);图形按钮注明「需模板/CV」;交互后弹出子面板 / 子态里的**新交互递归验证 + 记**(点开看有无新交互,验到叶子)。
- **automation 要读信息**:本画面 bot 做决策 / 存策略状态所需的数据 / 反馈(如 HP / 金币 / 轮次 / 选中态 / 反馈信号)—— 列清单,这些要建 area 供 op 读取;漏建 → op 拿不到 → 策略瞎跑。
- **识别快照** = ① 匹配画面 + is_precise;② 匹配 area 表;③ 全量 OCR 文本。多子态画面每子态快照用 `### N. 子态名(source_image)` 编号子标题。
- **备注 / 待查**:screen_info 现状、开放问题、变更检测方法、易变点。

**选择类画面建档三要点**(从 N 个选项里单选 / 多选:选中态 + 推进按钮 + 点击位置):
1. **选中态怎么呈现 —— 多种手段穷尽,别预设**(OCR「已选中」/ 视觉高亮边框 / 勾选 √ / 推进按钮灰→实 / 角标)。建档时 OCR + 视觉大模型 + 点击验都试,doc 记本画面**实际**怎么呈现。状态指示图标的模板建模见 §5(每态一模板 + 高阈值)。
2. **推进按钮记灰 / 实两态**(名字未必叫「确认」):两态都建,op 靠它判"可推进了"。
3. **点哪选中 —— 避开选项上触发别的交互的子区域**(图标开详情 / 按钮刷新 / 预览开大图):实测校准,doc 记"点哪个坐标 = 选中"。

## 5. 模板建模(图形 / 图标按钮;文字走 OCR)

**大原则:优先"建档时一次识别 → 存 screen_info → 自动化复用固定坐标 / 模板";运行时动态识别(CV / 视觉大模型)只用于真的运行时变化的元素。** 固定 UI 一次测准存 screen_info 即可,别每轮重检测。

### 5.1 识别方式决策(对每个 bot 要识别 / 交互的元素,按性质选)

1. **有稳定文字** → OCR(不截模板);文字独有且作画面锚点 → 设 `id_mark`(OCR area)。
2. **固定图形(图标按钮 / 状态指示 / 徽章),每次长得一样** → **截模板**(§5.2);该图形独有 → 可作 id_mark 模板。状态指示(radio 选中/未选中、下拉 ▽/△、勾选框)→ **每态一个模板** + 高阈值(0.9)区分。
3. **变化的多实例(角色立绘 / 头像 / 商店牌)** → **模板库 + 特征匹配(SIFT)**,非单模板。⚠️ 三个坑(触发条件+后果,建库必守):**整库同来源** —— 混来源(图鉴 + wiki 拼着补)→ conf 崩(脸近景 ≠ 半身,来源不一即崩);**标签↔图标按空间位置对齐,不按行索引**("第 N 个图标 ↔ 第 N 个名"—— 滚动后顶行被面板裁切 → CV 漏检顶行 → 索引错位 → 整行名贴错图);**存图 `cv2.imencode` + `ndarray.tofile`,非 `cv2.imwrite`**(Windows 中文路径挂)。建图鉴库的完整工序(图鉴优先 / 解锁过滤 / 采全判据 / 滚动翻页 / 采库脚本持久化 / 对齐实现)见 `practices/template-library.md`。
4. **要计数 / 定位(槽位数 / 头像位置)** → 多为**建档时一次 CV 检测**(轮廓 / 颜色阈值 / HoughCircles),结果(坐标 / 计数)**存 screen_info**(pc_rect),自动化用固定坐标 —— 很少需运行时动态 CV(仅布局运行时真变化才动态)。
5. **稀有 / 多类多实例(杂乱场景目标)** → YOLO。

### 5.2 图形按钮截模板(定位 → 裁 → 入档 → 回验)

1. **定位**:圆形 → `cv2.HoughCircles`(扫 param2 / 半径,取稳定命中数);其它形状 → 轮廓 + 圆度 `4πA/P² > 0.7` 或颜色阈值。两法互相印证。坐标获取方法论见 §4.4。
2. **裁模板**:用项目 `TemplateInfo` 生成(结构对齐既有模板:`raw.png` + `mask.png` + `config.yml`,`template_shape: circle` / `auto_mask: true`)。⚠️ `screen_image` 必须用**原始截图**(PNG / 未压缩),不要用 webp 归档版(lossy → 小区域裁剪放大 artifacts → 模板 conf 降)。
3. **入 screen_info**:`upsert_screen_area(screen_name, area_name, pc_rect=[x1,y1,x2,y2], template_sub_dir, template_id, ...)`。area_name 用功能名(中文),template_id 用英文 snake_case。**裁模板的框和写 pc_rect 的框大小不同**:裁模板框**紧贴图标**(图标多大裁多大);写 pc_rect 框**比图标大一圈**(紧贴框每边 +10px,夹到画面边界内)—— 给 template match 留余量,图标位置稍偏也能找到;pc_rect 别重叠邻接按钮。⚠️ 错的(别犯):pc_rect 写成紧框 → 图标偏几 px 就匹配不上;模板用大框裁(带余量)→ 模板多一圈背景,匹配分降。
4. **回验**:再跑 `analyze_screen`,确认新 area 命中、conf 高。

### 5.3 模板资产目录规范(首建即守,别先散放后迁移)

- **统一放项目的模板资产根 `<模板根>/<玩法>/<类型>/`**(典型如 `assets/template/<玩法>/<类型>/`):一级按玩法 / app 归组,内按**类型**分子目录,类型名自明语义(portrait 立绘 / equip 装备 / star 星标,按玩法实际内容定,原则「看目录名知道装什么」)。**别与既有玩法模板平级另立新根**。
- **源码包内禁放模板资产**:模板是运行时资源不是代码 —— 藏进源码包目录后散布无人知、构建打包易漏。
- **同类目标只一个库,别建同义双库**:发现「新旧来源并存」不是建第二个库的理由 —— 选定一个来源,迁移合并旧的;确需并存时在 config / 文档标明来源与用途差异。
- **生成器产物标注来源**:脚本烘焙 / 生成的模板在 `config.yml` 或生成脚本 docstring 标注来源,与手采模板可区分 —— 来源不同的模板混库是 conf 崩的常见根因。
- **首建即在规范目录建** ——「先临时放,以后迁」的「以后」不会来,散布就是这么长出来的。

## 6. 归档与 id_mark 测试

### 6.1 归档代表截图

每画面归档一张代表截图(多子态画面每子态一张)到测试仓 `screens/<screen_name>/<state>.webp`,供后续测试 fixture + 文档溯源。

**测试可用性**(归档 webp = mock 测试 fixture):
- **稳定态**(非过渡/动画帧):操作后 sleep 等动画完再截(§1.6;截过渡帧 → mock 不稳定)。
- **覆盖该 screen 关键 area**:测试断言依赖的 id_mark / 文字 area 要在帧内 + 命中(截完用 `analyze_screen` 回验目标 area 命中再归档)。
- **多子态每态一张**(测不同分支);**文件名 = 可读 state**(如 `派遣中.webp`,非截图时间戳);screen_name 含冒号用下划线。

**格式 + 路径**:webp q90(有损压缩,但整屏 OCR / 模板匹配实测识别无损效;省空间)/ 1080p 原生不缩放(同 screen_info 坐标)。⚠️ webp 归档版**不能当模板裁剪源**(§5.2),模板裁剪用原 PNG。⚠️ **路径是测试仓根 `screens/<screen_name>/<state>.webp`**(非 `test/screens/` —— mock 测试从测试仓根 `screens/` 加载,归档错位置 → 测试找不到 fixture)。

**转换**:用本 skill 自带的 `convert_to_webp.py`(`python <本 skill 目录>/convert_to_webp.py <图片.png | 目录>`,单张或目录批量),**不要手写转换逻辑**(易漏 Windows 中文路径坑)。webp q90,保留原 PNG 作模板裁剪源。

**覆盖检查(防断测试)**:归档时若目标 webp 已存在会被覆盖 / 要删旧图 → **覆盖前先查该图是否被测试 fixture 引用**(查测试代码读 fixture 的调用)—— 无引用可覆盖/删;有引用 → 用**不同 state 名**区分,旧图确需替换则先改测试引用。

**doc 不写具体 webp 数**(如「22 张」)—— 建档频繁加截图,数字易过时。写「实拍归档(测试仓 `screens/<name>/`)」即可。**归档后更新 doc `source_image`** 为测试仓相对路径。

**id_mark 的 pc_rect 比文字框宽一圈**(crop-OCR 坑):`find_area_in_screen(crop_first=True)` 先裁再 OCR —— **小 / 紧 / 背景杂的裁剪会让文字检测器漏检**(全屏能识别的,裁小框后丢字 → 真阳性失败)。解法:pc_rect 宽一圈给上下文(同 §5.2 模板 pc_rect 放大原则);**跨全部 fixture 验真阳性**(同尺寸 pc_rect 在不同背景的 crop-OCR 表现可能不同,少数几张过了不代表全过)。

### 6.2 id_mark 准确性测试

跑项目的 **id_mark 准确性测试**验本屏(真阳性 + 不撞别屏),可 `pytest -k '<本屏>'` 只测本屏;**项目若无此测试,照 `references/id-mark-test.md` 方法论建一个**。fail → 修 id_mark 再算归档完:
- **撞车(误命中别屏)**:按场景解(§4.3)—— 兄弟屏共享子序列 → 更长文本 / 收紧 lcs;overlay 盖父元素 → 父屏 id_mark 含被盖元素做双向配合;子态无独有锚 → 不设 id_mark。
- **坏 / 缺**:加独有锚 / 遮挡子态拆独立 screen(§4.3)。
