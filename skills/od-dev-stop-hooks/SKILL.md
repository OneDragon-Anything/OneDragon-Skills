# 停机钩子生命周期与停机现场处理

实机范式前提:没有模拟环境、对游戏当前状态无先验理解 → **实机是唯一测试环境**,埋在运行代码里的钩子就是观察与断点基础设施(定位发生的时间地点 / 捕获会话内造不出的随机态 / 停机等 AI 现场接手)。**停机现场是不可按需复现的实机证据**——该状态错过可能不再现,本 skill 所有纪律由此派生。

单一源切分:本 skill 只管**停机钩子的生命周期判据 + 停机现场处理协议**。埋钩子的代码手法(方案 / 前置门实现 / sentinel 写入代码)→ `od-dev-write-operation` runtime-craft「钩子触发停 bot 留画面」;停机 vs 采集的分流判据 → `od-dev-gameplay-automation` runtime-iteration「随机态钩子分流判据」;现场建档流程 → `od-dev-screen-onboarding`;run 被停的死因排查(不知道谁停的)→ `od-dev-debug-automation` §1。

## 0. 停机现场必做清单(遇钩子预期停机;没做完这 5 步不算完成)

1. ☐ **判归属**:停机现场事实在且自描述——日志 `[stop]` 行(框架钩子:reason + 截图路径)或 sentinel flag 文件(存量钩子:「HOOK-STOP」类标记)= 钩子预期停机 → 走本协议;不知道谁停的 → 先按 `od-dev-debug-automation` §1 四层排查,查明是活钩子预期停再回这里。**必做**
2. ☐ **读现场三要素**(触发定位 / 可执行处理步骤 / 删除或移除条件),照处理步骤走;步骤不在现场事实里 → 查项目守卫文档(guards 类),再缺 → 按 §1.3 钩子类型默认流程。**必做**
3. ☐ **处理目标态**(建档 / 点开确认 / 交叉验证),过 §1.2 禁绕过清单——出现「先跑起来」「大概是 X」类念头时,先回清单对照再动手。**必做**
4. ☐ **闭环收尾**(按 §2.1 分类):临时捕获钩子 → 删钩子代码 + 重启载入代码的进程(存量 flag 钩子同时删 flag);常驻兜底钩子 → 只重启 + 把现场缺的要素补进钩子代码,钩子保留。**必做**
5. ☐ **收尾自查**:grep 确认该删的钩子代码无残留、lint 干净;降级 / 移除过钩子的 → 用户已点头。**必做**

## 1. 停机现场处理协议(消费侧)

### 1.1 先判归属

- **现场事实在且自描述** = 预期停机 → 本协议。载体两代并存:**框架钩子** = 日志 `[stop]` 行(reason 含钩子标记与定位)+ 框架自动截图(框架 `stop_running(reason, save_screenshot=True)` 一行处置,截图落运行产物图目录);**存量钩子** = sentinel flag 文件(钩子标记 + 位置 + 收尾动作)。
- **载体在但内容裸**(只有状态名 / 数字)→ grep 写入者定位是哪个钩子(「反复出现的产物 = 活的生产者」,判据见 `od-dev-debug-automation` §4);查明是活钩子 → 本协议,并按 §1.3 默认流程处理 + 补要素。
- **没有现场事实、不知道谁停的** → 不是本 skill 场景,先按 `od-dev-debug-automation` §1 四层排查判死因。

### 1.2 禁绕过清单(压力下也守)

停机钩子的存在理由 = 该状态需要现场处理(建档 / 确认 / 验证)。以下做法都是**绕过它的变形**,禁止:

- **降级钩子(停机→留证)继续跑**:这是修改生产侧决策,**必须用户点头 + 携带证据结论**(§2.3),agent 只能提案不能自行降级。合理化「带病跑总比停着强」不成立——带病跑烧掉的是不可复现的证据。
- **降阈值 / 放宽匹配硬塞一个身份**(「低分但大概是 X」)= 用猜测掩盖未建档,识别缺陷被埋进主线。
- **单源归因**(一次视觉模型问答 / 「是旁边 UI 挡了」)= 证据不足;视觉模型提问纪律与多源交叉见 `od-dev-screen-onboarding` §2,至少双源一致才可采信。
- **直接删钩子 / 删 flag 继续跑** = 丢弃知识缺口,下次同一态再停一轮,什么都没省。

Red flags(说出即停,回本清单对照):「先跑完这局再建档」「大概是 X 之类的」「阈值调低点先配上」「这个 flag 碍事,删了」「问视觉模型一眼,说是什么就是什么」。

### 1.3 flag 缺要素 → 按钩子类型走默认流程

- **未知画面**(钩子因「画面 / 子屏不认识」停)→ 按 `od-dev-screen-onboarding` 建档(存证截图就在 sentinel 里)。
- **未知物品 / 元素**(钩子因「出现不认识的东西」停)→ **先确认存证截图在手**(交互会推进画面,证据先保全),再点开 / 交互确认其身份与行为,建档。
- **识别可疑**(钩子因「读数异常 / 置信可疑」停)→ 交叉验证三分支:离线重放存证 / 换识别路径复测 / 对照独立数据源;结论要么「识别缺陷」(修识别)要么「真状态」(建档),不许「存疑放着」。
- 处理完**把 flag 缺的要素补进钩子代码**(§2.2),下次触发不再裸。

### 1.4 证据保全纪律

停机现场截图 / sentinel 是该状态的全部证据:**先复制保全,再交互**(点开确认 / 建档交互都会推进画面,推进后原状态没了)。画面已被游戏动画推进走(只剩存证截图)→ 走 `od-dev-screen-onboarding`「随机/条件态」节的停机后画面已流转降级路径。

## 2. 钩子生命周期判据(生产侧)

### 2.1 两分类:临时捕获 vs 常驻兜底(收尾不同,flag 第三要素不同)

| | 临时捕获钩子 | 常驻兜底钩子 |
|---|---|---|
| 触发条件 | 特定目标态出现(珍贵 / 随机 / 会话内造不出) | 任何「持续未识别 / 未知」状态(安全网) |
| 存在理由 | 捕获一次,建档后使命完成 | 知识缺口存在一天就活一天 |
| 收尾条件 | **删除条件**:该态建档确认后删整段钩子 | **移除条件**:该类未知态全部建档后才可移除;平时触发只删 flag |
| flag 第三要素 | 删除条件(「处理完: 删钩子 + 删 flag」) | 移除条件 + 每次触发的处理步骤 |

⚠️ **兜底型按临时型写**(注释「建档后删本钩子」但实际是安全网)= 要么误删安全网、要么永远「临时」。埋之前先分类,分类写进钩子注释首行;判断已有钩子属哪类:看触发条件是**点名某个态**(临时)还是**兜一切未知**(常驻)。

### 2.2 现场三要素(契约;载体两代并存)

1. **触发定位**:谁停的(钩子标记,如 `HOOK-STOP`)+ 钩子位置 + 触发态 + 时间。
2. **可执行处理步骤**:接管者照做就能处理的一句话(缺了它接管者只能瞎猜——审计中最常见的不合格项就是只有定位没有步骤)。
3. **删除或移除条件**(按 §2.1 分类写)。

**载体**:新钩子优先用框架处置壳——`stop_running(reason=..., save_screenshot=True)` 一行,框架自动截图 + `[stop]` 日志行承载①②,处理步骤细则归项目守卫文档(guards 类),**勿自带截图/flag 文件写入代码**;存量 flag 文件载体(三要素写在 flag 内容里)照旧支持,直到随清理批退役。

格式示例与 sentinel 写入代码手法见 `od-dev-write-operation` runtime-craft「钩子触发停 bot 留画面」(本 skill 锁契约,不复制代码)。

### 2.3 降级治理(停机→留证 / 留证→停机)

- **降级双条件**:①**证据结论**——为什么不值得停(触发分析 / 离线重放定位了根因且误报源已修复,停机只会反复阻断实跑);②**用户点头**。缺一 = 逃生口,禁止。
- **agent 只能提案**:给出证据结论 + 降级影响(该类态今后只留证不停机,现场处理机会放弃),等用户决定。
- **反向升级同理**:留证钩子发现问题需要现场接手 → 也是用户决定,不自作主张升停机。

### 2.4 埋钩子前置与分层

- 埋之前:①分流判据(bot 卡住无法推进 → 停机;bot 能推进但 reader(画面读取 / 识别代码)不可靠 → 采集)→ `od-dev-gameplay-automation` runtime-iteration「随机态钩子分流判据」;②该态是否每 run 必现(必现 → 先建档别停机)与前置门实现 → `od-dev-write-operation` runtime-craft 钩子节步 1a / 步 2。
- **分层架构**(识别可疑类钩子):识别先行(低置信只留证记录,不阻塞流程)+ 语义确认停机(留证攒够证据、确认真信号后才升停机)——别一疑就停,停机是确认后的动作不是第一反应。
- 临时捕获钩子代码内必带自指针注释(「确认建档后删本段」);常驻兜底钩子注释首行标分类。

## 3. 审计(项目停机钩子合格性)

对项目里每个 `stop_running` 类停入口调用点过检查表:

- ☐ 现场事实载体合格(框架处置壳:reason 可定位 + 截图开启;存量 flag:文件写入在否)
- ☐ 三要素齐否(逐条:触发定位 / 可执行处理步骤 / 删除或移除条件;框架壳的处理步骤细则有守卫文档承接)
- ☐ 分类标注在否(临时捕获 / 常驻兜底,注释首行)
- ☐ 前置门在否(画面态锚点命中才检测,防过渡帧伪触发;判据见 `od-dev-gameplay-automation` 分流判据头部)

不合格 → 按 §2 补;属「常驻兜底被按临时型写」→ 改分类与收尾条件,别删钩子。
