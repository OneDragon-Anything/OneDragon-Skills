# 排查运行中自动化 bug(事后法证判据)

基座:**通用调试纪律**(读日志先行 / 假设驱动 / 一次只改一个变量,见 `od-dev-write-operation` 必守不变量 + 调试纪律)。本 skill 叠加**运行后排查**判据 —— 排查者不在场、从零重建现场才会踩的坑(开发中的调试内循环归 write-operation)。定位到根因后,**决定怎么修**见 `od-dev-deciding-a-fix`。

## 1. 先分清进程,找对日志

排查"用户反馈某次跑失败"前,先确认日志是哪个进程的(两者文件不同,看错就什么都找不到):
- **GUI / 一条龙调度器**(用户日常自动跑):项目根 `.log/log.txt`(TimedRotating,按天轮转成 `log.txt.YYYY-MM-DD`)。
- **MCP server**(给项目 MCP 工具用):其专属日志(MCP server 日志,路径按所在项目 `.debug/` 约定)。

用户反馈的运行失败几乎都在前者;MCP 工具调用本身的问题才看后者。

`run_record`(`config/<实例>/app_run_record/<app>.yml`;one_dragon 框架约定)的 `run_status`:**0 未运行 / 1 成功 / 2 失败 / 3 运行中**,配合 `daily_run_times` / `weekly_run_times` 计数判成功与否。⚠️ **run_status=3(运行中)有歧义**(还在跑 / 中断没复位)→ **交叉验活日志**:末条时间还在推进 = 还在跑;停在很久前 = 中断没复位。

**run 被停(状态 STOPPED / 日志显示提前退出)→ 先判死因,别急着归因外部**。四层排查序(由近及远,前一层排除才进下一层;每层都要有正向证据才下结论):
1. **死亡时刻日志**:用 `started_at` 锚点定位该 run 结束前的最后几条日志(先按上面分清进程:**用户日常自动跑看调度器日志;开发中经工具 / server 跑的 run 看对应 server 日志**),看有没有自家钩子 / 显式停机的日志行(钩子停机通常每停一次都写一行;连续多个 run 都早停 → 每具「尸体」上找这行,都在 = 同一生产者在杀)。没有 → 下一步。
2. **grep `stop_running`(框架公共停入口)的全调用点,自家钩子优先**:项目里谁会调停(临时采集 / 停机钩子、定时器、GUI 停按钮 handler)。⚠️ **「调用点已删」≠「已排除」**——进程没重启就还在跑旧代码(删代码后必须重启载入代码的进程才算生效;「删了但还秒停」是此形态的典型症状)。⚠️ **「人工结束」类标签是框架对任何 `stop_running` 的统一措辞,不是死因证据**—— 别拿它当「人工干的」实锤(它对钩子停、手停、外部停打的标签一样)。
3. **sentinel / flag 文件的写入者**:出现 flag 先 grep 写它的代码(谁 write、什么条件写);**反复出现的产物 = 活的生产者**(见 §4),删了又生 = 有活代码在写,先找写入者别再删。查明是**自家停机钩子预期触发**(flag 自描述「HOOK-STOP」类标记)→ 死因已明,移交 `od-dev-stop-hooks` 停机现场处理协议(本节职责到此为止,现场怎么处理别在这即兴)。
4. **最后才是外部归因(别的会话 / 工具管道 / 网络连接),且需正向证据**:要有「外部进程发过停指令」的直接痕迹(该进程的日志 / 命令历史)才成立。**以下都不构成外部归因证据**:连接数多(工具管道 / 连接池 / 子代理各建连完全可解释)、时序均匀(自家代码也是机器,「机器级精确」推不出「非自家」)、标签写「人工结束」(见 2)。

## 2. 定位故障环节(节点级)

- 从日志**节点流转**(`节点 X -> Y 返回状态 Z`)看卡在哪 —— 末尾几条流转指向故障节点。
- **数重复记录判「循环 vs 进展」**:在日志里数某句反复出现的状态/动作 —— 同一句**爆炸增长**(例如某条状态出现几千次)= 卡死循环;节点流转**在跳转推进** = 还在跑。
- 对照被测 op 代码里 `@operation_node` 装饰器连成的流转图(每个节点 + `@node_from` 边),看 bot 落在哪个分支、该分支预期会走到哪。

## 3. 识别类 bug 专项判据(画面 / OCR)

- **验证用的识别路径 = bot 运行时路径**:分析工具(`analyze_screen` 等)与 bot 运行时的画面识别可能用**不同识别参数**(裁剪方式等),边界 case 上结论会不一致 —— 分析工具说"匹配"、bot 可能"不匹配"(或反之)。**别拿分析工具的结论当作 bot 运行时的结论**;要么读 bot 的识别路径代码确认参数,要么用 bot 同参数离线复现。
- **OCR / 画面识别 bug 先离线验识别参数**:写离线脚本(用采集的截图 / 测试仓 fixture)遍历**裁剪方式(裁后 OCR vs 全图 OCR)× 匹配阈值 × 区域宽度**三者组合,锁定根因,别凭感觉猜。误匹配类 bug 常是「区域过宽 + 阈值过松 → 部分文字重叠也命中」。

## 4. 采集证据(让 bot "看见的" 可观察)

- **临时加「识别到画面就截图存盘」**:在被测 op「识别到某个画面、正要分发去处理」的位置,临时插一行 —— 把当前游戏画面截图存到磁盘(用 `is_debug` 开关包起来,只在调试开关打开时才存,免得正常运行时疯狂刷屏)→ 配合日志时间戳,事后能回看 bot 当时实际看到的是哪一帧画面。排查完**删掉这行临时代码**,别留在主线。
- **离线复现**:写个独立脚本,读采集的截图 / 测试仓 fixture,用**跟 bot 运行时一样的识别方式**(同样参数)跑一遍,改参数看 bug 是否复现 / 消失,从而验证假设。
- **反复出现的产物 = 活的生产者(与「孤儿残留」互斥)**:临时文件 / flag / sentinel / 截图**反复重现**(删了又生,≥2 次)→ 必有活代码在写。**删两次以上必须 grep 写入者**定位生产者(谁 write、什么条件),别再称「孤儿残留」——「孤儿」= 无生产者的历史遗留,与「反复重现」逻辑互斥;正确动作是找到并处理生产者(删钩子 / 改触发条件),不是反复清产物(清了再生,白清)。

## 5. 根因是「op 走到陌生画面」→ 先建档别猜修

定位到根因 = **op 走到一个你不完全认识其交互的画面/子屏**(handler 卡死 / op 报「画面不符」/ 点击落空不知落在哪)→ **先转画面建档**(按 `od-dev-screen-onboarding`):搞清画面全部可交互元素 + 各自点后跳哪,再回来改 op。

**别在画面认知不完整时猜 escape / 套兜底 / 直接改 op** —— 那是在猜的画面上修,必回归(下一个没猜到的交互又卡)。

**刹车判据**:你能否说出当前画面**全部可交互元素 + 各自点后跳哪**(对照 screen_info 的 area 定义 + op 代码流转)?说不出 / 只能猜 → 先建档,别继续 debug framing 盲改。

> debug framing(尤其进度压力 / loop 紧迫感)下默认跳「快修 / 猜 escape」不触发建档 —— 这正是要刹车的点。先确认画面认知完整,再 `od-dev-deciding-a-fix`(公共仓)定修法。
